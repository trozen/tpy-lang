# Frontend Plugin Design

Status: design draft (no implementation yet).

## Motivation

TPy targets Python source today. Some users want to translate other
source languages -- legacy DSLs, retro Pascal-family languages, internal
domain-specific languages -- into runnable native code, and would benefit
from reusing TPy's semantic analysis, code generation, and toolchain.

A **frontend plugin** is a Python module that translates source files of
some non-Python language into a `FrontendModule` (the **frontend IR**).
The compiler then lowers the IR to `TpyModule` and runs it through its
normal sema + codegen pipeline. The plugin is purely a *syntactic
frontend*: it produces frontend IR and stops.

The first concrete use case is a Turbo Pascal POC (see
`examples/frontends/pascal/DESIGN.md`). The design is also driven by a
larger internal target with cross-file implicit visibility,
project-file-driven source discovery, language-specific runtime state,
native C++ runtime bindings, and an out-of-tree plugin/runtime ownership
model. Both targets shape v1 directly. Beyond these, the IR fits
several other plugin patterns described next.

## Plugin shapes the design supports

Three illustrative shapes beyond the two concrete v1 targets. Each is
described concretely so future plugin authors can see where their use
case lands. The design supports more than this list -- the point is
breadth, not enumeration.

### Schema-driven code generation (e.g. Protocol Buffers)

Protobuf-style schemas define messages, enums, and (optionally) service
stubs. The plugin parses `.proto`, emits a `FrontendModule` with one
`Record` per message and one `Enum` per proto enum. Type references map
directly: `int32` -> `NamedType("Int32")`, `repeated T` ->
`NamedType("list", [TypeTypeArg(...)])`, `map<K,V>` ->
`NamedType("dict", ...)`, `optional T` -> `OptionalType(...)`. Imports
(`import "other.proto"`) become `FromImport`. Encode/decode methods
are generated by a TPy class macro shipped in the plugin's runtime
package -- the IR emits a `@pb.message` decorator (registered as
`MACRO` in the plugin's `decorator_manifest`); the class macro
generates the methods at sema time. Service stubs use the same
pattern at the class level: the plugin emits a `Record` for each
service with the rpc methods declared inside it and an
`@pb.service` class macro on the record; the class macro reads the
methods of the decorated record and generates the rpc-stub bodies.
v1's MACRO route is record-level only, so the unit of macro-driven
generation is the whole service class -- no method-level
decorators.

If the plugin wants a vendored C++ codec runtime instead of pure-TPy
encode/decode, `FrontendDirectives.cpp_includes` + `link_libs` pull
it in.

### Schema-only data descriptors (JSON Schema, Avro, etc.)

Pure schema files map straightforwardly to records, enums, and type
aliases. No runtime behavior to generate; the plugin's `parse()` just
translates the schema's type vocabulary into IR equivalents. Cyclic
schema references resolve through TPy's normal forward-reference
handling.

### Data files with compile-time validation (CSV, JSON data)

A plugin for `.csv` files can derive a schema from the header,
validate every row at compile time, generate a static parser
function, and store the raw data as a `StrView` constant. At runtime
the user calls a generated `get_rows()` function that invokes the
static parser on the raw text -- the parser is **infallible** because
the data was validated at compile time, so codegen can elide error
paths and bounds checks.

This pattern fits the v1 IR without exercising future requirement #21
(richer `Constant` value types): the data is stored as a flat string
(`FinalType`-compatible) and the structure is reconstructed by a
generated parser. Plugin authors can offer a `csv.storage = lazy |
eager` option -- `lazy` (raw text + parse on access) vs. `eager`
(parsed records initialized at module init) -- depending on access
patterns. Validation diagnostics use `FrontendDiagnostic` with
`source_language="csv"` so errors point at the CSV row + column in
the original file.

`.json` data splits into two cases: JSON used as a schema source maps
to records/enums (like JSON Schema); JSON used as data follows the
CSV pattern (raw text + generated parser, validated against an
inferred or supplied schema).

If the same data file is imported by multiple TPy modules, the plugin
should canonicalize: one source file -> one TPy module -> other
modules import from it. Otherwise the raw-text constant is compiled
into each importing module. This is the same canonicalization
protobuf-style plugins use; not a TPy-specific issue.

## Goals

- Let an out-of-tree translator emit frontend IR and have TPy lower,
  analyze, and codegen it like any other module.
- Stable contract surface (the IR) that is decoupled from `TpyModule`'s
  evolution.
- IR is structurally serializable (plain dataclasses + enums +
  primitives). Future cross-language IPC is "publish the schema."
- Compose with TPy's existing module-discovery model (lazy,
  import-driven) without forcing all plugins into that mode.
- Discipline against context creep: the IR is the boundary, not a
  negotiation.

## Non-goals

- **Plugins are not macros.** Macros transform Python AST during a TPy
  compile; plugins translate non-Python source *into* TPy IR before sema.
- **Plugins do not modify sema.** A plugin emits IR, then exits. No
  hooks into name resolution, type checking, or codegen.
- **Plugins do not extend the runtime.** A plugin may ship a companion
  TPy package its translated code imports, but TPy core has no special
  awareness of it -- it is a normal TPy library on the search path.
- **Lowering does not resolve names or types.** Lowering is an adapter
  + structural validator. Symbolic IR types lower to TPy parser
  `TypeRefNode`s; sema resolves those to `TpyType` as it does today.
- **No first-class IPC protocol in v1.** External compilers integrate
  via a thin Python wrapper that owns its own subprocess protocol. A
  TPy-versioned cross-language protocol = "publish the IR schema"; that
  is anticipated but deferred.

## Architecture overview

```
                               +-----------------+
  source  ----[ plugin ]---->  | FrontendModule  | ---[ lowering ]---> TpyModule
  (.pas,                       |     (IR)        |                        |
   .myl, ...)                  +-----------------+                        v
                                                                         sema
                                                                          |
                                                                          v
                                                                       codegen
                                                                          |
                                                                          v
                                                                          C++
```

The IR is the contract. Lowering owns the IR -> `TpyModule` adapter and
all parser-internal field synthesis (resolver, import maps, decorator
routing, etc.). Sema and codegen are unchanged.

## Plugin contract

```python
# tpyc/frontend_plugin.py (sketch)

class FrontendPlugin(ABC):
    api_version: ClassVar[int] = 1
    name: ClassVar[str]                                    # e.g. "pascal"
    extensions: ClassVar[tuple[str, ...]]                  # e.g. (".pas",)
    decorator_manifest: ClassVar[tuple[DecoratorEntry, ...]] = ()

    def __init__(self, options: dict[str, str]) -> None:
        self.options = options

    @abstractmethod
    def parse(self, ctx: WorkspaceContext,
              module_name: str, file_path: Path
              ) -> FrontendOutput:
        ...


@dataclass
class FrontendOutput:
    module: FrontendModule
    diagnostics: list[Diagnostic] = field(default_factory=list)
```

Plugins return raw `Diagnostic`s in `FrontendOutput.diagnostics`;
lowering wraps them in `FrontendDiagnostic` (with category
`PLUGIN_REPORTED`) before they reach the compiler's diagnostic channel
(see Diagnostics below).

Plugin discovery: a plugin module exposes a top-level `PLUGIN`
attribute set to the class (not an instance). The compiler instantiates
it once per `tpyc` invocation, passing the routed `--dsl-opt` dict.

## Frontend IR

The IR lives in `tpyc/frontend_ir/` and is composed of plain dataclasses
(no methods, no behavior). Every node in a sum type carries a `kind:
str` discriminator field for round-trip serialization without class
introspection. Every node carries an optional `loc: Loc | None`.

### Module

```python
@dataclass
class FrontendModule:
    api_version: int                          # = 1 for v1
    qname: str                                # canonical dotted module name
    source_language: str                      # "pascal" | "mylang" | ...
    source_lines: tuple[str, ...]             # may be empty if no loc anywhere

    imports: tuple[ImportDecl, ...]
    type_aliases: tuple[TypeAlias, ...]
    constants: tuple[Constant, ...]
    enums: tuple[Enum, ...]
    records: tuple[Record, ...]
    functions: tuple[Function, ...]
    top_level_stmts: tuple[Stmt, ...]

    directives: FrontendDirectives
```

Tuples (not lists) prevent accidental mutation and make structural
equality cheap. Dataclass instances are not hashable by default; if
hashability becomes useful (e.g. memoizing lowering results), the
relevant nodes can be marked `frozen=True` later.
The order of declaration kinds matters: lowering processes them in a
deterministic order.

### Imports

```python
@dataclass
class Import:                       # kind = "Import"
    module: str                     # absolute, dotted
    alias: str | None = None        # `import X as Y`

@dataclass
class FromImport:                   # kind = "FromImport"
    module: str
    names: tuple[ImportName, ...]

@dataclass
class ImportName:
    original: str
    local: str                      # equals original if no `as`
```

`ImportDecl = Import | FromImport`. Relative imports, star imports,
and package `__init__` semantics are out of scope for v1.

### Directives

```python
@dataclass
class FrontendDirectives:
    cpp_includes: tuple[CppInclude, ...] = ()
    link_libs: tuple[LinkLib, ...] = ()
    third_party_deps: tuple[ThirdPartyDep, ...] = ()
    native_module: bool = False
    cpp_namespace: str | None = None

@dataclass
class CppInclude:
    header: str
    platform: str | None = None    # e.g. "linux", "darwin"; None = all

@dataclass
class LinkLib:
    name: str                       # passed to linker as -lname
    platform: str | None = None     # None = all platforms

@dataclass
class ThirdPartyDep:
    name: str                       # registered third-party name (e.g. "pcre2")
    platform: str | None = None     # None = all platforms
```

These mirror the on-disk shape of `ModuleDirectives` (see
`tpyc/parse/nodes.py:1288`). The managed-vs-raw distinction is encoded
by *which list* a dep is in: `link_libs` are raw `-lname` deps;
`third_party_deps` are TPy-managed (e.g. PCRE2). Plugins that need a
managed dep emit it in `third_party_deps`; the parser flow's
`link("foo", managed=True)` is not reachable from the IR. Version
constraints on third-party deps are not modeled in v1 (see future
requirements).

### Type IR

Types are *symbolic*. The IR carries no `TpyType` instances. Lowering
converts symbolic types to parser `TypeRefNode`s; sema resolves those to
`TpyType`.

```python
@dataclass
class NamedType:                    # kind = "NamedType"
    name: str                       # "Int32", "Foo", "list", "BoundedList"
    args: tuple[TypeArg, ...] = ()  # generic args

@dataclass
class OptionalType: inner: TypeExpr                     # kind = "OptionalType"
@dataclass
class PointerType:  inner: TypeExpr                     # kind = "PointerType"
@dataclass
class ReadonlyType: inner: TypeExpr                     # kind = "ReadonlyType"
@dataclass
class OwnType:      inner: TypeExpr                     # kind = "OwnType"
@dataclass
class UnionType:    members: tuple[TypeExpr, ...]       # kind = "UnionType"
@dataclass
class CallableType:                                     # kind = "CallableType"
    params: tuple[TypeExpr, ...]
    return_type: TypeExpr
@dataclass
class LiteralType:                                      # kind = "LiteralType"
    values: tuple[LiteralValue, ...]                    # int | str | bool | None
```

`TypeExpr` is the union of the above.

Wrapper types are *nodes*, not flags. This preserves nesting:
`Ptr[readonly[Foo]]` and `readonly[Ptr[Foo]]` are distinct;
`Ptr[Foo] | None` and `Ptr[Foo | None]` are distinct.

Type arguments are not always types -- `Array[T, N]` and `FixStr[N]`
take integer args:

```python
@dataclass
class TypeTypeArg:  value: TypeExpr             # kind = "TypeTypeArg"
@dataclass
class IntTypeArg:   value: int                  # kind = "IntTypeArg"
```

`TypeArg = TypeTypeArg | IntTypeArg`. Current `TpyTypeRef.args` accepts
only `ResolverInputNode | int` (`tpyc/parse/nodes.py:98`), so
string-valued and constant-reference type arguments cannot lower
without resolver changes; both are deferred to future requirements.

### Generic declarations

```python
class TypeParamKind(Enum):
    TYPE = "TYPE"
    INT = "INT"

@dataclass
class TypeParam:
    name: str                              # "T", "N"
    kind: TypeParamKind                    # TYPE | INT
    bound: TypeExpr | None = None          # constraint (T: Number)
    default: TypeArg | None = None         # default value if not specified
```

Used on `Record`, `Function`, `TypeAlias` declarations. v1 does not
support variance; future protocol intersection support is reserved as
an `IntersectionType` node in `TypeExpr` (not a `bounds: list[...]` on
`TypeParam`).

### Expressions

```python
# Literals
IntLit(value: int)             # kind = "IntLit"
FloatLit(value: float)         # kind = "FloatLit"
StrLit(value: str)             # kind = "StrLit"
BoolLit(value: bool)           # kind = "BoolLit"
CharLit(value: str)            # single-char string; kind = "CharLit"
BytesLit(value: bytes)         # kind = "BytesLit"
NoneLit()                      # kind = "NoneLit"

# Composite literals
TupleLit(items: tuple[Expr, ...])
ListLit(items: tuple[Expr, ...])
DictLit(items: tuple[tuple[Expr, Expr], ...])
SetLit(items: tuple[Expr, ...])

# Comprehensions
ListComp(elt: Expr, generators: tuple[CompGenerator, ...])
DictComp(key: Expr, value: Expr, generators: tuple[CompGenerator, ...])
SetComp(elt: Expr, generators: tuple[CompGenerator, ...])
GeneratorExpr(elt: Expr, generators: tuple[CompGenerator, ...])

# Names + access
Name(ident: str)
Attr(target: Expr, ident: str)
Subscript(target: Expr, index: Expr)
Slice(start: Expr | None, stop: Expr | None, step: Expr | None)

# Operators
BinOp(op: BinOpKind, lhs: Expr, rhs: Expr)
UnaryOp(op: UnaryOpKind, operand: Expr)
Compare(lhs: Expr, ops: tuple[CmpOpKind, ...], comparators: tuple[Expr, ...])
                               # supports Python-style chains: a < b < c

# Calls
Call(callee: Expr,
     type_args: tuple[TypeArg, ...] = (),
     args: tuple[Expr, ...] = (),
     kwargs: tuple[tuple[str, Expr], ...] = (),
     star_args: Expr | None = None,
     double_star: Expr | None = None)

# Other
Conditional(cond: Expr, then: Expr, else_: Expr)    # ternary
Lambda(params: tuple[Param, ...], body: Expr)
FormatString(parts: tuple[FormatPart, ...])         # f-strings
```

`CmpOpKind` covers `==`, `!=`, `<`, `<=`, `>`, `>=`, `is`, `is_not`,
`in`, `not_in`. Plain method-call lowering (e.g. for natural-language
queries in the larger plugin) goes through `Call(Attr(...))`; the IR
does not introduce a separate `MethodCall` node.

**Low-level operations as TPy intrinsics, not IR nodes.** The IR has
no dedicated `AddressOf` or `Deref` node. Plugins that need
address-of (e.g. lowering Pascal `var` parameters or the larger
plugin's `byref`/`out` modes) emit a `Call` to TPy's existing
`take_ptr` builtin: `Call(Name("take_ptr"), args=(x,))`, where `x` is
an lvalue (`Name`/`Attr`/`Subscript`). Plugins that need to read a
value-typed pointee emit `Call(Name("deref"), args=(p,))`. Both are
TPy core intrinsics with sema-time validation (lvalue requirement on
`take_ptr`, null-check on `deref`); pointer arithmetic and raw memory
operations live under `tpy.unsafe.*`.

**Import contract.** `take_ptr` and `deref` are exported from `tpy`,
not implicit builtins. A plugin emitting calls to them must also
emit a corresponding import in the same module:

```python
FromImport(module="tpy",
           names=(ImportName("take_ptr", "take_ptr"),
                  ImportName("deref", "deref")))
```

Likewise, `tpy.unsafe.*` calls require a `FromImport(module="tpy.unsafe",
names=(...))`. The plugin emits each intrinsic-name as a bare `Name(...)`
in the call site; the import makes it resolvable at sema. Lowering
does not special-resolve these names -- they go through TPy's normal
import-resolution machinery. Keeping these as ordinary intrinsic
calls (rather than dedicated IR nodes) keeps the IR semantic-level
and the surface stable.

```python
   else_: tuple[Stmt, ...])
```

### Declarations

```python
@dataclass
class Param:
    name: str
    type: TypeExpr
    default: Expr | None = None
```

v1 has no parameter-mode field. Plugins that need by-reference or
out-parameter semantics lower them themselves: emit `Param(type=Ptr[T])`
and rewrite caller sites to pass pointers explicitly. First-class
parameter modes are deferred to a future TPy primitive.

```python
@dataclass
class Function:

class Record:
    name: str
    type_params: tuple[TypeParam, ...]
    base: NamedType | None                     # single inheritance
    fields: tuple[Field, ...]
    methods: tuple[Function, ...]
    nested_records: tuple[Record, ...]         # nested typedefs
    nested_enums: tuple[Enum, ...]
    nested_constants: tuple[Constant, ...]
    nested_aliases: tuple[TypeAlias, ...]

@dataclass
class EnumValue:
    name: str
    value: Expr | None
    decorators: tuple[Decorator, ...] = ()

@dataclass
class Enum:
    name: str
    base_type: NamedType | None                # explicit backing (Int / Str)
    values: tuple[EnumValue, ...]
    decorators: tuple[Decorator, ...]

@dataclass
class TypeAlias:
    name: str
    type_params: tuple[TypeParam, ...]
    target: TypeExpr

@dataclass
class Constant:
    """Compile-time constant declaration. Lowers to TPy's Final / class
    constant machinery. Distinct from a top-level Assign because
    source-language constant declarations carry distinct semantics
    (visibility, immutability, constexpr expectations) and lower

    name: str
```

v1 supported constant value types match TPy's `FinalType` set
(`tpyc/typesys.py:1686`): numeric (`Int*`, `UInt*`, `int`, `float`,
`Float32`), `Char`, `StrView`, and `tuple` of these. Top-level
constants must have a value (no forward declarations). Class
constants on generic classes are not supported. Plugins that need
record-, container-, or map-typed compile-time constants must emit
module-level globals with runtime initialization in v1; richer
constant support is future work.

### Decorators

The IR carries decorators as a single shape:

```python
@dataclass
class Decorator:
    name: str                              # dotted: "tpy.native", "mylang.tag"
    args: tuple[Expr, ...] = ()
    kwargs: tuple[tuple[str, Expr], ...] = ()
```

Decorators are allowed on `Function`, `Record`, `Enum`, `EnumValue`,
`Field`, and `Constant`. Lowering decides what each decorator does
based on the **decorator registry** (next section).

### Decorator registry and plugin manifest

The compiler holds a registry mapping decorator names to a route:

```python
class DecoratorRoute(Enum):
    BUILTIN_LOWERING = "BUILTIN_LOWERING"   # TPy-builtin decorator (lowering handles)
    MACRO = "MACRO"                          # populates pending_macros

@dataclass
class DecoratorEntry:
    name: str                               # dotted, e.g. "tpy.native", "mylang.dataclass"
    route: DecoratorRoute
    target_kinds: tuple[str, ...]           # "function", "record", "field", "enum",
                                            # "enum_value", "constant"
```

The registry is **compiler-owned**: TPy core preloads the registry with
its built-in decorators (`tpy.native` -> BUILTIN_LOWERING,
`tpy.readonly` -> BUILTIN_LOWERING, `tpy.error_return` ->
BUILTIN_LOWERING, `tpy.dataclass` -> MACRO, etc.). Each plugin
contributes additional entries via its `decorator_manifest` ClassVar at
load time. Conflicts (two sources registering the same name with
different routes) are a hard load-time error.

Behavior at lowering:
- **Known decorator** -- routed per the registry entry.
- **Unknown decorator** -- lowering diagnostic (`PLUGIN_IR_INVALID`).
  No silent passthrough; this catches typos and prevents accidental
  coupling.

v1 supports only two routes (`BUILTIN_LOWERING` and `MACRO`) because
those are the only routes for which TPy's existing AST has destinations:
`TpyFunction` consumes builtin decorators into typed flags
(`tpyc/parse/nodes.py:1071`); `TpyRecord` carries `pending_macros`
(`tpyc/parse/nodes.py:1230`). Routes that pass arbitrary metadata
through to sema or runtime (e.g. for plugin-runtime decorators that
are not macros and not TPy builtins) need new AST storage; they are
deferred to future requirements.

The two routes also have different valid `target_kinds`:

- **`BUILTIN_LOWERING`** can target `function`, `record`, `field`,
  `enum`, `enum_value`, or `constant` -- TPy core picks where each
  recognized builtin decorator's effect lands.
- **`MACRO`** is **record-level only** in v1. TPy class macros run on
  records via `pending_macros`; there is no equivalent slot on
  `TpyFunction`, `Field`, `Enum`, `EnumValue`, or `Constant`. A
  `DecoratorEntry` with `route=MACRO` and any non-record target kind
  is a manifest-load error.

For v1, plugin-runtime decorators must therefore be either:
- TPy class macros (`@class_macro`, registered as `MACRO`,
  decorating `Record`s; the macro can synthesize methods, fields,
  and nested decls inside the record).
- TPy call-site or builder-trace macros (`@call_macro`,
  `@builder_macro`); these don't appear in `decorator_manifest`
  because they're not decorators on declarations.
- TPy built-in decorators added to TPy core specifically for the
  plugin's needs (e.g. a plugin-runtime decorator that maps to a
  `BUILTIN_LOWERING` flag on `TpyFunction` or `TpyRecord`; this is a
  TPy-core change, not a plugin-side capability).

Decorators that are pure documentation / external-tool metadata
(IDE hints, lints, etc.) can be encoded as comments or as plugin-
specific source-file directives parsed by the plugin itself, not as
TPy decorators in the IR.

### Source locations

```python
@dataclass(frozen=True)
class Loc:
    file: Path
    line: int                # 1-based
    col: int                 # 1-based
    end_line: int            # inclusive
    end_col: int             # inclusive
    source_language: str     # "pascal" | "mylang" | ...
```

Every node accepts an optional `loc`. The plugin **should** populate
`loc` everywhere it has it. If any node carries a populated `loc`,
`FrontendModule.source_lines` must be non-empty (lowering checks).

## Lowering pass

Lowering lives in `tpyc/frontend_ir/lower.py` and is invoked by the
compiler after the plugin returns a `FrontendOutput`. It:

1. **Validates** the IR structurally:
   - `api_version` matches the compiler's supported set.
   - Sum-type variants are well-formed (every node in a union has a
     valid discriminator).
   - Imports are absolute; no relative / star / package-init.
   - Decorator names resolve via the decorator registry.
   - `loc` populated implies `source_lines` non-empty.
   - Type wrapper nodes are well-formed (`OptionalType` not wrapping
     `OptionalType` directly, etc.).
2. **Normalizes** imports: produces both `TpyImport` statements in
   `top_level_stmts` (for codegen's `__tpy_init()` emission) and
   `user_module_imports` / `bare_module_imports` / `module_aliases` /
   `imports` dict entries (for sema discovery).
3. **Synthesizes parser internals**: attaches a no-op resolver to the
   `TpyModule`, populates `directives`, sets `qname` on records and
   functions, etc.
4. **Translates symbolic types** (`TypeExpr`) to parser `TypeRefNode`s.
   Lowering does *not* resolve these to `TpyType` -- that is sema's
   job.
5. **Routes decorators** per registry: `BUILTIN_LOWERING` decorators
   become `TpyFunction` typed flags / linkage; `MACRO` decorators
   populate `pending_macros` on the lowered `TpyRecord`. Unknown
   decorator names are reported as `PLUGIN_IR_INVALID`.
6. **Preserves source locations**: every TPy AST node lowered from an
   IR node carries the original `loc`. Diagnostics from sema and
   codegen point at the original (non-Python) source.
7. **Emits diagnostics** for malformed IR (see Diagnostics below).

Lowering does **not**:
- Resolve names. Sema does.
- Resolve types to `TpyType`. Sema does.
- Run macros. Sema does (after lowering, via the existing macro pass).
- Perform sema-like checks (type compatibility, overload resolution,
  etc.).

The lowering / sema boundary is a hard contract:

> Every schema-valid IR module must either lower successfully or
> produce a documented compiler diagnostic. Any uncaught exception or
> impossible-state error after validation is a compiler bug.

## CLI

```
tpyc --dsl-plugin <path-or-module> [--dsl-plugin ...]
     --dsl-opt <name>.<key>=<value> [--dsl-opt ...]
     <input>
```

Plugins are loaded before module discovery starts. The arguments for
both flags are repeatable. `--dsl-plugin` accepts a path to a `.py`
file or an importable dotted module name. `--dsl-opt` routes to a
plugin by `<name>` prefix; unrouted options are an error.

## Loading and registration

### In-process plugins (canonical path)

1. If the spec is a path to an existing `.py` file -- load via
   `importlib.util.spec_from_file_location`.
2. Else -- treat as an importable module name and call
   `importlib.import_module`.
3. Fetch `PLUGIN` attribute. Validate it is a `FrontendPlugin`
   subclass and that its `api_version` is supported.
4. Instantiate with the routed options dict.
5. Merge `decorator_manifest` into the compiler's decorator registry.
   Conflict (same decorator name, different route) is a load-time error.
6. Register with the compiler's `FrontendRegistry`, keyed by
   extensions. Extension collision is a load-time error.

### Plugin trust boundary

Frontend plugins are **compile-time trusted code**. Unlike macro
modules (`tpyc/macro_loader.py` restricts builtins/imports because
macro code may eventually run in a self-hosted VM), plugins run with
unrestricted Python -- full builtins, full `import`, free to launch
subprocesses, read files. The trust is no different from any other
tool the user invokes.

### External compilers via subprocess

The canonical pattern for non-Python compilers is a thin Python plugin
that owns a subprocess:

```python
class MyFrontend(FrontendPlugin):
    api_version = 1
    name = "mylang"
    extensions = (".myl",)
    decorator_manifest = (
        DecoratorEntry("mylang.dataclass", DecoratorRoute.MACRO,
                       target_kinds=("record",)),
        # ...
    )

    def parse(self, ctx, module_name, file_path):
        result = subprocess.run(
            [self.options["compiler_path"], "--emit-ir-json", str(file_path)],
            capture_output=True, check=True)
        module = _decode_frontend_module(json.loads(result.stdout))
        return FrontendOutput(module=module)
```

The plugin author owns the IPC format. A future `SubprocessPlugin`
helper class can ship a TPy-versioned JSON schema -- since the IR is
plain dataclasses, this is straightforward when needed.

## WorkspaceContext

```python
@dataclass(frozen=True)
class WorkspaceContext:
    api_version: int                  # matches FrontendPlugin.api_version
    entry_point: Path                 # the tpyc input file
    search_dirs: tuple[Path, ...]     # base_dir + lib search paths
    options: dict[str, str]           # --dsl-opt routed to this plugin
    no_stdlib: bool                   # mirror of --no-stdlib

    def read_file(self, path: Path) -> str: ...
    def find_files(self, ext: str, root: Path | None = None) -> list[Path]: ...
    def resolve_module(self, dotted_name: str) -> Path | None: ...
```

- **Per-file plugins (Pascal-shape):** ignore `ctx` except for
  `options` and `no_stdlib`.
- **Cross-file-aware plugins:** use `find_files` / `read_file` to look
  at sibling sources during translation -- e.g. to materialize
  explicit imports for languages with implicit cross-file visibility.
- `resolve_module` exposes the same lookup TPy uses internally,
  including plugin-registered extensions, so a plugin can ask "what
  file is module X?" without reimplementing search-path semantics.

Future extensions that require compiler-owned mutable state behind
context methods (compile-time data registry, plugin-registered
module-path overrides) are listed below; they may force `frozen=True`
to be relaxed or accompanied by a separate mutable companion.

## Compiler integration

### Module resolver as a provider chain

`ModuleResolver` (`tpyc/modules/resolver.py`) currently hardcodes `.py`
in `_resolve_in()` and `get_module_name()`. v1 refactors it into a
chain of providers:

```
ModuleResolver
  resolvers: tuple[ModuleResolverProvider, ...]
    PythonResolverProvider  (default)
    PluginResolverProvider  (one per registered plugin extension set)
```

Each provider implements `try_resolve(base_dir, dotted_name) ->
ResolvedModule | None` and `try_strip_extension(filename) -> str |
None`. Resolution and module-name extraction iterate providers in
registration order; first match wins.

Two consequences:

- **Frontend-aware module naming.** `get_module_name()` consults all
  providers. `tpyc myproject.dpr`, with the plugin registering
  `.dpr`, yields module name `myproject` (not `myproject.dpr`, which
  would be parsed as a package path downstream).
- **Future-compatible.** Plugin-registered module-path overrides
  (future requirement #16) become "add another provider," not a
  retrofit.

### Discovery dispatch

`Compiler._discover_modules` (`tpyc/compiler.py:1019`) currently parses
every discovered file with `Parser.parse()`. After resolution, it
inspects the file's extension:

- If `.py` -- existing path (Parser, optionally macro module).
- Else if a plugin claims the extension -- call `plugin.parse(ctx,
  module_name, file_path)`, run **lowering** over the result, register
  the resulting `TpyModule` into `self.modules` like any other module.
  Subsequent discovery iterates the module's `user_module_imports` as
  usual.

Implicit stdlib (`tpy`, `typing`, `builtins`) is unaffected -- those
modules are always `.py`, always parsed by `Parser`.

### Project-file-driven languages

Some languages declare their source set externally to the source files
themselves -- a CMake-style project file, a `.dpr` Pascal project, a
manifest. These compose with TPy's existing import-driven discovery:

1. The plugin claims the project-file extension (e.g. `.dpr`).
2. `tpyc myproject.dpr` makes the project file the entry point.
3. The plugin's `parse()` for that file reads the project (using
   `ctx.read_file`), extracts the source list, and returns a synthetic
   `FrontendModule` whose `imports` list contains one bare `Import`
   per project source file. Lowering synthesizes both the
   `TpyImport` statements (required for codegen `__tpy_init()`) and
   the dependency entries (required for sema).
4. TPy's normal discovery loop resolves each import and calls
   `plugin.parse()` on each source file.

Constraint for v1: source files referenced from the project must be
reachable via search dirs (`-L`). Arbitrary paths need plugin-registered
module-path overrides (future requirement #16).

## Constraint contracts

### Imports (v1)

Plugin-emitted modules may use:
- Absolute `Import(module, alias=None)`.
- Absolute `FromImport(module, names=[(orig, local), ...])`.

Plugin-emitted modules may **not** use:
- Relative imports.
- Star imports (`from X import *`).
- Package `__init__` semantics. Plugin modules are flat in v1.

### `--no-stdlib`

`WorkspaceContext.no_stdlib` mirrors the user's `--no-stdlib` flag.
With it set, plugins must not emit references to stdlib symbols
(`print`, `len`, types from `tpy`, etc.). A plugin's runtime library
on the search path is still resolvable; "stdlib" here means TPy's
implicit stdlib (`tpy`, `typing`, `builtins`).

### Macros

Plugin-emitted modules **may** include **class-macro decorators**
(e.g. `@dataclass`) on `Record`s; those are routed through the
decorator registry as `MACRO`. The class macro runs at sema time and
generates methods, fields, and nested decls inside the decorated
record.

Call-site macros (`@call_macro`) and builder-trace macros
(`@builder_macro`) are different mechanisms: they are decorators
applied to *function definitions inside macro modules* (`# tpy:
macro_module` Python files), not decorators a plugin would emit on
its own declarations. Plugin-emitted code **may freely call**
functions that happen to be call-site or builder-trace macros (the
sema-time expansion happens at the call site automatically), but the
plugin itself does not declare such macros and does not list their
names in `decorator_manifest`.

Plugin-emitted modules **may not** themselves be macro modules. The
plugin's `parse()` does not produce a `# tpy: macro_module`
directive; macro modules are loaded and executed via a different
code path (`MacroRegistry`) that requires Python source.

### Options

`--dsl-opt name.key=value`. The `name` segment selects the plugin;
only options whose `name` matches a registered plugin are routed.
Unrouted options are a CLI error. Plugin-side schema validation
(typed options) is deferred to a future API.

## Diagnostics

Plugins surface diagnostics via TPy's existing `Diagnostic` type
(`tpyc/diagnostics.py:22-59`), wrapped in a thin envelope that carries
plugin-frontend-specific category and metadata:

```python
class FrontendDiagnosticCategory(Enum):
    PLUGIN_REPORTED = "PLUGIN_REPORTED"
    PLUGIN_IR_INVALID = "PLUGIN_IR_INVALID"
    LOWERING_INTERNAL = "LOWERING_INTERNAL"

@dataclass
class FrontendDiagnostic:
    diagnostic: Diagnostic                 # original Diagnostic, preserved
    category: FrontendDiagnosticCategory
    plugin_name: str | None = None
    source_language: str | None = None
    plugin_diagnostic_code: str | None = None
```

The wrapper is necessary because TPy's `DiagnosticLevel` is currently
only `ERROR | WARNING` (`tpyc/diagnostics.py:22`); the envelope keeps
category metadata without forcing a `DiagnosticLevel` extension. The
underlying `Diagnostic` is preserved unmodified for tests and
tooling.

Categories carry distinct semantics:

- **`PLUGIN_REPORTED`** -- diagnostics from the plugin's `parse()`
  return value (`FrontendOutput.diagnostics`). Lowering wraps each
  with the plugin's name and source-language tag. Severity from the
  plugin is honored: `ERROR` aborts the affected module.
- **`PLUGIN_IR_INVALID`** -- the IR violates a structural contract
  detected during lowering (decorator name not in registry, bad type
  wrapper, unknown sum-type discriminator, etc.). The wrapped
  diagnostic has severity `ERROR`; aborts the affected module. Blames
  the plugin with a clear, local error.
- **`LOWERING_INTERNAL`** -- the lowering pass hit an
  impossible-state condition after structural validation passed.
  This is a TPy compiler bug, not a plugin bug. The wrapped
  diagnostic has severity `ERROR`; aborts compilation; the renderer
  prefixes the message with an "internal compiler error" banner and
  instructs the user to file an issue.

The lowering / sema boundary contract:

> Every schema-valid IR module must either lower successfully or
> produce a documented compiler diagnostic. Any uncaught exception or
> impossible-state error after validation is a compiler bug
> (`LOWERING_INTERNAL`), not a plugin bug.

For fatal errors a plugin cannot recover from, raise
`FrontendPluginError` carrying a single `Diagnostic`. The compiler
catches it and renders it as `PLUGIN_REPORTED` with severity `ERROR`.

Plugins must not write to stderr or stdout directly. All user-facing
output flows through `Diagnostic`.

## API stability

The plugin API is **provisional through v1**:

- `FrontendPlugin`, `FrontendRegistry`, `FrontendOutput`,
  `WorkspaceContext`, `FrontendPluginError`, the `PLUGIN` module
  attribute, the decorator manifest mechanism, the IR types under
  `tpyc/frontend_ir/`, the lowering pass, `api_version`, and the CLI
  flags are committed for v1.
- `api_version` versions the **entire frontend API contract**, not
  only the IR shape. A bump signals breaking changes to any of: IR
  schema, lowering semantics, decorator routes, the diagnostics
  envelope, or `WorkspaceContext` method semantics. Plugins
  targeting older `api_version` continue to work as long as the
  compiler advertises support.
- `TpyModule` and the parser AST node classes remain **internal**.
  Plugins do not depend on them.
- Future-requirements items below are explicitly *not* part of the v1
  contract.

## Anticipated future requirements

These capabilities are not implemented in v1, but the v1 design must
not foreclose them.

1. **Workspace-wide translation.** Covered: `WorkspaceContext.find_files`
   and `read_file`.
2. **Compile-time data registry.** A typed key/value store the plugin
   populates and sema can read. Adding it requires more than a context
   field: each module gets a fresh `SemanticAnalyzer`
   (`tpyc/compiler.py:1459-1462`), so shared data must be threaded
   into every analyzer's context. Not foreclosed; future work.
3. **Compile-time auxiliary file loading.** Already covered by
   `ctx.read_file`; future helper might add caching.
4. **Source-location preservation.** v1 covers via `loc` on nodes.
   Open question: how diagnostics render carets when the original
   source is non-Python.
5. **Cross-file symbol-resolution helpers.** Workspace-wide symbol
   table. Today plugins do this themselves via `find_files`.
6. **Decorator registry extension API.** Plugins register entries via
   `decorator_manifest` (covered in v1).
7. **Per-language runtime libraries.** v1 imposes no coupling.
8. **External compiler integration / caching.** Per-plugin in v1.
9. **Pattern- or template-based overload dispatch.** Plugin lowers in
   v1; no TPy-side mechanism needed.
10. **Per-iteration / per-turn runtime state.** Plugin's runtime
    library implements semantics; TPy uninvolved.
11. **Scope-based virtual dispatch.** Plugin lowers to explicit
    dispatch tables.
12. **Custom conversion / coercion semantics.** Plugin translates to
    explicit constructor / function calls.
13. **Mutable value-copy types.** Covered via existing TPy types
    (`tplib.fix_str.FixStr`, etc.).
14. **First-class by-reference / out parameter modes.** v1 has no
    `Param.mode`; plugins lower by-ref/out to `Ptr[T]` and rewrite
    callers themselves. A future TPy parameter-mode primitive (with
    proper sema/codegen support for write-back semantics) would let
    the IR re-add a `Param.mode` field.
15. **Standardized cross-language IPC protocol.** Now straightforward:
    publish the IR JSON schema. The IR is plain dataclasses, so
    `dataclasses.asdict` round-trips with kind discriminators. A
    `SubprocessPlugin` helper packaging this is future work.
16. **Plugin-registered module-path overrides.** For project-file-
    driven languages whose source files live outside search dirs.
    Concrete shape: `ctx.register_module_path(canonical_name, path)`,
    consulted by `ModuleResolver` before falling back to its
    search-dir-based lookup. Conflicts with `frozen=True` on
    `WorkspaceContext`; either drop frozen or model registration as
    method calls into compiler-owned mutable state behind the context.
17. **Variance and protocol intersections in generic decls.** Reserved
    via `IntersectionType` in `TypeExpr`; not exposed on `TypeParam`.
18. **Plugin-side option schema validation.** Today options are an
    untyped `dict[str, str]`; future API can add typed schema.
19. **Decorator routes beyond `BUILTIN_LOWERING | MACRO`.** v1
    restricts the registry to these two routes because they are the
    only ones with destinations on the current TPy AST. Adding
    `RUNTIME_METADATA` (passes a decorator's args through to a
    runtime-readable metadata slot) and `SEMANTIC_PASSTHROUGH`
    (preserves a decorator AST node for sema to resolve against the
    plugin's runtime library) requires new AST storage on
    `TpyFunction` / `TpyRecord` / `FieldInfo`. Future work.
20. **`StrTypeArg` and `ConstRefArg` type arguments.** Current
    `TpyTypeRef.args` accepts only `ResolverInputNode | int`. Future
    resolver work would let the IR carry string-valued and
    constant-reference type args.
21. **Richer compile-time constants.** v1 restricts `Constant` to
    `FinalType`-compatible values (numerics, `Char`, `StrView`,
    tuples). Records, containers, and maps as compile-time constants
    require sema support beyond `FinalType`.
22. **Version constraints on third-party deps.** The IR's
    `ThirdPartyDep` carries name + platform but not version
    constraints; TPy's third-party build plan does not currently
    consume version information. Future work tied to the build
    pipeline.

## Open questions

- **Async / batched `parse()`.** Some external compilers run faster
  fed many files in one call. v1 says no -- one synchronous call per
  file. Revisit if benchmarks show it dominates.
- **"This file exists but should not be compiled."** No signal in
  v1; plugin omits the unit from the synthetic-entry's imports.
- **Plugin lifecycle hooks.** No `setup` / `teardown` in v1. A plugin
  needing a daemon launches it in `__init__` and relies on process
  exit for cleanup.
- **Parallelism / reentrancy.** v1: plugin authors should not assume
  concurrent calls (TPy currently parses serially), and should not
  hold mutable state on the plugin instance beyond `options`. If
  parallel `parse()` becomes a goal, this becomes a hard contract.
- **Plugin-state plumbing for compile-time data registry.** Future
  requirement #2 needs shared data threaded through per-module
  analyzers. Where this lives is unresolved.
- **Multi-claim collision policy.** v1: hard error if two plugins
  claim the same extension. No precedence rules.
- **Plugin reload semantics.** REPL or watch-mode invocations may
  load the same plugin repeatedly. v1 does not specify; caching
  `PLUGIN` instances by `(spec, options)` is a reasonable default.
- **IR diagnostic carets for non-Python source.** TPy's diagnostic
  formatter renders source lines from `module.source_lines`. For
  plugin-emitted modules, those are the original (non-Python) source
  lines. How to render correctly when token columns differ from
  rendered columns is open.
