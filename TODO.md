## Open feature gaps
- Generic generators with multiple yield points (struct-based codegen path) are not yet supported -- the out-of-line `__next__()` in .cpp won't link for template structs. Currently guarded with a sema error. Fix: emit struct + `__next__()` body into the header when the function has type params.
- Property narrowing not supported: `if f.val is not None: f.val + 1` does not narrow because property access is a method call (could return different values). Same as function calls. Workaround: `v = f.val; if v is not None: v + 1`. Could support narrowing for simple field-returning getters in the future (requires getter body analysis).
- Tuple iteration + Iterable conformance bundle. `for x in some_tuple:` fails sema with "Cannot iterate over type tuple[...]", and passing a tuple (literal or bound variable) to an `Iterable[T]` param fails conformance in `sema/protocols.py`. Real CPython compat gap -- `math.prod((1.0, 2.0, 3.0))` works in CPython, errors in TPy. Coupled fix needed: (1) sema `type_conforms_to_protocol` case for TupleType when all element types widen to T; (2) codegen emits a std::array-style view from `std::tuple<T, T, ...>` for iteration (std::tuple has no begin/end); (3) for-loop codegen dispatches to that view for tuple iterables. Doing just (1) would make sema accept code that then fails C++ template instantiation (the class of bug we've been cleaning up). Workaround: bind to `list[T]` first or pass a list literal. Surfaced while making math.prod/fsum/sumprod/dist take Iterable[float]; those are now done but skip tuple inputs.
- No `AnyInt` protocol covering BigInt + all `AnyFixedInt`. `AnyFixedInt` bounds a generic to fixed-width ints only (excludes BigInt). Writing a generic stdlib function like `gcd[T: AnyInt](a: T, b: T) -> T` that accepts BigInt *and* any fixed-width int has no natural bound. Surfaces when trying to write pure-TPy generics over int types (`math.gcd`, `math.isqrt`, anywhere int-algebraic). Workaround: declare as `int`-only (forces BigInt; small-int callers pay widening cost). Fix: add an `AnyInt` protocol in `lib/tpy/tpy/_core/_types.py` that unions BigInt + AnyFixedInt, with the arithmetic/comparison surface needed for common algorithms.
- Generic type params over int types can't use basic arithmetic without a bound. Pure-TPy `def gcd[T](a: T, b: T) -> T` rejects `a = -a` ("Cannot reassign parameter"; workaround: copy to local), `x = -x` on T ("Invalid operand type for unary '-'"), and `abs(x)` on T ("No matching overload for abs(T)"). Each is because T has no known signed-int bound. Resolving via the `AnyInt` protocol above (with `__neg__` / `__abs__` surface) would unblock pure-TPy integer generics. The ban on reassigning generic-typed parameters is probably separate and may warrant its own review -- for some patterns it's a real ergonomic tax.
- No `Numeric` (or `AnyNumber`) protocol covering `AnyInt + float + Float32`. Blocks writing a generic `math.prod[T: Numeric](Iterable[T], *, start: T = 1) -> T` and similar generic numerics. `start: T = 1` works at sema (int literal coerces to T via normal default-value coercion; verified), so the only missing piece is the bound itself plus its declared arithmetic surface (`__mul__`, `__add__` at minimum). Depends on `AnyInt` above. Once both land, `prod` can be a single generic instead of N overloads, avoiding the empty-list W2 ambiguity entirely. Broader payoff: unblocks user-written generic numeric code (vector math, statistics fragments, aggregation primitives) that currently has no bound to use.
- Atomic shared-ownership smart pointer in TPy: `Arc[T]` (atomic refcounts). Non-atomic `Rc[T]` and its `Weak[T]` companion ship in `tplib` for single-threaded use; the multi-threaded analog is a v3+ item (multi-threaded executor, multi-awaiter Future). Open design: refcount-update memory ordering (acquire/release vs seq-cst on each refcount op), `Weak[T]`'s atomic upgrade compare-exchange shape, and interaction with cross-thread async primitives + a `Sync` bound on T.
- `thread_local` storage in TPy. Needed to express `current_executor` (and any future per-thread global) directly in TPy rather than as a C++ thread-local `void*` pointer with TPy-side `_get_current_executor` / `_set_current_executor` / `_clear_current_executor` bridges (see `lib/tpy/asyncio/_executor.py`). Low priority since the v1 executor is single-threaded; matters when multi-threaded async (v3+) lands.
- Generic class specializations for value / reference / void / move-only / non-default-constructible `T`. TPy can declare `class Poll[T]` but can't express the four specializations the C++ runtime has today (`Poll<T>` value, `Poll<void>`, `Poll<T&>`, plus move-only and non-default-constructible T variants via `std::optional` storage). Blocks porting `tpy::Poll<T>` to TPy (the last primitive in `runtime/cpp/include/tpy/async.hpp` after the v1.1 port). Open design: do generic classes get explicit specialization syntax (e.g. `class Poll[T = None]: ...` overload), or does TPy emit a uniform representation that handles all cases (some kind of internal tagged storage)? Adjacent to the BUGS.md entry on `def f[T] -> T` for `T = None` (same family: TPy generics don't currently know how to handle T=void uniformly). Until this lands, `Poll[T]` stays as four hand-written C++ specializations and TPy code uses the existing `@native("tpy::Poll")` binding.
- `@cpp_template` literal-brace escape syntax. The substitution engine treats `{...}` as a placeholder field name, so C++ aggregate-init / lambda / scope braces in the template string can't be expressed (e.g. `@cpp_template("::tpy::Handle{static_cast<void*>(&{0})}")` fails with `Internal error: unexpected '{' in field name`). Workaround today: wrap the brace-using expression in a templated C++ helper and bind to that helper via `@cpp_template`. Fix: add `{{` / `}}` Python-f-string-style escape syntax. Pairs with the BUGS.md entry on the same code path (UX: produce a clear diagnostic instead of an internal error when literal braces appear). Surfaced during async v1.1 Phase 2.2.
- `Final[list[T]]` / `Final[Array[T, N]]` for compile-time constant tables. Today `Final[T]` only allows primitives (`int`, `float`, `bool`, `str`/`StrView`, `Char`, `IntN`) and `tuple` (see `docs/LANGUAGE_FEATURES.md:5071`); array-shaped round-constant tables (SHA-2 H0/K, AES S-boxes, CRC tables, etc.) have no natural spelling. `Final[tuple[UInt32, UInt32, ..., UInt32]]` works but is unwieldy at N=64+ and doesn't compose with `Span[UInt32]` consumers without a conversion. A module-level `list[UInt32]` heap-allocates once at module init; correct but wrong shape for what is conceptually a `constexpr std::array`. Right surface is probably `Final[Array[UInt32, 8]]` -> `inline constexpr std::array<uint32_t, 8>` (header-emitted, no init order, fully constant-folded). Open: whether to also accept `Final[list[T]]` as syntactic sugar that codegens to the same `std::array` (size from initializer length).
- `Out[T]` annotation for by-ref out-parameters (upstream #20). C/C++ APIs commonly return multiple values via by-reference out-params (`void f(FixStr30 sd, ContractDataBuffer*& outCdb, ExchangeCdb*& outExchangeCdb)`). Porting these to TPy today requires changing the signature shape -- typically a `tuple[Ptr[T], Ptr[T]]` return -- which deviates from source parity. Surface: `def f(sd: FixStr30, out_cdb: Out[Ptr[CDB]], out_ex: Out[Ptr[ECDB]]) -> None`, lowering to `void f(FixStr30 sd, CDB*& out_cdb, ECDB*& out_ex)`. Two call-site shapes to consider: (a) implicit pack -- `cdb, ex = f(sd)` and the compiler synthesizes locals bound by reference to the out positions; (b) explicit -- caller declares locals first and passes by name (`f(sd, out_cdb=cdb, out_ex=ex)`). Body-side semantics in both cases: assignments to `Out[T]` parameters write through to the caller's locals. Why it matters: canonical Aerie codegen shape for `_algo_*` helpers that produce more than one value -- with `Out[T]` the port can stay 1:1 with the C++ source. Existing parity gap (recap): tpy already special-cases container parameters to be passed as `T&` / `const T&` based on mutation analysis; `Out[T]` extends that to a user-facing annotation for the case where the caller explicitly wants by-ref semantics regardless of mutation.

## Ownership & Consuming Iteration
- Consuming `items()` for dict: consuming `__iter__` works for keys, but consuming `items()` can't use `@overload` with `Own[Self]` because the return type changes (`dict_items` -> `Iterator[tuple]`), breaking non-iteration callers like `len(d.items())`. Needs a mechanism that only selects consuming dispatch when used as a for-loop iterable.
- `own_iter()` is list-only: kept as explicit escape hatch for non-last-use consuming. Could be made generic (dispatch to consuming `__iter__` on any type).
- `own()` builtin: explicit `T -> Own[T]` conversion (analogous to `span()` -> `Span[T]`).
- User-defined drain iterators (e.g. `ArrayListDrainIter`): view types with borrow tracking. See `docs/CONSUMING_ITERATION_DESIGN.md`.
- Codegen `std::move` for owned `self.field` returns: sema types `Own[Self].field` correctly as `Own[T]`, but codegen emits `return this->inner;` instead of `return std::move(this->inner);`. Breaks any `@nocopy` / unique-ownership field pattern with a C++ "use of deleted function X(const X&)" error from the copy path. Reproduces with `Own[Inner]` field + method body that mutates other state before `return self.inner`. Noted as "Partial" in `docs/CONSUMING_ITERATION_DESIGN.md` status table.

Today `IntLiteralType` is resolved at the assignment site to `default_int_type` (Int32 by default), so `a = 0; f(a)` for `f(x: UInt64)` requires either `a: UInt64 = 0` or a cast. The current `literal_default_vars` retro-widening covers function-local cases that re-fit a fixed-int target on first typed-slot use, but module-level constants (`CONST = 5`), collection-element literals (`weights = [10, 20, 30]; send_byte(weights[0])`), and locals reassigned from a non-literal expression don't benefit. The full alternative would be to keep `IntLiteralType` polymorphic *everywhere* until first use that demands a concrete type -- the consistent mental model is "literals adapt to context anywhere", but the cost surface is wide: comparisons, prints, `for x in xs:` iter element types, generic inference, container element-type unification, and ~all sema sites that read `var_types[id(decl)]` mid-flow would need to handle "still IntLit" or trigger resolution. Also requires a deliberate generic-inference policy (do unbound `T` resolve to default_int from a literal arg, or look ahead at constraints?). Defer until the retro-widen cliff (function-local mutation drops the seed; conflicting demands lock to first usage) starts producing user complaints in real code.
- CPython native (C) module for tpy stubs: the `lib/cpy/tpy/` stubs are pure Python. A C extension module could improve CPython performance for programs that use tpy types (Int32, Array, Span, etc.) heavily.
- investigate rust like feature (borrowing, lifetimes etc) to make the language safe; however these should be softer restrictions than in rust
- zig language: what it is, how is it different from C, what useful patterns can we learn
- Distinct types (newtypes): `class Meters(Distinct[float]): pass` -- zero-cost wrapper that creates a nominally distinct type. Prevents mixing incompatible values of the same underlying type (units, IDs, currencies). C++ codegen: thin struct wrapper or strong typedef. Inspired by Nim's `distinct` keyword.
- `@constexpr` decorator: mark pure functions as compile-time evaluable, emit C++ `constexpr`. Useful for lookup tables, constants, config. Low implementation cost -- lean on C++ compiler. `TABLE: Final[Int32] = factorial(10)` computed at compile time.
- Inline iterators: `@inline` on generator functions to unroll the loop body at the call site instead of creating a state machine. Zero overhead, important for hot paths. Generalizes what `range()` already does implicitly to user-defined iterators. Inspired by Nim's inline vs closure iterator distinction.
- Runtime exception migration -- see `docs/EXCEPTION_DESIGN.md` for the per-type migration table (status, sites, divergences). Pending items live there, not here.
- Better runtime panic message for unhandled `@error_return` calls. Currently `_maybe_error_return_unwrap` (`tpyc/codegen_cpp/expressions.py`) emits `tpy_panic("unhandled error return")` which is opaque -- doesn't include the function name or the error value's data. Improve to `tpy_panic("unhandled X in <func>: " + e.message)` or similar. Affects all return-tier panic sites uniformly.

## Builtins
- Generic Fn param type deduction: `sorted[T,K](Iterable[T], Fn[[T],K])` shares T between iterable and Fn, so the Fn param can widen T (e.g. `sorted([3,1,4], key=negate)` widens T from Int32 to BigInt). In C++, T and KeyFn are independent template params -- the key function's type is deduced separately and implicit conversion handles the call. The proper TPy fix: support independent callable type params bounded over other params, e.g. `sorted[T, KFn: Callable[[T], Comparable]](Iterable[T], KFn)`. Current behavior (widening) is correct but suboptimal; explicit `list[Int32]` + BigInt key already errors.
- type(); (in future `T = type(x); z = T()`)
- tpy.ctypes.CInt32
- ptr() function? Auto-select Ptr vs Ptr[readonly[T]] based on binding mutability. Needs sema-level magic (mutability not in type, it's in binding context).
- `tpy.unsafe.unsafe_address_of(x) -> int`: return the memory address of an object as an integer. Useful for identity comparison in tests (proving reference semantics vs silent copy). C++ codegen: `reinterpret_cast<uintptr_t>(&x)`.

## Python features
- Enum name lookup: `Kind["TEXT"]` -> `Kind.TEXT`. CPython uses `EnumMeta.__getitem__` with a string key. C++ codegen: `EnumUtil<Kind>::from_name("TEXT")` (already exists in runtime). Needs subscript support on enum types in sema + codegen.
- properties master
- Generator: `yield from`, `send()`, `throw()`, `close()`
- Generator: protocol-typed params (`def gen(it: Iterator[T])`) -- needs template struct + factory. Currently emits `T&` without `template<typename T>` and simple generator path tries `begin()/end()` instead of `__next__()`.
- Generator: liveness optimization -- only promote yield-crossing variables to struct fields, keep others as stack locals in `__next__()` (currently all locals are promoted)
- Closures: `std::move_only_function` for `Callable` with `Own[T]` params/returns (design doc says to use it, currently uses `std::function` with rvalue params which works but is incorrect per C++23 semantics)
- Closures: `@noalloc` enforcement (Phase 5) -- `Callable` in `@noalloc` context should be rejected. Currently compiles without error.
- `in` operator without `__contains__`: warn in `@hotpath`/`@noalloc` contexts. Falls back to O(n) linear iteration (`std::ranges::contains` for built-in NativeIterables, `::tpy::__iter__` + `__next__` for others), which is almost certainly not intended in perf-critical code. Users should define `__contains__` for O(1) lookup or be aware of the cost.
- Closures: method references (`obj.method` as a value) -- needs partial application binding `self`. Currently gives "has no field" error.
- Protocol isinstance in ternary expressions: `x = a.foo() if isinstance(a, P1) else a.bar()` generates a runtime `?:` but both branches must be valid C++ at template instantiation time. Fix: generate an IIFE with `if constexpr` inside, e.g. `[&]() -> T { if constexpr (P1<T_a>) { return a.foo(); } else { return a.bar(); } }()`. This also enables single-line field init in `__init__` (goes into the C++ member initializer list instead of requiring unconditional pre-assignment + reassignment in branches).
- Allow `@runtime_checkable` decorator on protocols (no-op in tpyc, enables CPython compatibility for isinstance checks on user-defined protocols)
- Nested patterns in match/case: `case Box(value=str() as v)` for disambiguating parameterized union members like `Box[str] | Box[int]`. Uses field guards with type sub-patterns -- standard Python match syntax, CPython-compatible.
- allow type annotation to use "" (forward decl)
- C-style for loop: reassigning loop variable affects iteration (differs from Python)

## Type System
- `is_trivially_destructible()`: current approximation uses `is_value_type() and not is_expensive_copy()`, which is conservative for non-value types (e.g. Span, SpanIter are trivially destructible but return False). Proper implementation: primitives/views/pointers always trivial; records trivial if no `__del__` and all fields/bases are trivially destructible; tuples/optionals trivial if elements are. Used by `del` codegen to elide move-sink.

## Refactor
- Unify comparison operator codegen with arithmetic: comparisons (`==`, `!=`, `<`, etc.) now resolve through `BINOP_TO_METHOD` + `resolved_binop` like arithmetic ops, but two issues remain: (1) `DUNDER_CPP_TEMPLATES` in `operators.py` duplicates `DUNDER_TO_BINARY_OP` in `codegen_cpp/context.py` -- both map dunder names to C++ operators. Consolidate into one table or derive templates from the operator character. (2) The comparison codegen section still has its own special cases (BigInt/float cast, IntEnum coercion, Optional unwrap, literal folding) that run before `resolved_binop` dispatch. Ideally these would be handled uniformly in the binop result path.
- Extract shared arg-binding helper between `_gen_call` and `_gen_method_call` in `codegen_cpp/expressions.py`. Today each dispatcher has its own loop over `(arg, param)` pairs that applies coercion, covariant wrapping, `@dynamic` adapter insertion, `TpyTypeParamConstruct` / `TpyVarargPack` materialization, TypeParamRef substitution, etc. The loops have diverged repeatedly: `TpyVarargPack` was first handled only in `_gen_call` (broke `math.hypot(*coords)` -> mirrored into `_gen_method_call`'s first-pass loop), and then again only in that first-pass loop (broke method `*args` user-record calls -> mirrored into the user-record branch at the bottom of `_gen_method_call`). `_gen_method_call` alone has at least two arg-emission loops (first-pass + per-record-type fallback) that drift independently. Fix: pull the per-arg transformation into a helper `_bind_args(args: list[TpyExpr], params: list[(str, TpyType)], type_subst) -> list[str]` and call it from all paths. Keeps the dispatch split (the paths resolve very differently -- registry lookup vs receiver-type method resolution + TypedDict/callable-field/nested-constructor/property/dunder special cases) while eliminating the duplicated arg-list logic that has been the source of "feature X added to one path, not the other" bugs. Pairs with: consider having sema rewrite module-qualified calls (`math.hypot(x, y)` is currently `TpyMethodCall(obj=Name("math"), ...)`) into bare `TpyCall` with a qualified name, so they route through the simpler dispatcher -- `math` is a compile-time namespace, not a runtime object with methods.
- Inplace operator C++ return type: `__iadd__`/`__ior__` etc. declare returning self type (Python semantics) but the C++ helpers (`list_extend`, `dict_update`) return `void`. Add thin wrappers that return `T&` (e.g. `list_extend_inplace`, `dict_update_inplace`) so the declared return type matches the C++ signature. Affects list and dict.
- `tpy::ptr_variant<Ts...>` wrapper: replace `std::variant<Ts*...>` in param signatures with a thin wrapper that has an implicit converting constructor from `ptr_variant<T*...>` to `ptr_variant<const T*...>`. This would let deduced-const (non-mutated) params use deep const consistently with `@readonly`, without breaking callers. Currently deduced-const uses shallow const (`const variant<T*...>`) which doesn't prevent mutation through the pointer at the C++ level. Start with param signatures only; locals/fields/returns can stay `std::variant`.
- Inline `and`/`or` chains for side-effect-free operands: `a or b or c` currently emits an intermediate temp (`auto&& __tmp = (a ? a : b); result = (__tmp ? __tmp : c)`) to avoid double-evaluation. When all operands are provably side-effect-free (variables, literals), the temp is unnecessary and the chain can be emitted as a single nested ternary (`!a.empty() ? a : !b.empty() ? b : c`), which is more readable.
- `tpy::tpy_callable<F, R(Args...)>` concept: replace verbose `requires requires(__F0& __fn, ...) { { __fn(...) } -> std::convertible_to<R>; }` blocks with a compact `tpy::tpy_callable<__F0, R(Args...)>` concept in the runtime. Same `R(Args...)` notation as `std::function`. Needs a helper trait with partial specialization (`std::invocable` + `std::convertible_to` for return, void special case). Cosmetic improvement -- only worth prioritizing if it measurably speeds up C++ compilation for template-heavy Fn usage.
- Unify rvalue materialization: two overlapping mechanisms exist for extending rvalue lifetimes -- the slot system (`std::optional<T>` slots in `_gen_pointer_local_init`, tied to var decl infrastructure) and TempState (`auto&&` temps, expression-level). Both solve the same problem at different abstraction levels. Consider exposing a lower-level "materialize this rvalue" API that both var decls and expression-level temps (e.g. `and`/`or` ternaries) can share.
- Transparent coercion codegen: `TpyCoerce` in codegen has a growing list of special cases for when to forward `coerce_target` vs `actual_type` to the inner `gen_expr` (literals need the target to pick C++ representation; view coercions need it for zero-copy paths). Add a `transparent: bool` flag on coercion definitions so the decision is made at coercion definition time in `coercions.py`, not with `isinstance` checks in codegen.
- Deferred type resolution in parser: the parser currently resolves type names eagerly during parsing, but its per-module TypeRegistry lacks cross-module types. Two workarounds exist: (1) a `resolved` guard that accepts any import-resolved name as a NominalType in annotation context (sema validates later), and (2) speculative `_parse_type_annotation` at call-parsing sites with a sema fix to clear `call_type` when the name turns out to be a function. The proper fix: the parser should produce unresolved type reference nodes and let sema (which has full cross-module information) resolve them. This would also eliminate `_resolve_primitive_type` special cases for `slice`/`int`/`float`/etc. -- sema would resolve all type names uniformly through type factories.
- Push subscript metadata from compiler hardcoding into library-declared type metadata. Today the codegen bounds-safe path needs to know whether a type's C++ `operator[]` takes `size_t` (built-in containers: `vector`/`array`/`span`/`string`/`bytes` families) or the user's declared param type (typically `int32_t` for user records). The decision lives in `_is_concrete_user_record` (`codegen_cpp/expressions.py`) gated on `is_list/is_array/is_span/is_str_category/is_bytes_category` predicates from `type_def_registry.py` -- "STL types use size_t" is a fact about the library that's currently baked into the compiler. Cleaner: declare each type's `operator[]` parameter type as part of its TPy stub metadata (and similar properties: bounds-checked vs unchecked, supports negative indices, etc.) and have codegen query it. Pairs with the broader "Unify `TypeDef.cpp_formatter` and `@native` / `_native_cpp_names`" entry in the strict-warning hardening section -- both are about pushing per-type C++ properties from compiler-side hardcoding into library-declared metadata. Same shape applies to other ad-hoc per-type knowledge in codegen (e.g. the `iter_range` adapter dispatch, Python-int polymorphism per-type rules).
- Migrate generators onto the async resumable-frame abstraction. Once async/await ships (see `docs/ASYNC_DESIGN.md`), the language has two parallel state-machine codegens: the existing generator codegen (`tpyc/codegen_cpp/gen_generators.py`, ~850 lines: simple-generator lambda fast path + path-2 struct mode with known gaps like generic multi-yield rejection) and the new resumable-frame abstraction shared by `async def` lowering. Migrating generators onto the resumable frame unifies them: one shared "suspension points + frame fields + resume table + unwind state" mechanism handles both `yield` and `await`. Side benefits: the path-2 struct gaps go away (resumable-frame is generic-aware by construction), and `yield from` / `send` / `throw` / `close` / async generators all become incremental rather than from-scratch features. Open question: whether the simple-generator lambda path stays as a peephole optimization (zero state, single yield in one loop -> direct lambda), or is folded into the general path with the C++ compiler doing the optimization. Defer until async ships and the abstraction has been exercised; the simple path is real perf today.
- Resolve `@native(cpp_return_type=T)` annotation from string to `TpyType`. The user-supplied type name (`UInt64` etc.) is parsed into `_NameArg`, stored as a string on `TpyFunction.native_cpp_return_type` and `FunctionInfo.native_cpp_return_type`, and never read for its content -- codegen only checks `is not None` and casts to the *declared TPy return* (`fi.return_type`). The "true type" intent of the annotation is lost. Resolve the name in sema (registry lookup, mirror how `error_return(StopIteration)` resolves to a qualified record name) and store the resolved `TpyType`. Unlocks: (a) validation that the declared `cpp_return_type` is wider than `fi.return_type` (catches accidental `cpp_return_type=Int8` on a method declared `-> Int64`), (b) using the source type to drive smarter codegen (e.g. choosing between `static_cast` and `tpy::checked_cast` based on the conversion direction), (c) better error messages when the name doesn't resolve (today: silently accepted at parse time, breaks at codegen lookup if anything reads it).
- Reject `@error_return(E)` + `@native("name", cpp_return_type=T)` on the same method/function at sema time. The combination is meaningful (a C++ function returning `std::expected<T, E>` where T is wider than declared) but codegen short-circuits the cast in `_maybe_native_return_cast` (the `error_return_type is None` guard) -- so the user's `cpp_return_type` is silently ignored and `-Wconversion` may fire from inside the unwrap expression. Either implement proper composition (cast inside the unwrap statement-expression) or reject at sema with a clear error pointing the user at `@cpp_template`.
- Consolidate `_substitute_type_params` / `_subst_type_params` / `_partial_substitute`. Four copies of the same "replace TypeParamRef from a name->TpyType map, pass through unknowns" walk now exist: `tpyc/sema/operators.py`, `tpyc/sema/match.py`, `tpyc/sema/calls.py::_partial_substitute`, and `tpyc/cycle_detection.py` (the new one, which adds NominalType int-slot preservation for Array[T, N]). The canonical version is `tpyc/sema/type_ops.py::substitute_type_params` on the type-resolution context, but it lives on a sema-only object and not all sites can reach it. Extract a stateless helper (e.g. `typesys.substitute_type_params(typ, subst)` taking `dict[str, TpyType | int]`) that all four call sites consume; the int-slot handling becomes default rather than the special case it is in cycle_detection's copy. Surfaced by /tpy-review of the structural-cycle walker.

## C++ Codegen Review Findings (2026-03-12, updated 2026-03-18)

### Systematic suboptimalities
- **[HIGH effort]** Double subscript in augmented assignment: `a[i] += v` emits `__setitem__(a, i, add_check(__getitem__(a, i), v))` -- two separate bounds checks + index normalization. Hand-written C++ would use a single indexed access. Fix needs a reference-based codegen path (e.g. `__getitem_ref__` or direct `operator[]`).
- **[HIGH effort]** Inherited fields body-assigned instead of member initializer list: child constructors without `super()` assign inherited `std::string`/container fields in the body (default-construct then assign) instead of via MIL or base-class constructor delegation. Adds an extra default construction per non-trivial inherited field.
- **[MED effort]** Double `__deref__()` call in auto-deref field access: `r.x + r.y` where `r` has user-defined `__deref__()` emits `r.__deref__().x + r.__deref__().y` -- two separate deref calls. Should generate a temporary for the deref result when multiple field/method accesses share the same deref base in one expression.
### Minor type mismatches
- **[LOW]** Generator yield tuple uses `T&` instead of `T`: generic for-generators emit `auto __val = std::tuple<int32_t, T&>{...}` because the loop variable is bound as `auto&&`. The return wraps it in `std::optional<std::tuple<int32_t, val_or_ref_t<T>>>`, so the implicit tuple converting constructor strips the ref and it compiles correctly. Cosmetic -- the intermediate type is technically wrong but has no runtime impact.

### Performance: JSON parser codegen overhead
Benchmarked with CME MBO order book (15MB JSON, 20K messages). Library-level optimizations (skip_value rewrite, redundant _skip_ws elimination) brought 68ms->59ms. Hand-optimizing the generated C++ (removing checked arithmetic, direct pointer indexing) brought it to 23ms (7.6x vs CPython). The gap is:
- **[MED effort]** StrView/str direct indexing: `sv[i]` where `i` is non-negative Int32 guarded by `i < len` should emit `sv.data()[i]` instead of `__getitem__(sv, i)` with `normalize_index`. The pattern `while pos < len: c = data[pos]` is ubiquitous in parsers.
- **[MED effort]** Checked arithmetic elision for bounded loop counters: `pos += 1` where `pos < len` was just checked, `pos` is Int32, and `len` is Int32 -- the increment can't overflow. Extend `value_range.py` to propagate bounds from loop/if guards.

### Missed optimizations
- **[Open, no work planned]** Generic `T=str`/`T=bytes` param ABI doesn't match non-generic. Direct `str` params lower to `std::string_view`; generic-T routes through `param_val_or_ref_t<T>` keyed on the C++ storage type and gives `const std::string&` -- the trait can't distinguish TPy `str` from TPy `String` since they share `std::string` storage. Same conflation for `bytes`/`bytearray`. Cost: generic-T-over-str pays a `std::string` materialization at call sites (SSO covers short literals; long literals heap-allocate once per call). No fix is unambiguously best; every idiomatic option pays a real cost (distinct types via inheritance breaks `vector<auto_string>` <-> `vector<std::string>` interop; codegen monomorphization is heavy compiler internals; descriptor templates compromise readable-C++ output). Recommended fix *if* the perf gap ever justifies the work: codegen monomorphization (per-call function emission, output stays idiomatic, vector interop preserved). See `docs/IR_DESIGN.md` "Open Questions" item 8 for the full landscape. Surfaced on `heapq.heappush[str]` and on the generic-U-over-str dangling-view bug.
- **[MED effort]** Proven-safe `T=StrView` inference for pass-through generics. Until the U-over-str dangling-view fix landed, `prefer_strview_for_literals` auto-downgraded `T=str` to `T=StrView` when bare-T params received string literals, on the safety theory that string literals have static lifetime. The downgrade was zero-cost for pure pass-through (`def transform[U](x: U) -> U: return x` with `transform("hello")` produced `transform<string_view>("hello")` -- no materialization). Removed during the dangling-view fix because the signature-level safety check (excluding `Fn[..., T]` / `Own[T]` / record fields) couldn't soundly cover the bug class -- a generic body can construct/store/forward T values, and signature scanning misses that. To claw back the perf, the right shape is **body analysis**: only auto-infer `T=StrView` when the generic is *proven* borrow/pass-through safe -- body returns/yields exactly one of the bare-T literal-backed params, no construction/storage/forwarding of new T values. Use `return_borrows_from` facts if they can express it; otherwise it's an explicit body pass. Today the perf is recovered by writing `transform[StrView]("...")` explicitly. Surfaced when test diffs showed `transform<std::string_view>` -> `transform<std::string>` after dropping the downgrade.
- **[LOW]** Gratuitous named-temp hoisting for non-identifier call args. `_gen_call` / `_gen_method_call` hoist every non-bare-identifier argument to a named local, even when no materialization, lifetime extension, or last-use analysis is needed: `heappush(h, 0)` emits `int32_t __tmp_1 = 0; heappush(h, __tmp_1);` instead of `heappush(h, 0);`. Observed across `cases/stdlib/heapq/expected/src/main.cpp` for trivial int literals, BigInt constructor calls, list literals, and the string case above. Pure source-level bloat -- RVO/dead-store-elim optimizes it at runtime, but it noises up generated C++ and adds work to the C++ frontend (already a compile-time bottleneck). Likely a uniformity decision in codegen to simplify evaluation-order / auto-move analysis. Fix: only hoist when the arg needs materialization (list literal -> vector, literal -> type-conversion), a slot for auto-move, or when two args could alias; let trivial literals pass through inline.
- **[MED effort]** Dead branch elision in codegen: when a condition folds to a constant (`if (true)` / `if (false)`), emit only the live branch body instead of the entire if/else structure. Currently the folded constant is emitted and the C++ compiler optimizes it away, but this adds unnecessary work to C++ compilation which is already a bottleneck. Applies to Literal narrowing (`if mode == "rb":` inside a branch where mode is known), union overload specialization (`isinstance` checks), and any future constant-folding path. Pattern exists in `_gen_if_overload_specialized` for union isinstance -- generalize to all if-conditions.
- **[LOW]** String concat chain produces N-1 intermediate allocations: `a + b + c + d` emits left-associative nested `str_concat` calls, each allocating a temporary `std::string`. A codegen optimization detecting a chain of `+` on string-view operands could emit a single `reserve` + N `append` calls.
- **[LOW]** BigInt method return copies: any method (including property getters) returning `int`/BigInt returns by value (`::tpy::BigInt`), copying on every call. Not property-specific -- `is_value_type()=True` makes `_resolve_return_type` use value return. `str` has `StrView` as a zero-copy alternative; BigInt has no equivalent view type. Fix options: (A) add a `BigIntView` / `const BigInt&` return convention for non-mutating methods, (B) extend `_resolve_return_type` to use `const T&` for `is_expensive_copy()` types in const methods.
- **[LOW]** `__param_` copy for reassigned parameters: when a parameter is reassigned in the function body, codegen takes it by `const&` then copies into a mutable local. For BigInt/string params, taking by value instead would let the caller move. Only helps when caller passes an rvalue; for lvalue calls it's worse (forces copy at call site vs zero-cost `const&`). Also changes ABI (not API).

## Low Priority
- Automatic `Iterable[T]` range-for dispatch via a range-adapter. Codegen emits a single range-for over a helper `::tpy::iter_range(items)` that returns `std::ranges::ref_view(items)` when the concrete type satisfies `NativeIterable` (zero-overhead direct begin/end) or `::tpy::__iter__(items)` otherwise (`native_iterator` or user iterator with `next_iter_mixin`-synthesized begin/end). Single loop body in generated C++; dispatch hides inside the helper via `if constexpr`. Strictly cleaner than both the manual `Iterable[T] | NativeIterable[T]` + isinstance pattern (ugly) and an `if constexpr`-around-body approach (body duplicated). Could collapse the current universal default (`for (;;) { r = __itr.__next__(); ... }`) into the same `for (auto x : iter_range(...))` form for uniformity. Gotchas to resolve: (1) `val_or_ref<T>` unwrapping in the loop variable (needs a deref-hook in `next_iter_mixin::iterator` or an `operator T` decay); (2) move-only iterators (`map`/`filter`/`zip` results) — verify both branches preserve no-copy semantics; (3) rvalue iterables need an lvalue binding first (already done via `auto&& __src`). Infrastructure already in place: protocol narrowing + concrete-type NativeIterable detection both plumbed through codegen. Confirm via benchmark that uniformly routing everything through the adapter doesn't regress anything.
- Native records without `__init__` silently get a positional constructor synthesized from field order. This is fragile -- reordering fields in the `.py` stub breaks callers with no error. Should require an explicit `__init__` stub instead (like non-native records).
- TypedDict per-field `NotRequired[]` / `Required[]` (PEP 655) for finer control than `total=False`.
- `f"{x!r}"` doesn't use the repr() sema fallback: `repr(x)` accepts primitives and user records, but `f"{x!r}"` still requires the `Representable` protocol. Should share the same acceptance logic.
- `= default` semantic gap: records with required `__init__` params currently emit `ClassName() = default;` if their C++ fields are all trivially constructible, bypassing the Python-level construction contract. Should emit `= delete` (or nothing) instead -- `std::optional<T>` and containers don't require default-constructibility, so the impact is limited to direct `T t;` / `T arr[N]` patterns which tpyc doesn't generate anyway. Fix: check `init_params` required count in `_fld_type_cpp_default_constructible` (same as `_is_default_constructible`). See `docs/CONSTRUCTOR_DESIGN.md` open question 4.
- Unnecessary pointer locals for loop-scoped tuple unpack vars: `reassigned_vars` marks a name as reassigned when it appears in two for-loops, even though the C++ declarations are in independent loop-body scopes. This causes `T*` pointer indirection instead of `T&` reference binding. The scopes are independent in C++ so re-declaration as `T&` each iteration is safe.
- None-seeded variable assigned in all branches stays `Optional[T]`: when `x = None` is followed by assignment in both the `if` and `else` branches (so every path guarantees a value), `x` is still typed `std::optional<T>` after the if/else block. Post-dominance analysis could demote it to `T` and skip the optional wrapper. Not a correctness issue -- output is identical -- but adds unnecessary runtime cost and less readable C++.

## Known Limitations
- Subscript narrowing: `if items[i] is not None:` does not narrow `items[i]`. Hard to make sound due to index aliasing and container mutation; would need invalidation on any container write.
- Pointer-local slot reuse: reassigned T* pointer-locals allocate a fresh `std::optional<T>` slot per assignment. The initial slot could be reused after reassignment instead of allocating a new one.
- INT type params on functions: parsing works (`def foo[T, N: int]`) but codegen crashes for non-stub functions -- `inferred_type_args` contains `int` values that `type_to_cpp()` can't handle. Need `type_param_kinds` on `FunctionInfo` + codegen fixes. Stubs (`@cpp_template`/`@native`) work fine.
- Union isinstance narrowing in ternary: `x if isinstance(x, str) else ...` where `x: str | int` would need `std::get<T>()` extraction, which requires statement-level codegen (variable declaration for the extracted value).
