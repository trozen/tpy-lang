- `@native("rename")` silently ignores the module's `cpp_namespace` -- design footgun. Current semantics: `@native` (no arg) in a `cpp_namespace("X")` module emits `::X::<PythonName>`; `@native("name")` emits bare `name` (namespace ignored); `@native("ns::name")` emits `ns::name`. Writing `@native("sys_time_t")` in a `cpp_namespace("mylib")` module reads as "relative to mylib" but emits unqualified -- silent mis-binding if `::sys_time_t` happens to exist globally. Migration: audit existing `@native("ns::X")` call sites where `ns` matches the enclosing `cpp_namespace` -- currently redundant, becomes wrong under new semantics. Minimal viable alternative: warn when a `@native` rename string contains no `::` and the enclosing module has a `cpp_namespace`.

## Bugs
- Synthesized begin/end on user NativeIterable records calls begin() on a temporary iterator. `codegen_cpp/records.py` emits `auto begin() { return this->__iter__().begin(); }` for user records with `__iter__(self) -> SpanIter[T]` and no explicit begin/end. Currently safe for SpanIter (its begin() returns a raw span iterator pointing into the container, no self-pointer), but fragile: if `__iter__()` ever returns a `next_iter_mixin`-derived type whose begin() stores a parent back-pointer, the pointer would dangle. The for-loop peephole, comprehensions, and `in` operator capture `__iter__()` first as a forward-safety measure. Remaining uncontained callsites: generator expressions (`codegen_cpp/expressions.py::_gen_generator_expression`) and generator-body begin/end loop (`codegen_cpp/gen_generators.py:379,389`). Root-cause fix: remove the synthesis or make `NextIterator` own the Parent by value.
- Const inference gap for self passed through unknown callees: when a method passes `self` to a generic function whose FI is ephemeral (substituted copy, not tracked by Phase 2), mutation propagation skips the -1 sentinel in the unknown-callee conservative path (`caller_idx >= 0` guard in `mutation_propagation.py`). This means the method could be incorrectly inferred as const. Fixing this requires resolving ephemeral FIs back to their canonical registry entries, but FI object identity is not preserved across the registration/normalization/analysis lifecycle (multiple call paths create ephemeral FIs, and the canonical FI may not exist yet at recording time). See `_resolve_single` in `mutation_propagation.py`.
- `__str__` vs `__repr__` separation: C++ `operator<<` serves as both, but Python distinguishes them. `print(x)` should use `__str__` (no quotes on strings), while container printing (`print([x])`) should use `__repr__` (quotes). Currently `operator<<` can't distinguish the two contexts. For recursive unions, `print(json_val)` where json_val holds a dict with string values prints `{'a': hello}` instead of `{'a': 'hello'}`. Affects all types, not just recursive unions -- the compiler handles this ad-hoc via `gen_print` (top-level) vs `detail::print_element` (containers). Fix: implement proper `__str__`/`__repr__` methods and have `print()` call `__str__`, containers call `__repr__`.
- Enable C++ compiler warnings as errors (see `CppCompilerConfig.warn_flags` in compiler.py): blocked on exhaustive match/finally/with not emitting `__builtin_unreachable()` after end labels (`-Werror=return-type`), INT64_MIN/UINT64_MAX emitted as bare literals (`-Werror` large-integer-constant), and native globals emitting `extern T x = val` (`-Werror` extern-initialized). Also need generated code cleanup for `-Wall`/`-Wextra`/`-Wsign-conversion` (unused vars/labels/params, sign-conversion on array indexing).
- Generic generators with multiple yield points (struct-based codegen path) are not yet supported -- the out-of-line `__next__()` in .cpp won't link for template structs. Currently guarded with a sema error. Fix: emit struct + `__next__()` body into the header when the function has type params.
- Non-native functions in builtin modules can't be called from user code: codegen emits unqualified names (e.g. bare `enumerate(...)` instead of `tpystd::builtins::enumerate(...)`). The `imported_names` path considers any registered function as "shadowing" the import. Blocks defining pure TPy generator builtins. Workaround: use `@cpp_template`/`@native` with C++ implementation instead.
- Use-after-free not caught by borrow checker: `old = d.get(k); del d[k]; use(old)` -- `dict.get()` returns a pointer into the dict's internal storage. `del d[k]` frees that entry, making `old` a dangling pointer. The subsequent `use(old)` is undefined behavior (reads garbage). The borrow checker should warn that `old` borrows from `d` and `del d[k]` invalidates it. Workaround: reorder to use `old` before `del`.
- Property narrowing not supported: `if f.val is not None: f.val + 1` does not narrow because property access is a method call (could return different values). Same as function calls. Workaround: `v = f.val; if v is not None: v + 1`. Could support narrowing for simple field-returning getters in the future (requires getter body analysis).
- Overload resolution: generic overloads with protocol params lose to concrete overloads with coercion. `sum[T: AnyFixedInt](Iterable[T])` doesn't match `list[Int32]` in pass 1 because `_structural_match` requires `type(arg) == type(param)` -- `ArrayType` != `NominalType("Iterable")`. The concrete `sum(Iterable[float])` then wins via coercion in pass 2. Fix: `_structural_match` should check protocol conformance when `param` is a protocol type, so generic overloads with protocol params match in pass 1. Workaround: add concrete overloads for common types (Int32, Int64) before the generic.
- `repr()` and f-string `{}` don't work on union types: `repr(x)` where `x: A | B` fails with "No matching overload". Requires isinstance narrowing to access the concrete type. Fix: `_repr_fallback_template` should handle `UnionType` via `std::visit` dispatch.
- `key in dict` fails when key is a tuple type: the `in` operator sees the tuple LHS and tries tuple `__contains__` instead of dict `__contains__`. Workaround: use `dict.get()` or restructure keys as flat integers.
- `[False] * n` crashes at runtime: `list[bool]` maps to `std::vector<bool>`, which is a C++ special case (bit-packed proxy type). `repeat_range`/`from_range` don't work with it because `vector<bool>::reference` is a proxy, not a real `bool&`. Workaround: use `list[Int32]` with 0/1 values. Fix: either avoid `std::vector<bool>` (use `std::vector<uint8_t>` or `std::vector<char>` for `list[bool]`), or specialize the repeat path.
- Readonly-deduced method returns `Span[const T]` but declared return type has `Span[T]`: when a method is deduced readonly, `list_slice` on the const container returns `std::span<const T>`, but the return type `Own[Span[T] | list[T]]` uses non-const `std::span<T>`. The implicit conversion fails. Fix: propagate readonly into Span members of union return types when the method is deduced const, or emit a const_cast in codegen.
- Inherited `__repr__` not used by `operator<<`: `_gen_record_ostream` only checks direct methods (not inherited) to avoid `BaseException.__str__` leaking into exception subclasses. This means `print(child)` gives `<Child object at 0x...>` even when the parent defines `__repr__`, but `repr(child)` correctly finds the inherited method. Consider checking inherited `__repr__` while excluding known problematic base classes.
- `in` operator error with multi-overload `__contains__`: when no overload matches, the error reports only the first overload's param type (e.g. "expected UInt8") even though other overloads exist (e.g. `bytes`). Should list all candidates like function call overload errors do.
- Variable re-exports through native_module facades don't produce usable VARIABLE bindings downstream. `lib/tpy/tpy/__init__.py` is `# tpy: native_module` (declaration-only, no C++); doing `from ._submodule import SOME_CONST` there and then user code doing `from tpy import SOME_CONST` fails sema with "'SOME_CONST' is not a variable" (expressions.py:528 -- the binding kind is IMPORTED_NAME, not VARIABLE). Types/functions/records re-export through native_module facades fine; only variables hit this. Workaround: user imports directly from the submodule -- that's why `tpy.version` is a separate submodule (`from tpy.version import __version__`) rather than re-exported through `tpy`. Fix: namespace lookup should follow IMPORTED_NAME to the underlying binding and expose it as a variable when the source is a module-level const.
- Redundant LHS `deref_check` in `p.x = EXPR` when the RHS already derefed `p`. C++17 sequences RHS-before-LHS for the whole assignment, so a `deref_check(p)` on the RHS provably runs before any LHS code -- the LHS's own `deref_check(p)` is dead. `p.x = p.y + 1` currently emits `::tpy::deref_check(p).x = (::tpy::add_check<int32_t>(::tpy::deref_check(p).y, 1));` when `p`'s non-null status wasn't already established. Statement-boundary narrowing (fixed in this commit for cross-statement elision) can't help here because sema analyzes the target before the value; runtime evaluation is reversed. A narrow special case in assignment codegen would catch it: if the RHS expression emission added `p` to `non_null_ptr_vars` (via the pending-flush mechanism), the LHS can use that fact when rendered. Live in `codegen_cpp/statements.py` in the assignment emission path. Pre-existing pattern exposed by the new `ptr_deref_statement_boundary` regression test.
- `is_final` on `ModuleVarInfo` does not propagate through package `__init__.py` re-exports. `compiler.py::_extract_exports` populates `exports.final_variables` from `analyzer.ctx.final_globals`, which only contains *locally-declared* Finals; when `pkg/__init__.py` does `from .constants import VERSION` (where `VERSION: Final[str]`), the re-exported `VERSION` is added to `exports.variables` but not `exports.final_variables`, so downstream `_is_static_str` treats `from pkg import VERSION` as non-static. Fix: when a name is re-exported (present in `exports.reexported_variables`), look up the source module's `ModuleVarInfo.is_final` and propagate it. Noticed while threading Final info end-to-end for the macro_api `Final[str]` detection.
- Init chain doesn't propagate transitively through native_module facades. When a non-native submodule (e.g. `tpy.version`) has module-level constants with non-trivial `__tpy_init()` and its parent is `# tpy: native_module`, user code that reaches those constants via attribute access on the parent (e.g. `tpy.version.__version__` via `import tpy`) compiles but reads default-initialized values because the submodule's `__tpy_init()` is never chained into the user module's `__tpy_init()`. Workaround: import the submodule directly (`from tpy.version import ...`) which does chain the init. Fix: emit init-chain edges for transitive imports even when the intermediate module is a native_module. Pairs with the sema fix above.
- `import pkg.sub` followed by attribute access (`pkg.sub.X`) not supported in tpyc; only `from pkg.sub import X` works. With `import tpy.version` + `tpy.version.__version__`, sema rejects with "Undefined variable: 'tpy'" even though the import succeeded. Works in CPython (standard Python import semantics). Workaround: use `from tpy.version import __version__` instead. Fix: bind the top-level package name as a namespace-like object after `import pkg.sub` so attribute access walks the chain.
- `BytesView` as dict key / set element: `__hash__` works but `std::span<const uint8_t>` has no `operator==`, so `ordered_map`/`ordered_set` fail to compile. Needs an `__eq__` overload or `std::equal_to` specialization.
- Comprehension in a non-`Own` reference-returning function is UB. `def f() -> list[T]: return [x for x in ...]` where the return is lowered as a reference/view (e.g. an implicit `std::vector<T>&` path) would dangle because the comprehension's `__result` lives in a GCC stmt-expr block (formerly an IIFE lambda -- same issue). Pre-existing, not introduced by the IIFE->stmt-expr conversion. No known reproducer in current tests because container returns flow through `Own[T]` (by-value). - `fixed_int.hpp` checked-arith helpers rely on C++23 P2448 for the `std::string` construction in their overflow panic branches -- works but is non-obvious. - `type_conforms_to_protocol` side-effect in `PendingListType + UNKNOWN_ELEMENT` path (added in `sema/protocols.py:~111`). When an empty list literal conforms to `Iterable[T]`, the check mutates `info.coerced_element_type = protocol.type_args[0]` so the pending-list resolver can finalize. Under overload resolution, `type_conforms_to_protocol` is called once per candidate; the first successful probe cements the element type even if that overload is later rejected. With the `if info.coerced_element_type is None` guard, subsequent probes are skipped -- if overload A (`Iterable[int]`) is tried first and B (`Iterable[float]`) is the winner, the empty list resolves as `list[int]` instead of `list[float]`. Safe for all current stdlib callers (no overload groups with competing `Iterable[X]/Iterable[Y]` members), but latent bug for future such overloads. Fix: defer the coercion write to the post-resolution winner (pass coercion slot through as an out-param to the matched overload, not into the per-probe conformance check). Keep the check itself pure.
- Tuple iteration + Iterable conformance bundle. `for x in some_tuple:` fails sema with "Cannot iterate over type tuple[...]", and passing a tuple (literal or bound variable) to an `Iterable[T]` param fails conformance in `sema/protocols.py`. Real CPython compat gap -- `math.prod((1.0, 2.0, 3.0))` works in CPython, errors in TPy. Coupled fix needed: (1) sema `type_conforms_to_protocol` case for TupleType when all element types widen to T; (2) codegen emits a std::array-style view from `std::tuple<T, T, ...>` for iteration (std::tuple has no begin/end); (3) for-loop codegen dispatches to that view for tuple iterables. Doing just (1) would make sema accept code that then fails C++ template instantiation (the class of bug we've been cleaning up). Workaround: bind to `list[T]` first or pass a list literal. Surfaced while making math.prod/fsum/sumprod/dist take Iterable[float]; those are now done but skip tuple inputs.
- No `AnyInt` protocol covering BigInt + all `AnyFixedInt`. `AnyFixedInt` bounds a generic to fixed-width ints only (excludes BigInt). Writing a generic stdlib function like `gcd[T: AnyInt](a: T, b: T) -> T` that accepts BigInt *and* any fixed-width int has no natural bound. Surfaces when trying to write pure-TPy generics over int types (`math.gcd`, `math.isqrt`, anywhere int-algebraic). Workaround: declare as `int`-only (forces BigInt; small-int callers pay widening cost). Fix: add an `AnyInt` protocol in `lib/tpy/tpy/_core/_types.py` that unions BigInt + AnyFixedInt, with the arithmetic/comparison surface needed for common algorithms.
- Generic type params over int types can't use basic arithmetic without a bound. Pure-TPy `def gcd[T](a: T, b: T) -> T` rejects `a = -a` ("Cannot reassign parameter"; workaround: copy to local), `x = -x` on T ("Invalid operand type for unary '-'"), and `abs(x)` on T ("No matching overload for abs(T)"). Each is because T has no known signed-int bound. Resolving via the `AnyInt` protocol above (with `__neg__` / `__abs__` surface) would unblock pure-TPy integer generics. The ban on reassigning generic-typed parameters is probably separate and may warrant its own review -- for some patterns it's a real ergonomic tax.
- `tpy::fmod` / `tpy::fmod_f32` use C's `std::fmod` (sign-of-dividend, truncation), but Python's `%` on floats uses floor semantics (sign-of-divisor). Agrees for same-sign operands but diverges for mixed signs (Python `-1.5 % 2.5 == 1.0`; `std::fmod(-1.5, 2.5) == -1.5`). Fix: replace with `a - floor(a / b) * b` in both the runtime and constexpr paths. Will change the result of `%` on mixed-sign floats, so bump related snapshots.
- Final initializer overflow / div-by-zero (`Final[Int32] = -INT32_MIN`, `Final[float] = A / 0.0`) currently surface as cryptic C++ constexpr errors via P2448 rather than clean tpyc sema diagnostics. Users should never see a C++ error. Fix: fold constant Final initializers in sema and emit a proper diagnostic (with source location + explanation) when the fold panics. The P2448 rejection can remain as a last-resort safety net but should not be the user-visible mechanism.
- Iterating directly over a call that returns `Own[list[T]]` fails C++ compilation: `for e in make_batch(n):` emits `auto& __obj_0 = make_batch(n);` which can't bind an lvalue reference to an rvalue. Happens both at top level and inside function bodies. Workaround: bind the call to a named local first (`batch = make_batch(n); for e in batch:`). Fix: use `auto&&` (or `auto` for value types) for the hidden iteration temporary when the iterable expression is an rvalue. Likely in `codegen_cpp/statements.py` for-loop emission.
- Variable-hoist gap across sibling scopes: when the same local name is declared with `name: T = ...` inside a while-loop body **and** inside a sibling if/elif branch of the same function, the codegen hoists a single declaration at the loop's (inner) scope and then emits bare `name = ...` (no type) for the sibling branches, producing "not declared in this scope" C++ errors. Reproduced in `base64._b64_encode` while writing the stdlib module -- names `b0`/`b1` used inside `while ...:` and inside the subsequent `if rem == 1:`/`elif rem == 2:` branches. Workaround: rename the variables in the sibling branches. Fix: hoist same-name locals across branch-sibling scopes to the function scope (or emit fresh declarations in each branch). Lives in the codegen scope/hoist logic.
- Free function with `bytearray` parameter + in-body mutation (`param.append(...)`) gets the parameter lowered as `const std::vector<uint8_t>&` in generated C++, then fails with "passing const ... discards qualifiers" from `push_back`. Reproduced in `hashlib._pack_be32(dst: bytearray, v: UInt32)` while writing the SHA-256 module. - Consuming `items()` for dict: consuming `__iter__` works for keys, but consuming `items()` can't use `@overload` with `Own[Self]` because the return type changes (`dict_items` -> `Iterator[tuple]`), breaking non-iteration callers like `len(d.items())`. ## Safety
- Reassignment of borrowed variable doesn't warn: `remove_storage_borrows` silently clears active borrows on reassignment (`s = "other"`) without warning. Only mutation (`.append()`, `del`) triggers warnings. Affects all types but especially `str` in generators -- the only way to invalidate a `string_view` is reassignment/destruction, which is exactly the case the tracker misses.
- Globals not tracked in borrow system: `mark_param_mutated` only checks `current_param_names` (`context.py:688`), so global variable mutations are invisible to the borrow tracker. `ref = g[0]; g.append(x)` produces no warning.
- Nonlocal mutations invisible to outer scope: nested function analysis runs in isolated state (`save_function_state`/`reset_function_tracking`). Mutations to nonlocal variables inside closures don't propagate back to the outer function's borrow tracker.
- User-type indirect structural mutation not detected: `_is_invalidating_method` uses `direct_structural_mutated_params` (Phase 1), so `add_twice()` calling `self.add()` which does `self._items.append()` is not caught. Phase 2 propagates `structural_mutated_params` transitively, but the borrow check runs during Phase 1. Fix: add deferred borrow checks after Phase 2, similar to `resolve_pending_borrow_checks`.
- `Span[str]` subscript view: `SpanType.subscript_borrows()` is intentionally not overridden because `v = s[0]` registers `s` as the str-borrow source, but mutations to the backing container (`arr[0] = "x"` where `s = Span[str](arr)`) call `mark_str_borrowers_mutated("arr")` -- missing `s`. Fix requires `mark_str_borrowers_mutated` to chase the borrow tracker's alias chain so backing-container mutations also invalidate views borrowed through spans.
- View type borrow tracking for user types: currently only built-in view types (Span, Ptr) are tracked as borrows. Likely needed when designing tpy stdlib types. See escape analysis design doc (Future Extensions) for field-level vs class-level annotation tradeoffs.
- Hoisted non-value loop variable as view: `for s in items: ... print(s)` where `s` is `std::string_view` -- the hoisted `s` is a view into the container, not a copy. If the container is mutated between loop exit and use of `s`, the view dangles. Same concern exists with `const auto&` loop vars. Consider emitting a value copy for hoisted non-value loop variables.

## Investigate
- CPython native (C) module for tpy stubs: the `lib/cpy/tpy/` stubs are pure Python. A C extension module could improve CPython performance for programs that use tpy types (Int32, Array, Span, etc.) heavily.
- investigate rust like feature (borrowing, lifetimes etc) to make the language safe; however these should be softer restrictions than in rust
- zig language: what it is, how is it different from C, what useful patterns can we learn
- Distinct types (newtypes): `class Meters(Distinct[float]): pass` -- zero-cost wrapper that creates a nominally distinct type. Prevents mixing incompatible values of the same underlying type (units, IDs, currencies). C++ codegen: thin struct wrapper or strong typedef. Inspired by Nim's `distinct` keyword.
- `@constexpr` decorator: mark pure functions as compile-time evaluable, emit C++ `constexpr`. Useful for lookup tables, constants, config. Low implementation cost -- lean on C++ compiler. `TABLE: Final[Int32] = factorial(10)` computed at compile time.
- Inline iterators: `@inline` on generator functions to unroll the loop body at the call site instead of creating a state machine. Zero overhead, important for hot paths. Generalizes what `range()` already does implicitly to user-defined iterators. Inspired by Nim's inline vs closure iterator distinction.
- Runtime error exception model. Several CPython builtin exceptions currently manifest as panics in TPy: `IndexError` (bounds violations), `KeyError` (dict miss), `OverflowError` (fixed-int overflow), `ZeroDivisionError`, `AssertionError`, `TypeError` (rare runtime sites), `AttributeError` (dynamic-access paths). `ValueError`, `OSError`, `FileNotFoundError`, `StopIteration` are already catchable. Decision needed before any migration: should the panic set become catchable, and how? Two honest positions: **(a) panic is right** -- these are programmer errors, not recoverable conditions; zero overhead vs ~10-20% cost for unwind plumbing in hot loops; matches Rust/Zig philosophy; catching `IndexError` typically masks bugs; and **(b) catchable matches CPython idioms** -- `try: d[k] except KeyError: default` and `getattr(x, 'a', default)` are standard Python, code ports rely on these catches. Likely answer: build-time configurable. Axes: (1) global default (panic seems right for TPy's perf lean); (2) per-site mechanism -- single CLI flag, performance-profile-based (`@noalloc`/`@hotpath` imply panic, default catchable), F8 compile-time conditional, or per-category flags; (3) per-error-type split (`IndexError`/`KeyError` = bugs, `OverflowError`/`ZeroDivisionError` sometimes recoverable) vs uniform treatment. Natural interactions: F8 feature flags as the vehicle; performance profiles as the natural panic/catchable split. Each conversion is mechanical (define exception type, replace `tpy_panic(...)` with throw, verify two-tier exception propagation) -- ~50-70 sites total across the affected categories, worth deciding direction once rather than ad-hoc. Surfaced by the builtins section of STDLIB_ROADMAP.md.

## Refactor
- Unify comparison operator codegen with arithmetic: comparisons (`==`, `!=`, `<`, etc.) now resolve through `BINOP_TO_METHOD` + `resolved_binop` like arithmetic ops, but two issues remain: (1) `DUNDER_CPP_TEMPLATES` in `operators.py` duplicates `DUNDER_TO_BINARY_OP` in `codegen_cpp/context.py` -- both map dunder names to C++ operators. Consolidate into one table or derive templates from the operator character. (2) The comparison codegen section still has its own special cases (BigInt/float cast, IntEnum coercion, Optional unwrap, literal folding) that run before `resolved_binop` dispatch. Ideally these would be handled uniformly in the binop result path.
- Extract shared arg-binding helper between `_gen_call` and `_gen_method_call` in `codegen_cpp/expressions.py`. Today each dispatcher has its own loop over `(arg, param)` pairs that applies coercion, covariant wrapping, `@dynamic` adapter insertion, `TpyTypeParamConstruct` / `TpyVarargPack` materialization, TypeParamRef substitution, etc. The two loops have diverged repeatedly (most recently `TpyVarargPack` was handled only in `_gen_call`, causing `math.hypot(*coords)` called as `math.hypot(x, y)` to emit `/* unknown expr */` -- since fixed by mirroring the dispatch into `_gen_method_call`). Fix: pull the per-arg transformation into a helper `_bind_args(args: list[TpyExpr], params: list[(str, TpyType)], type_subst) -> list[str]` and call it from both paths. Keeps the dispatch split (the two paths resolve very differently -- registry lookup vs receiver-type method resolution + TypedDict/callable-field/nested-constructor/property/dunder special cases) while eliminating the duplicated arg-list logic that has been the source of "feature X added to one path, not the other" bugs. Pairs with: consider having sema rewrite module-qualified calls (`math.hypot(x, y)` is currently `TpyMethodCall(obj=Name("math"), ...)`) into bare `TpyCall` with a qualified name, so they route through the simpler dispatcher -- `math` is a compile-time namespace, not a runtime object with methods.
- Inplace operator C++ return type: `__iadd__`/`__ior__` etc. declare returning self type (Python semantics) but the C++ helpers (`list_extend`, `dict_update`) return `void`. Add thin wrappers that return `T&` (e.g. `list_extend_inplace`, `dict_update_inplace`) so the declared return type matches the C++ signature. Affects list and dict.
- `tpy::ptr_variant<Ts...>` wrapper: replace `std::variant<Ts*...>` in param signatures with a thin wrapper that has an implicit converting constructor from `ptr_variant<T*...>` to `ptr_variant<const T*...>`. This would let deduced-const (non-mutated) params use deep const consistently with `@readonly`, without breaking callers. Currently deduced-const uses shallow const (`const variant<T*...>`) which doesn't prevent mutation through the pointer at the C++ level. Start with param signatures only; locals/fields/returns can stay `std::variant`.
- Inline `and`/`or` chains for side-effect-free operands: `a or b or c` currently emits an intermediate temp (`auto&& __tmp = (a ? a : b); result = (__tmp ? __tmp : c)`) to avoid double-evaluation. When all operands are provably side-effect-free (variables, literals), the temp is unnecessary and the chain can be emitted as a single nested ternary (`!a.empty() ? a : !b.empty() ? b : c`), which is more readable.
- `tpy::tpy_callable<F, R(Args...)>` concept: replace verbose `requires requires(__F0& __fn, ...) { { __fn(...) } -> std::convertible_to<R>; }` blocks with a compact `tpy::tpy_callable<__F0, R(Args...)>` concept in the runtime. Same `R(Args...)` notation as `std::function`. Needs a helper trait with partial specialization (`std::invocable` + `std::convertible_to` for return, void special case). Cosmetic improvement -- only worth prioritizing if it measurably speeds up C++ compilation for template-heavy Fn usage.
- Unify rvalue materialization: two overlapping mechanisms exist for extending rvalue lifetimes -- the slot system (`std::optional<T>` slots in `_gen_pointer_local_init`, tied to var decl infrastructure) and TempState (`auto&&` temps, expression-level). Both solve the same problem at different abstraction levels. Consider exposing a lower-level "materialize this rvalue" API that both var decls and expression-level temps (e.g. `and`/`or` ternaries) can share.
- Transparent coercion codegen: `TpyCoerce` in codegen has a growing list of special cases for when to forward `coerce_target` vs `actual_type` to the inner `gen_expr` (literals need the target to pick C++ representation; view coercions need it for zero-copy paths). Add a `transparent: bool` flag on coercion definitions so the decision is made at coercion definition time in `coercions.py`, not with `isinstance` checks in codegen.
- Deferred type resolution in parser: the parser currently resolves type names eagerly during parsing, but its per-module TypeRegistry lacks cross-module types. Two workarounds exist: (1) a `resolved` guard that accepts any import-resolved name as a NominalType in annotation context (sema validates later), and (2) speculative `_parse_type_annotation` at call-parsing sites with a sema fix to clear `call_type` when the name turns out to be a function. The proper fix: the parser should produce unresolved type reference nodes and let sema (which has full cross-module information) resolve them. This would also eliminate `_resolve_primitive_type` special cases for `slice`/`int`/`float`/etc. -- sema would resolve all type names uniformly through type factories.

## C++ Codegen Review Findings (2026-03-12, updated 2026-03-18)

### Systematic suboptimalities
- **[HIGH effort]** Double subscript in augmented assignment: `a[i] += v` emits `__setitem__(a, i, add_check(__getitem__(a, i), v))` -- two separate bounds checks + index normalization. Hand-written C++ would use a single indexed access. Fix needs a reference-based codegen path (e.g. `__getitem_ref__` or direct `operator[]`).
- **[HIGH effort]** Inherited fields body-assigned instead of member initializer list: child constructors without `super()` assign inherited `std::string`/container fields in the body (default-construct then assign) instead of via MIL or base-class constructor delegation. Adds an extra default construction per non-trivial inherited field.
- **[MED effort]** Double `__deref__()` call in auto-deref field access: `r.x + r.y` where `r` has user-defined `__deref__()` emits `r.__deref__().x + r.__deref__().y` -- two separate deref calls. Should generate a temporary for the deref result when multiple field/method accesses share the same deref base in one expression.
### Minor type mismatches
- **[LOW]** Generator yield tuple uses `T&` instead of `T`: generic for-generators emit `auto __val = std::tuple<int32_t, T&>{...}` because the loop variable is bound as `auto&&`. The return wraps it in `std::optional<std::tuple<int32_t, val_or_ref_t<T>>>`, so the implicit tuple converting constructor strips the ref and it compiles correctly. Cosmetic -- the intermediate type is technically wrong but has no runtime impact.

### Performance: JSON parser codegen overhead
Benchmarked with CME MBO order book (15MB JSON, 20K messages). Library-level optimizations (skip_value rewrite, redundant _skip_ws elimination) brought 68ms->59ms. Hand-optimizing the generated C++ (removing checked arithmetic, direct pointer indexing) brought it to 23ms (7.6x vs CPython). The gap is:
- **[MED effort]** StrView/str direct indexing: `sv[i]` where `i` is non-negative Int32 guarded by `i < len` should emit `sv.data()[i]` instead of `__getitem__(sv, i)` with `normalize_index`. The pattern `while pos < len: c = data[pos]` is ubiquitous in parsers.
- **[MED effort]** Checked arithmetic elision for bounded loop counters: `pos += 1` where `pos < len` was just checked, `pos` is Int32, and `len` is Int32 -- the increment can't overflow. Extend `value_range.py` to propagate bounds from loop/if guards.

### Missed optimizations
- **[MED effort]** Generic `T=str` params use `const std::string&` instead of `std::string_view`. Direct str params (`def f(s: str)`) correctly lower to `std::string_view`, but when str reaches a param through a generic bound (`def f[T: Comparable](item: T)` instantiated with `T = std::string`), `param_val_or_ref_t<T>` in `runtime/cpp/include/tpy/type_traits.hpp` gives `const T&` -- no specialization for `T = std::string`. Consequences: string literals force materialization to `std::string` at call sites (`std::string __tmp = "cherry"; heappush(h, __tmp);` instead of passing the literal); callers holding `string_view` can't pass without constructing a string; generic code using str args pays an avoidable allocation on every call. Fix: add a `param_type_t<T>` trait alongside `param_val_or_ref_t<T>` with a specialization `std::string -> std::string_view` (candidate future specializations: `std::vector<T> -> std::span<const T>` for readonly generic params). Surfaced on `heapq.heappush[str]` while reviewing generated code for `cases/stdlib/heapq`.
- **[LOW]** Gratuitous named-temp hoisting for non-identifier call args. `_gen_call` / `_gen_method_call` hoist every non-bare-identifier argument to a named local, even when no materialization, lifetime extension, or last-use analysis is needed: `heappush(h, 0)` emits `int32_t __tmp_1 = 0; heappush(h, __tmp_1);` instead of `heappush(h, 0);`. Observed across `cases/stdlib/heapq/expected/src/main.cpp` for trivial int literals, BigInt constructor calls, list literals, and the string case above. Pure source-level bloat -- RVO/dead-store-elim optimizes it at runtime, but it noises up generated C++ and adds work to the C++ frontend (already a compile-time bottleneck). Likely a uniformity decision in codegen to simplify evaluation-order / auto-move analysis. Fix: only hoist when the arg needs materialization (list literal -> vector, literal -> type-conversion), a slot for auto-move, or when two args could alias; let trivial literals pass through inline.
- **[MED effort]** Dead branch elision in codegen: when a condition folds to a constant (`if (true)` / `if (false)`), emit only the live branch body instead of the entire if/else structure. Currently the folded constant is emitted and the C++ compiler optimizes it away, but this adds unnecessary work to C++ compilation which is already a bottleneck. Applies to Literal narrowing (`if mode == "rb":` inside a branch where mode is known), union overload specialization (`isinstance` checks), and any future constant-folding path. Pattern exists in `_gen_if_overload_specialized` for union isinstance -- generalize to all if-conditions.
- **[LOW]** String concat chain produces N-1 intermediate allocations: `a + b + c + d` emits left-associative nested `str_concat` calls, each allocating a temporary `std::string`. A codegen optimization detecting a chain of `+` on string-view operands could emit a single `reserve` + N `append` calls.
- **[LOW]** BigInt method return copies: any method (including property getters) returning `int`/BigInt returns by value (`::tpy::BigInt`), copying on every call. Not property-specific -- `is_value_type()=True` makes `_resolve_return_type` use value return. `str` has `StrView` as a zero-copy alternative; BigInt has no equivalent view type. Fix options: (A) add a `BigIntView` / `const BigInt&` return convention for non-mutating methods, (B) extend `_resolve_return_type` to use `const T&` for `is_expensive_copy()` types in const methods.
- **[LOW]** `__param_` copy for reassigned parameters: when a parameter is reassigned in the function body, codegen takes it by `const&` then copies into a mutable local. For BigInt/string params, taking by value instead would let the caller move. Only helps when caller passes an rvalue; for lvalue calls it's worse (forces copy at call site vs zero-cost `const&`). Also changes ABI (not API).

## Low Priority
- Automatic `Iterable[T]` range-for dispatch via a range-adapter. Codegen emits a single range-for over a helper `::tpy::iter_range(items)` that returns `std::ranges::ref_view(items)` when the concrete type satisfies `NativeIterable` (zero-overhead direct begin/end) or `::tpy::__iter__(items)` otherwise (`native_iterator` or user iterator with `next_iter_mixin`-synthesized begin/end). Single loop body in generated C++; dispatch hides inside the helper via `if constexpr`. Strictly cleaner than both the manual `Iterable[T] | NativeIterable[T]` + isinstance pattern (ugly) and an `if constexpr`-around-body approach (body duplicated). Could collapse the current universal default (`for (;;) { r = __itr.__next__(); ... }`) into the same `for (auto x : iter_range(...))` form for uniformity. Gotchas to resolve: (1) `val_or_ref<T>` unwrapping in the loop variable (needs a deref-hook in `next_iter_mixin::iterator` or an `operator T` decay); (2) move-only iterators (`map`/`filter`/`zip` results) — verify both branches preserve no-copy semantics; (3) rvalue iterables need an lvalue binding first (already done via `auto&& __src`). Infrastructure already in place: protocol narrowing + concrete-type NativeIterable detection both plumbed through codegen. Confirm via benchmark that uniformly routing everything through the adapter doesn't regress anything.
- Native records without `__init__` silently get a positional constructor synthesized from field order. This is fragile -- reordering fields in the `.py` stub breaks callers with no error. Should require an explicit `__init__` stub instead (like non-native records).
- TypedDict per-field `NotRequired[]` / `Required[]` (PEP 655) for finer control than `total=False`.
- `f"{x!r}"` doesn't use the repr() sema fallback: `repr(x)` accepts primitives and user records, but `f"{x!r}"` still requires the `Representable` protocol. Should share the same acceptance logic.
- Catch uncaught `tpy::BaseException` in generated `main()`: currently an unhandled exception produces GCC's `terminate called after throwing...` message, which is a C++ implementation detail. Should catch `tpy::BaseException` and print Python-style `ExceptionType: message` to stderr instead.
- `= default` semantic gap: records with required `__init__` params currently emit `ClassName() = default;` if their C++ fields are all trivially constructible, bypassing the Python-level construction contract. Should emit `= delete` (or nothing) instead -- `std::optional<T>` and containers don't require default-constructibility, so the impact is limited to direct `T t;` / `T arr[N]` patterns which tpyc doesn't generate anyway. Fix: check `init_params` required count in `_fld_type_cpp_default_constructible` (same as `_is_default_constructible`). See `docs/CONSTRUCTOR_DESIGN.md` open question 4.
- Unnecessary pointer locals for loop-scoped tuple unpack vars: `reassigned_vars` marks a name as reassigned when it appears in two for-loops, even though the C++ declarations are in independent loop-body scopes. This causes `T*` pointer indirection instead of `T&` reference binding. The scopes are independent in C++ so re-declaration as `T&` each iteration is safe.
- None-seeded variable assigned in all branches stays `Optional[T]`: when `x = None` is followed by assignment in both the `if` and `else` branches (so every path guarantees a value), `x` is still typed `std::optional<T>` after the if/else block. Post-dominance analysis could demote it to `T` and skip the optional wrapper. Not a correctness issue -- output is identical -- but adds unnecessary runtime cost and less readable C++.

## Known Limitations
- Subscript narrowing: `if items[i] is not None:` does not narrow `items[i]`. Hard to make sound due to index aliasing and container mutation; would need invalidation on any container write.
- Pointer-local slot reuse: reassigned T* pointer-locals allocate a fresh `std::optional<T>` slot per assignment. The initial slot could be reused after reassignment instead of allocating a new one.
- Inherited constructor forwarding: multi-level inheritance (`Child -> Mid -> Base`) where intermediate classes have no `__init__` doesn't forward the base constructor. C++ generates `Child() = default;` only, so `Child(args)` fails. Workaround: add explicit `__init__` + `super().__init__()` at each level.
- INT type params on functions: parsing works (`def foo[T, N: int]`) but codegen crashes for non-stub functions -- `inferred_type_args` contains `int` values that `type_to_cpp()` can't handle. Need `type_param_kinds` on `FunctionInfo` + codegen fixes. Stubs (`@cpp_template`/`@native`) work fine.
- Union isinstance narrowing in ternary: `x if isinstance(x, str) else ...` where `x: str | int` would need `std::get<T>()` extraction, which requires statement-level codegen (variable declaration for the extracted value).
