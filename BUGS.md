# Bugs

Known compiler defects: incorrect output, crashes, miscompiles, rejection of valid code, missing diagnostics for unsafe code.

For missing features and language design gaps see `TODO.md`.

Each entry's first line is a **[priority size]** tag plus a one-sentence summary; the full description follows on the next lines. Priority is one of:

- `IMM` -- users hit this in their first non-trivial program (or basic Python idioms);
- `HIGH` -- users hit this regularly in non-trivial programs / stdlib work;
- `MED` -- specific patterns or advanced features;
- `LOW` -- latent / quality / hardening, no current user impact.

Size is one of `small` (hours-1d), `medium` (1-3d), `large` (~week), `xlarge` (bigger).

## Compiler bugs
- **[LOW small]** Generic TPy function consuming a `list[T].pop()` into a local fails C++ build when `T` is a reference type (`val_or_ref_t<T> = T&` can't bind to `pop_back`'s rvalue return).
  Reproducer: `def heappop[T: Comparable](heap: list[T]) -> Own[T]: lastelt = heap.pop(); ...` from `lib/tpy/heapq.py`, instantiated with any user reference-type T (e.g. `class TimerEntry: ...; heap: list[TimerEntry]; heappop(heap)`). Generated code: `::tpy::val_or_ref_t<T> lastelt = ::tpy::pop_back(heap);` -- `val_or_ref_t<T>` for ref T is `T&`, but `pop_back` returns by value. Error: `cannot bind non-const lvalue reference of type 'T&' to an rvalue of type 'T'`. **Already documented** as a "language-level blocker" in the `lib/tpy/heapq.py` header (Phase-1-era comment), but never tracked here. Effect: ref-type heaps, ref-type generic stacks, and any other generic pattern that locally binds a `list.pop()` result. Surfaced again while attempting to swap `Executor.timer_heap` to `list[TimerEntry]` (ref-type variant) during async v1.x post-Phase-4 cleanup. **Workaround in heapq:** declare `lastelt: Own[T] = heap.pop()` (annotate the local as owning, side-stepping `val_or_ref_t`); requires a TPy-side check that `Own[T]` for value T resolves to plain T storage. **Fix:** codegen for generic-T locals bound from "consuming" calls (pop_back, dict.popitem, etc.) should use `Own[T]` storage shape rather than `val_or_ref_t<T>`. Sibling to the ValueType-specialization-ordering entry below: either fix independently unblocks `Executor.timer_heap` becoming a `list[TimerEntry]` (the natural shape).
- **[LOW small]** Non-`@native` ValueType record's `is_value_type` specialization is emitted *after* template instantiation sites in the same TU, producing C++ `specialization of X after instantiation` errors.
  Reproducer: `class TimerEntry(ValueType): deadline: float; waker: Waker; def __lt__(self, o): ...` used inside the same module as `heapq.heappush(self.heap, TimerEntry(...))`. Generated `_executor.hpp` emits in this order: (1) class definition, (2) `heappush<TimerEntry>(...)` call inside an inline method body, (3) `template<> struct tpy::is_value_type<...::TimerEntry> : std::true_type {}` at the end of the file. C++ rejects (3) because (2) already instantiated `heappush` while seeing the default `is_value_type<T> = false_type`, deducing `param_val_or_ref_t<T> = T&` and `val_or_ref_t<T> = T&`. **Workaround:** route the value through tuples + a parallel dict (the shape `lib/tpy/asyncio/_executor.py:Executor.timer_heap` shipped — see comment on `timer_heap` field), or restructure so the consumer that instantiates the template lives in a downstream module whose `.hpp` includes the value-type module's `.hpp` (the specialization is visible before instantiation). **Fix:** in `tpyc/codegen_cpp/generator.py:929-932`, emit each value-type record's `is_value_type` specialization right after the record's class body, *before* any inline method bodies / templated calls that might depend on it. Same family as the `@native` value-type namespace bug below — both stem from `is_value_type` being emitted at file end rather than per-class. Surfaced while attempting to swap `Executor`'s tuple+dict timer heap to `list[TimerEntry]` during async v1.x post-Phase-4 cleanup.
- **[LOW small]** `@native(...)`-decorated value-type record emits `tpy::is_value_type<...>` specialization in the module's own C++ namespace instead of the `@native` rename target.
  Reproducer: declare `@native("tpy::ExecutorHandle") class ExecutorHandle(ValueType): ...` in a module with `# tpy: cpp_namespace("tpystd::asyncio::_executor")`. The C++ class is `tpy::ExecutorHandle` (per `@native`), but codegen emits `template<> struct tpy::is_value_type<tpystd::asyncio::_executor::ExecutorHandle> : std::true_type {};` — a specialization for a non-existent type. C++ fails with `template argument 1 is invalid`. Lives in `tpyc/codegen_cpp/generator.py:929-932` where `module_to_cpp_namespace(self.ctx.module_name)` is hardcoded as the namespace; the `@native` rename should override it for records with linkage targeting an external C++ name. **Workaround:** don't inherit `ValueType` on `@native` records — TPy then treats them as reference types, which breaks other code (locals bound by `T&` lvalue reference can't bind to rvalue returns); the better workaround is to register the type in `tpyc/type_def_registry.py` with `is_value_type=True` (the path Waker / Poll / Task use). Hit during async v1.x Phase 3 while attempting to store an `ExecutorHandle` field on `_ExecutorScope` for thread-local save/restore — sidestepped by skipping the save in the scope guard since v1 asyncio.run doesn't nest. **Third symptom (silent overhead, no compile error):** an `@native` POD that *isn't* declared `ValueType` (the workaround above) is then treated as a *reference* type by codegen, so any coroutine-local of that type gets wrapped in `std::optional<T>` even though the type is a 16-byte POD. Verified for `ExecutorHandle` -- the coroutine state struct in `executor_bindings_smoke/expected/include/main.hpp:29` emits `std::optional<::tpy::ExecutorHandle> h`. Inflates coroutine frame size and adds a runtime check per access. Fix: register the type via `tpyc/type_def_registry.py` with `is_value_type=True` (current best practice for `@native` POD types).
- **[LOW small]** `@cpp_template` body containing a literal `{` or `}` produces an internal error instead of a clear diagnostic, and there's no escape syntax.
  Reproducer: `@cpp_template("::tpy::ExecutorHandle{static_cast<void*>(&{self})}")` (intended: emit C++ aggregate-init braces literally, with `{self}` substituted). The substitution engine treats `{static_cast...}` as a placeholder field name and raises `Internal error: unexpected '{' in field name` (from Python's `str.format` machinery) with no source location pointing at the decorator. Hit during async v1.x Phase 2.2 when trying to emit `ExecutorHandle{&obj}` aggregate init inline. **Workaround:** introduce a tiny C++ template helper that wraps the brace-initialized expression (Phase 2.2 went this route: `tpy::make_executor_handle<T>(T&)`). **Fix:** (a) UX -- catch the format-time error and re-raise as a TPy diagnostic with the decorator's source location and a hint that literal braces aren't supported; (b) feature -- add `{{` / `}}` escape syntax (matches Python f-string convention) so callers can spell literal braces. The same hazard applies to any `@cpp_template` string that wants to use C++ brace-init / lambda braces / scope braces.
- **[LOW small]** Nested-type access through a module-qualified class chain (`m.Outer.Inner`, `m.Outer.Kind.A`) is not implemented; only the bare-name shape (`from m import Outer; Outer.Inner`) works.
  Reproducer: `import m; m.Outer.Inner()` -- where `Outer` is imported from `m` and has a nested `class Inner` -- falls through the module-qualified dispatcher (which only handles class constants and staticmethods) into the bare-name analysis path and errors as "'m' is not a variable". Same for `m.Outer.Kind.A` (nested enum value through module-qualifier). The fix is symmetric to the existing module-qualified class-constant path: extend `_analyze_field_access`'s module-qualified branch to also call into the nested-type resolution helpers (`_resolve_nested_type_access`, `_resolve_nested_chain`). Workaround: `from m import Outer` then `Outer.Inner`. Surfaced as a deferred item during the module-qualified static-method-call fix.
- **[MED small]** Cross-module nested-type qualified names (`Outer.Inner`, `Outer.Kind`) rejected as type annotations: `Parse error: Unsupported qualified type: Outer.Inner`.
  Reproducer: `from m import Container` (where `Container` has nested `class Inner` and `class Kind(Enum)`); then `def f(x: Container.Inner) -> ...` errors at parse with `Unsupported qualified type: Container.Inner`. Construction (`Container.Inner()`) works, enum value access (`Container.Kind.BOX`) works, but the same dotted name in annotation position fails. Module-level alias `InnerAlias = Container.Inner` doesn't help: the alias resolves at sema but `Container.Inner` in the assignment fails the same way. CPython accepts both annotations. Affects local and cross-module nested types equally -- not strictly a cross-module bug. Lives in the parser's type-ref grammar, which doesn't accept dotted names whose head is a class binding (only dotted modules like `typing.Optional`). Fix: extend the type-ref parser to accept `<bare-name>.<bare-name>` chains where the head resolves to a record or enum at type-resolution time. Workaround: avoid annotating with the nested type (use the parent type or restructure to top-level). Surfaced by `/tpy-fuzzy-test cross-module class member access` (probes 12, 14 of `non-call-attribute-access`).
- **[LOW small]** Misleading `'X' is not a variable` error fires for several distinct unsupported patterns, blaming the class/module name rather than the actual problem.
  Same error string surfaces for: (1) `Foo.nonexistent_method(...)` -- class exists, method lookup failed (CPython: `type object 'Foo' has no attribute 'X'`); (2) `Foo.nonexistent_field` -- same; (3) `f = Foo.staticmethod` (taking method as value without calling) -- class exists, taking-method-as-value isn't supported. Not cross-module-specific; same error for local classes. A parallel misleading case: bound-instance-method as value (`m = inst.add`) errors with `Record 'Calculator' has no field 'add'` even though `add` is a (callable) method, not a missing field. Each fallthrough should emit a targeted message ("class 'X' has no static method 'Y'", "static methods can only be called, not taken as values", "bound method references are not supported"). Lives in `_analyze_name`'s fallback at `tpyc/sema/expressions.py:540` and the equivalent field-access fallthroughs. Surfaced by `/tpy-fuzzy-test cross-module class member access`.
- **[LOW small]** Importing the same module/name twice in the same file (mixing un-aliased and aliased forms) confuses the binding pipeline and drops the un-aliased symbol.
  Two variants surfaced. Variant A (codegen): `from m import X; from m import X as Y` -- subsequent use of `X` (e.g. `X.make(7)`) emits unqualified C++ `X::make(7)` but no `using ::tpyapp::m::X;` is emitted in the generated header (only `using Y = ::tpyapp::m::X;`). C++ compile error: `'X' has not been declared`. Variant B (sema): `import m; import m as alias` -- bare `m.X.method()` errors at sema as `Undefined variable: 'm'` (the alias import shadows the un-aliased binding). The same pattern affects `import pkg.sub` + `from pkg import sub`: only the last form is usable. Workaround: pick one form per file. Lives in import-binding bookkeeping (sema) and `using`-emission (codegen). Surfaced while writing a regression test for module-qualified static method calls (attempted to cover both shapes in one file).
- **[LOW medium]** `@nocopy` class cannot accept a sibling instance as a borrowed `__init__` parameter -- forces awkward factory patterns for shared-pointer-shaped types.
  Reproducer: a class like `Rc[T]` (or any `@nocopy` smart-pointer wrapper) wants a "share" constructor that takes another `Rc[T]` by borrow, bumps a shared refcount, and stores the same internal pointer. Two natural shapes both fail. `def __init__(self, x: Rc[T])` is rejected as "@nocopy type 'Rc[T]' cannot be copied into 'x: Own[Rc[T]]'" -- the param is implicitly treated as `Own[Rc[T]]`. Explicit `def __init__(self, x: Ptr[Rc[T]])` parses, but overload resolution against a `Rc(take_ptr(self))` call site picks the wrong overload (matches `Own[T]` with `T = Ptr[Rc[T]]` instead of the Ptr-taking sig). Net effect: no clean way to write a sharing constructor as a method on the class. Workaround: `tplib.Rc` uses a single underlying `__init__(cell: Ptr[_RcCell[T]])` plus a `clone()` method that handles the refcount bump and constructs the new `Rc` internally -- avoids the sharing-constructor entirely. Proper fix would involve either (a) allowing borrow semantics for the receiver-typed param of a @nocopy class's `__init__` without implicit `Own[]` lifting, or (b) better overload resolution preference rules so `Ptr[Concrete]` beats `Own[Generic]`. Surfaced while implementing Rc[T].
- **[LOW medium]** Direct inheritance of a generic `@dynamic` protocol with `T` in method-parameter position is sema-rejected as an interim guard; the proper codegen fix is still pending.
  Reproducer: `@dynamic class Sink[T](Protocol): def put(self, val: T) -> None: ...`; `class IntSink(Sink[Int32]): def put(self, val: Int32) -> None: ...`. Without the guard, the base virtual emits `virtual void put(::tpy::param_val_or_ref_t<T> val) = 0` (instantiates to `void put(const int32_t&)` for `T=Int32`), while the direct-inheritor's override emits `void put(int32_t val) override` -- different signature, override does not match, derived class remains abstract. The structural-conformance (adapter) path correctly uses `param_val_or_ref_t<T>` in the override; only the direct-inheritor path skips this. Return-position `T` (e.g. `get() -> T`) is unaffected. **Current state:** `validate_record_inheritance` rejects this shape with a diagnostic pointing users at structural conformance (test: `error_protocol_dynamic_generic_inherit_param_T`). **Pending fix:** record codegen should emit the override using `param_val_or_ref_t<concrete_T>` (or equivalently `const concrete&` for value types) so both inheritance paths work; the sema guard can then be removed. Surfaced by `/tpy-fuzzy-test generic @dynamic protocols`.
- **[LOW medium]** Variable re-export from a cycle peer fails at sema with "'X' not found in module".
  `from a import LIMIT` (where `a` is a cycle peer that itself does `from c import LIMIT`, c being a non-cycle module) hits "'LIMIT' not found in module 'a'". Same root cause as the type alias entry below: pre-population covers records / enums / protocols / functions but not variables, and at the consumer's bind_imports time the cycle peer's `exports.variables` is still empty. Pre-popping variables would carry the parser's still-unresolved `TypeRefNode` into the binding's `info` slot and crash downstream sema. Fix requires deferring variable type resolution or splitting pre-pop into a "name only" pass that runs before resolution and a "type fill" pass after. Workaround: define the variable in a non-cycle module and have the consumer import directly from there.
- **[LOW medium]** Type alias re-export from a cycle peer fails at sema with "'X' not found in module".
  `from b import ShapeAlias` (where `b` is a cycle peer of the consumer and defines `type ShapeAlias = Int32`) hits "'ShapeAlias' not found in module 'b'" -- the consumer's bind_imports runs before `b`'s, so `b.exports.type_aliases` is still empty, and the cycle re-export pre-population pass doesn't cover type aliases. Records / enums / functions are pre-pop'd; type aliases are skipped because the alias body is an unresolved `TypeRefNode` at pre-pop time and downstream sema would crash on a `TypeRefNode` reaching a `TpyType` slot. Fix requires either (a) a third pass that re-pre-pops type aliases after each module's `_resolve_module_refs` runs, or (b) deferring type alias resolution further so `_register_from_attribute_binding` can lazily fetch the resolved body. Workaround: define the alias outside the cycle and have both peers import from there.
- **[LOW small]** `from . import *` (dot-only, package-level star) silently no-ops; failure surfaces at downstream call sites with no diagnostic at the import line.
  Reproducer: inside `pkg/consumer.py`, `from . import *` is accepted without any diagnostic. The module's local definitions (e.g. `def get_value() -> ...`) then fail to show up in `pkg.consumer`'s exports, and a downstream `from pkg.consumer import get_value` errors as `'get_value' not found in module 'pkg.consumer'`. CPython treats `from . import *` as star-importing from the current package's `__init__`. TPy's compile-time expansion appears to corrupt the consumer module's export pipeline when this form is used. Fix should either implement the CPython semantics (star from package `__init__`) or reject the form at parse time with a precise diagnostic. Workaround: spell out the target as `from .module import *` or use explicit named imports.
- **[LOW small]** `from pkg import *` doesn't propagate submodule bindings exposed via `pkg.__init__.__all__`.
  Reproducer: `pkg/__init__.py` does `from . import utils; __all__ = ["utils"]`; consumer does `from pkg import *`; `utils` is not in scope (`Undefined variable: 'utils'`). CPython works. The compile-time star-import expansion walks the source's `module_attributes` and `ast.imports` but treats submodule bindings (module-namespace names) differently from records/functions/enums/variables/type aliases. Workaround: `from pkg import utils` named import.
- **[MED medium]** Borrow checker doesn't flag `old = d.get(k); del d[k]; use(old)` as a dangling pointer use.
  Use-after-free not caught by borrow checker: `old = d.get(k); del d[k]; use(old)` -- `dict.get()` returns a pointer into the dict's internal storage. `del d[k]` frees that entry, making `old` a dangling pointer. The subsequent `use(old)` is undefined behavior (reads garbage). The borrow checker should warn that `old` borrows from `d` and `del d[k]` invalidates it. Workaround: reorder to use `old` before `del`.
- **[MED medium]** Readonly-deduced method returning `Own[Span[T] | list[T]]` fails because const Span doesn't convert to declared non-const Span.
  Readonly-deduced method returns `Span[const T]` but declared return type has `Span[T]`: when a method is deduced readonly, `list_slice` on the const container returns `std::span<const T>`, but the return type `Own[Span[T] | list[T]]` uses non-const `std::span<T>`. The implicit conversion fails. Fix: propagate readonly into Span members of union return types when the method is deduced const, or emit a const_cast in codegen.
- **[LOW small]** `Rc[readonly[T]]` (shared-immutable) cannot be cloned or downgraded; `Weak[readonly[T]]` cannot be upgraded -- every refcount-mutating method (`Rc.clone`, `Rc.downgrade`, `Weak.upgrade`, `Weak.clone`) writes a count field on `self._cell` and is therefore not `@readonly`, so a `readonly[Rc[T]]` or `readonly[Weak[T]]` handle has no way to share or upgrade.
  Reproducer: `def share(r: readonly[Rc[T]]) -> Own[Rc[T]]: return r.clone()` fails because `clone()` mutates `self._cell.strong` and is therefore not `@readonly`; same shape for `downgrade()` (mutates `weak`), `Weak.upgrade()` (mutates `strong`), `Weak.clone()` (mutates `weak`). A readonly Rc/Weak reference (the documented shared-immutable use case via `Rc[readonly[T]]`) is therefore unsharable. The semantic issue is that the refcounts are **external bookkeeping** -- conceptually `mutable` in C++ terms -- whereas TPy's readonly system treats the entire Rc/Weak handle as immutable. Possible fixes: (a) a field-level `mutable` (or `@interior_mutable`) marker so the refcount fields are writable through `readonly[Self]`; (b) special-case the refcount fields via internal `unsafe_const_cast` inside `clone()` / `downgrade()` / `upgrade()` (uglier, but localized); (c) acknowledge the limitation and document that shared-immutable use cases need a different shape (e.g. an `Rc[Frozen[T]]` wrapper that owns the read-only invariant elsewhere). Surfaced during the `Rc[T]` review.
- **[LOW small]** `Covariant[T]` converting constructor codegen assumes direct field-pointer covariance, fails when the field type wraps T through a non-covariant layer (e.g. `Ptr[_RcCell[T]]`).
  Reproducer: a class `class Rc[T](Covariant[T]): _cell: Ptr[_RcCell[T]]` emits a covariant converting ctor that initializes `_cell(std::move(__other._cell))` where `__other._cell` is `_RcCell<U>*` and `_cell` expects `_RcCell<T>*` -- C++ pointer covariance doesn't propagate through `_RcCell`. Compile fails the moment a `Rc[Child] -> Rc[Parent]` coercion is attempted; the `Covariant[T]` claim is silently advertised but unusable. `Box[T](Covariant[T])` works only because its `_ptr: Ptr[T]` field is directly pointer-covariant (`Child*` -> `Parent*` in C++). Workaround in `tplib/rc.py`: do not declare `Covariant[T]` for wrappers whose field types interpose a layer. Proper fix: codegen should detect when a covariant-base field requires conversion (not just move) and either emit the proper construction (delegating to a per-type conversion helper) or sema-reject the class with a clear message pointing at the wrapping field. Surfaced during the `Rc[T]` review.
- **[LOW small]** Sema's user-function-call dispatch path doesn't resolve `PendingViewType` in the inferred type substitution; the unresolved type flows into `resolved_function_info.params` and is only resolved at codegen time on a per-call-site basis. Builtin functions explicitly pass `resolve_pending_view=True` to `_resolve_call_overloads`; user functions (including generic static methods like `Rc.new`) don't.
  Reproducer: any `Rc.new(s)` / `Box(s)` / generic `def f[T](x: Own[T])` call with a `PendingStrType` lvalue argument leaves `PendingStrType` baked into the resolved function's param types. Currently safe because the codegen sites that read these param types route through `self.types.type_to_cpp` (which calls `_resolve_pending_view`) -- specifically the `gen_call_arg` Own[str] copy-temp path was fixed in this branch by swapping `own.wrapped.to_cpp()` -> `self.types.type_to_cpp(own.wrapped)`. But any new codegen site that does `.to_cpp()` directly on a param/return type (there are 100+ such direct calls in `tpyc/codegen_cpp/` today) is a latent crash for the same bug class. Architectural fix: pass `resolve_pending_view=True` in `_analyze_user_function_call`'s `_resolve_call_overloads` call (calls.py around line 3767) -- mirrors the builtin path -- so resolved_function_info never carries PendingViewType. Until then, any new codegen direct-`.to_cpp()` call on a sema-derived type should be reviewed for this hazard. Surfaced during `/tpy-review` of the gen_call_arg fix.
- **[MED small]** `Rc.new(3.14)` (and any generic `Own[T]` factory called with a bare float literal) emits the literal value into the C++ template-argument position instead of the resolved float type.
  Reproducer: `Rc.new(3.14)` parses, sema accepts, codegen emits `::tpystd::tplib::rc::Rc<3.14> r = Rc<3.14>::new_(3.14);`. C++ rejects with `expected a type, got '3.1400000000000001e+0'`. `Rc.new(Float64(3.14))` and `f = 3.14; Rc.new(f)` both work. Distinct from the str-lvalue PendingStrType bug (fixed in `gen_call_arg` by routing the Own[str] inner-type emission through `self.types.type_to_cpp`, so `_resolve_pending_view` runs): there the bug was a direct `.to_cpp()` call on a PendingStrType bypassing the codegen resolver, here the float literal is being substituted as the template argument itself instead of being resolved to a type first. Lives in the codegen path that emits the generic instantiation for static method calls (or in the inference layer that lets a FloatLiteralType reach codegen as a type-arg). Workaround: bind the literal to an annotated local first (`f: Float64 = 3.14; Rc.new(f)`) or wrap with the concrete type (`Rc.new(Float64(3.14))`). Surfaced during the `/tpy-fuzzy-test tplib/rc.py` pass.
- **[LOW small]** `gen_call_arg`'s `Own[T]` copy-temp-and-move pattern fires uniformly across types, including trivially-copyable ones where the `std::move` is a no-op and the temp is pure noise.
  Reproducer: `s = "hi"; Rc.new(s)` emits `std::string_view __tmp_1{s}; Rc<std::string_view>::new_(std::move(__tmp_1));` -- correct but verbose; `Rc<std::string_view>::new_(s)` would suffice. The temp+move is meaningful for `std::string` (transfers heap buffer) and for non-trivially-copyable T in general; for trivially-copyable resolved types (`std::string_view`, primitives, `std::span`) it adds two redundant lines per call site. Lives in the `is_any_str_type` branch of `tpyc/codegen_cpp/expressions.py:864-873` (and by extension the parallel `auto`-deduction branch). Fix: gate the temp+move on a trivially-copyable check on the resolved Own[T] inner; pass the source through directly otherwise. Cosmetic only -- no correctness or perf concern (the move-on-trivially-copyable is a no-op in optimized builds). Surfaced reading the snapshot for `tests/cases/tplib/rc_new_str_lvalue` after the recent gen_call_arg fix.
- **[MED small]** Dict literal initialization for an `@nocopy` value type triggers a `deleted copy constructor` C++ error from `ordered_map`'s `initializer_list` ctor; per-key assignment works.
  Reproducer: `d: dict[str, Rc[Val]] = {"a": r.clone(), "b": r.clone()}` -- sema accepts the `.clone()` rvalues, but the generated `tpy::ordered_map<K, V>(std::initializer_list<std::tuple<K, V>>)` ctor calls `insert_or_assign(std::get<0>(t), std::get<1>(t))`, and `std::get<1>(t)` produces a const reference into the initializer_list element (which is itself non-mutable per the standard), forcing a copy of the `V`. `Rc<T>::Rc(const Rc&) = delete` triggers a multi-screen template error with no TPy source location. Workaround: `d: dict[str, Rc[Val]] = {}; d["a"] = r.clone(); d["b"] = r.clone()` (works -- `operator[]=` goes through move-construction). Generalizes to any `@nocopy` V (Box, user `@nocopy` records, future `Arc`); also expected to bite `set[Rc[T]]` literals once `set[Rc[T]]` is allowed at all (see following entry). Fix paths: (a) sema-level rejection of dict/set literals with `@nocopy` value types, with a hint pointing at the per-key assignment workaround; (b) `ordered_map`'s `initializer_list` ctor moves elements out via `std::move(const_cast<...>)` (ugly but standard-allowed for `initializer_list` elements), or codegen emits a multi-statement construction for the literal. Surfaced by `/tpy-fuzzy-test tplib/rc.py` (`sharing/probe_10.py`).
- **[MED small]** `set[Rc[T]]` and `dict[Rc[T], V]` are inconsistently rejected: sema rejects with a wrong message when `T` is a user record with `__hash__`; for `T = Int32` sema passes silently and the failure surfaces as a multi-screen C++ template error from `ordered_set`/`ordered_map`'s pair / map internals (which require copy-constructible keys).

- **[LOW small]** `hash(Box[NotHashable])` produces a generic "No matching overload" diagnostic instead of the specific class-shadowed bound violation message.
  When a class has `__hash__[T: Hashable]` shadowing class T and the receiver is `Box[NotHashable]`, the protocol-conformance path in `tpyc/sema/protocols.py:type_has_method_with_signature` correctly rejects conformance to `Hashable` (so the call is rejected), but it does so by silently dropping the overload via `continue`. The user-facing diagnostic at the `hash()` call site becomes "No matching overload for hash(Box[NotHashable])" rather than the more informative "Method '__hash__' requires type parameter 'T' to satisfy 'Hashable', but 'NotHashable' does not conform" that the operator dispatch path emits. ## Safety / borrow checker
- **[LOW small]** Missing diagnostic: passing `coro: Awaitable[T]` (non-`Own`) to a consuming sink emits invalid C++ instead of a sema error.
  Reproducer: `def consume_it[T](coro: Awaitable[T]) -> Task[T]: return _make_executor_owned_task[T](coro)`. The non-`Own` param is a borrow (emitted as `T_coro&`); the sink consumes its arg via `make_executor_owned_task<T>(CoroT&&)`. Codegen correctly doesn't move from a borrow, but sema doesn't reject either, so `CoroT` deduces to `T_coro&` and `std::optional<T_coro&>` fails the C++ build with an unhelpful template-stack error. **Workaround:** annotate the param as `Own[Awaitable[T]]`. **Fix:** sema should detect "borrow protocol passed to consuming-only sink" and emit a TPy diagnostic suggesting `Own[Awaitable[T]]`.
- **[LOW small]** Missing diagnostic for non-last-use of an `Own[T]` arg passed to a forwarding-style `@cpp_template`; user gets an unhelpful C++ template error instead of a TPy sema error.
  Reproducer: `def caller[T](coro: Own[Awaitable[T]]) -> Task[T]: task = _make_executor_owned_task[T](coro); return _make_executor_owned_task[T](coro)`. Codegen auto-moves `Own[T]` args at last use (post v1.2 step 2); the first call is not last-use, so `coro` is emitted as a bare lvalue, the C++ forwarding ref deduces `CoroT = T&`, and `std::optional<T&>` fails to compile with a deep template-stack error. **Workaround:** copy explicitly via `tpy.copy(coro)` if you need two uses (only valid for copyable T), or refactor to call once. **Fix:** sema should detect "Own[T] referenced after a non-last-use consume site" and emit a clear TPy diagnostic. (Before v1.2 step 2 this was a runtime use-after-move via a hard-coded `std::move({N})` in the template; now it's a C++ build failure.)
- **[HIGH medium]** Returning a borrow into an `Own[OptionalType[P_ref]]` / `Own[UnionType non-value]` param's storage is a dangling pointer; no diagnostic.
  Three shapes today emit compiling-but-unsafe C++:
   1. `def f(x: Own[P | None]) -> P | None: return x` -- the function returns `::tpy::optional_to_ptr(x)`; `x` is `std::optional<P>&&` and dies at function exit, so the returned `P*` dangles immediately.
   2. `def f(x: Own[P | None]) -> tuple[P | None, Int32]: return (x, ...)` -- the returned tuple holds `&*x` in its first slot; same dangling lifetime.
   3. `def f(u: Own[A | B]) -> A | B: return u` -- `::tpy::to_ptr_variant(u)` emits pointers into the value-variant param; same dangling lifetime at function exit.
  Same family as the existing "Cannot return local or temporary as reference" diagnostic that fires for plain `Own[T]` returning a borrow -- but the storage/borrow-form duality of pointer-repr Optional and pointer-variant Union means the returned shape (`P*` / `variant<A*, B*>`) looks like a pointer-form return rather than a borrow into a value, and the existing dangling-return check doesn't trip. The codegen paths landed in the `tuple-optional-lift-2` branch (`_optional_pointer_form_value`'s `optional_locals` lift, the `is_own_ptr_variant_param` return branch) are doing what the source asks; the sema-level rejection is missing. **Tests on master** (`tests/cases/auto_move/scalar_own_optional/`, `scalar_own_union/`) currently exercise these three shapes -- they pass only because the read-back happens immediately after the call and the optional/variant destructor doesn't clobber the bytes before the read. Will fail under ASan or under different compiler optimization levels. **Fix:** extend the dangling-reference check in `sema/compatibility.py` (or `sema/statements.py`'s return path) to reject `return x` and `return (x, ...)` when the returned shape is borrow-form pointer/variant AND the source is an `Own[OptionalType[P_ref]]` / `Own[UnionType non-value]` param. The tests will need updating once the diagnostic lands.
- **[MED medium]** Simple-generator yields holding references into the iterable (`tuple[..., T]` borrow form) dangle if the iterable is structurally mutated between polls.
  Both simple-for-NativeIterable and simple-while branches in `tpyc/codegen_cpp/gen_generators.py` emit a `make_generator<std::tuple<..., T&>>` slot when the yield type is a non-Optional tuple of non-value elements -- the yielded tuple holds a `T&` into the iterable's backing storage. If the consumer or the lambda's post-yield code structurally mutates the iterable (`items.append(...)`, `items.clear()`, dict insert that triggers rehash), already-yielded references dangle. The borrow checker doesn't track iterator-captured containers, so the unsafe pattern compiles silently. Fix path: extend the borrow checker to track "iterable captured by reference in generator lambda", reject structural-mutation methods on it for the duration of any outstanding yielded reference. In the meantime, falling back to value-form yields (`elem_type.to_cpp()` instead of `to_cpp_return()`) trades performance for safety -- could be wired behind an opt-in if user impact warrants.
- **[MED medium]** `async def` with reference-typed parameters: a `Task<T>` constructed via `asyncio.create_task` (or `Task::from_coro`) that escapes the caller's scope can dangle on those parameters.
  `tpyc/codegen_cpp/gen_async.py:_classify_params` stores non-value-type async-def params as C++ reference fields (`T& param`) in the coroutine struct. When the struct is moved into a `Task<T>` via `create_task` and the Task outlives the parameter's source storage, the reference becomes dangling. Per `docs/ASYNC_DESIGN.md` "Parameter capture": "For escaping calls (`create_task(some_async(items))` where `items` is local to the caller), the borrow checker rejects it." That rejection is not yet implemented. Workaround: pass `Own[T]` so the coroutine struct stores by value, or pass via `Box[T]`. Fix: extend the borrow checker / closure-escape analysis to flag `create_task(f(local_ref))` where `f` captures the ref by reference and the call escapes.
- **[MED medium]** Borrowed-mode `await` operands can dangle if the awaited reference-type object does not outlive the suspension.
  Async codegen stores reference-type awaitables (for example `Future[T]`) as a raw pointer in the coroutine frame so `await f` preserves object identity and another task can complete the same Future. This is correct for stable lvalues such as frame fields, but it is unsafe if the operand is a temporary or a shorter-lived local whose lifetime ends before the awaiter resumes. The missing borrow check is the same shape as the escaping `create_task` capture bug above: any borrowed await operand must be proven to outlive the coroutine suspension, or the compiler should reject it with a clear diagnostic.
- **[MED medium]** Borrow tracker only checks param names; global mutations are silent (`ref = g[0]; g.append(x)` produces no warning).
  Globals not tracked in borrow system: `mark_param_mutated` only checks `current_param_names` (`context.py:688`), so global variable mutations are invisible to the borrow tracker. `ref = g[0]; g.append(x)` produces no warning.
- **[MED medium]** Nested function analysis runs in isolated borrow state; nonlocal mutations inside closures don't propagate.
  Nonlocal mutations invisible to outer scope: nested function analysis runs in isolated state (`save_function_state`/`reset_function_tracking`). Mutations to nonlocal variables inside closures don't propagate back to the outer function's borrow tracker.
- **[MED medium]** Borrow check runs in Phase 1 using direct mutation facts; transitive structural mutation through helper methods is missed.
  User-type indirect structural mutation not detected: `_is_invalidating_method` uses `direct_structural_mutated_params` (Phase 1), so `add_twice()` calling `self.add()` which does `self._items.append()` is not caught. Phase 2 propagates `structural_mutated_params` transitively, but the borrow check runs during Phase 1. Fix: add deferred borrow checks after Phase 2, similar to `resolve_pending_borrow_checks`.
- **[LOW medium]** `v = s[0]` where `s: Span[str]` registers `s` as the str-borrow source, but mutations to the backing container don't invalidate `v` (alias chain).
  `Span[str]` subscript view: `SpanType.subscript_borrows()` is intentionally not overridden because `v = s[0]` registers `s` as the str-borrow source, but mutations to the backing container (`arr[0] = "x"` where `s = Span[str](arr)`) call `mark_str_borrowers_mutated("arr")` -- missing `s`. Fix requires `mark_str_borrowers_mutated` to chase the borrow tracker's alias chain so backing-container mutations also invalidate views borrowed through spans.
- **[LOW large]** Only built-in view types (Span, Ptr) are tracked as borrows; user-type view tracking needs the field-vs-class annotation design.
  View type borrow tracking for user types: currently only built-in view types (Span, Ptr) are tracked as borrows. Likely needed when designing tpy stdlib types. See escape analysis design doc (Future Extensions) for field-level vs class-level annotation tradeoffs.
- **[LOW medium]** Hoisted `string_view` (or `const auto&`) loop variable still references container memory after the loop; mutation post-loop dangles it.
  Hoisted non-value loop variable as view: `for s in items: ... print(s)` where `s` is `std::string_view` -- the hoisted `s` is a view into the container, not a copy. If the container is mutated between loop exit and use of `s`, the view dangles. Same concern exists with `const auto&` loop vars. Consider emitting a value copy for hoisted non-value loop variables.
- **[MED small]** `return StrView(local_str)` not caught -- explicit StrView construction from a local owned string slips through the return-dangling check.
  Both `def f() -> StrView: s = some_str(); return StrView(s)` (non-generic) and `def f[T](x: T) -> StrView: s = str(x); return StrView(s)` (generic) compile silently and produce a dangling view at runtime. The output starts with garbage bytes because `s` is destroyed at function return. The check at `compatibility.py:check_dangling_reference` covers the implicit-coercion case (returning `s` directly with declared return `StrView` is rejected) and explicit `StrView(s + "!")` constructed from a temporary, but the `_view_constructor_arg` path gates on `expr.call_type is not None` -- which is not set when `StrView(s)` is analyzed as a regular function call. The fallback `is_dangling_return(TpyCall(StrView, ...))` reaches the "regular function call -- assume safe" branch and returns False. Same gap inherited by the new lambda/yield view-dangling checks for `lambda x: StrView(local_str)` patterns where `local_str` is a named local rather than constructed inline. Fix: extend `_view_constructor_arg` to recognize `StrView(...)` / `BytesView(...)` / `Span[...](...)` calls regardless of the `call_type` setting, then check whether the constructor's argument is dangling.
