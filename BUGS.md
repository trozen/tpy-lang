# Bugs

Known compiler defects: incorrect output, crashes, miscompiles, rejection of valid code, missing diagnostics for unsafe code.

For missing features and language design gaps see `TODO.md`.

Each entry's first line is a **[priority size]** tag plus a one-sentence summary; the full description follows on the next lines. Priority is one of:

- `IMM` -- users hit this in their first non-trivial program (or basic Python idioms);
- `HIGH` -- users hit this regularly in non-trivial programs / stdlib work;
- `MED` -- specific patterns or advanced features;
- `LOW` -- latent / quality / hardening, no current user impact.

Size is one of `small` (hours-1d), `medium` (1-3d), `large` (~week), `xlarge` (bigger).

## Compiler bugs
- **[LOW small]** Sema/codegen asymmetry on Own-peeling for polymorphic-subclass narrowing facts. Sema's `_polymorphic_subclass_fact` in `tpyc/sema/statements.py:1384` applies a local `_peel` that strips `OwnType` and `ReadonlyType` before calling `is_polymorphic_subclass_fact` -- so an `Own[Pet]` parameter narrowed via `isinstance(p, Dog)` produces a fact. The three codegen call sites in `tpyc/codegen_cpp/statements.py` (`_build_isinstance_init_clause`, `_emit_isinstance_extractions`, the `_gen_if` post-guard filter) pass `lookup_var_type(...)` directly, and `polymorphic_source_inner` (`tpyc/typesys.py:3389`) only strips `Readonly` -- so codegen sees the OwnType and the predicate returns False. Result: sema thinks the fact is alive, codegen drops it; the std::get/std::any branches don't match either and the emit falls through to the variant-extraction path or produces a C++ compile error. **Fix shape:** bake Own-stripping into `polymorphic_source_inner` itself so it benefits all 5+ call sites uniformly (sema fact filter, codegen if-init, codegen extraction, codegen post-guard filter, expressions.py inline isinstance). Pre-existing on master; widened to a 3rd codegen call site by `fix-poly-early-return-narrowing`. Filed during /tpy-review of `fix-poly-early-return-narrowing`.
- **[LOW small]** Mutual hashed-container-element cycle between two records (`class A: s: Own[set["B"]]; class B: s: Own[set["A"]]`) silently emits ill-formed C++. The Kahn-algorithm cycle-fallback in `tpyc/codegen_cpp/records.py::sort_records_by_inheritance` appends both records in source order; whichever emits second sees a complete `std::hash<>` for its element, but whichever emits first does not -- the user sees a wall of C++ template errors instead of a TPy-level diagnostic. The new hash-element edges introduced on `validate-tuple-own-opt-poly` make this failure mode newly reachable (inheritance-only edges could not produce element-side cycles). **Fix shape:** detect cycles where the dependency type is `hash-element` (as distinct from `inheritance`) and emit a TPy diagnostic ("`set`-of / `dict`-keyed cycle between records X and Y") with guidance to break the cycle via an indirection (`Own[set[Box[Y]]]` etc.). Filed during /tpy-review of `validate-tuple-own-opt-poly`.
- **[LOW small]** Property setter for an `Optional[Polymorphic]` field emits a confusing diagnostic. The user writes `@pet.setter def pet(self, value: Optional[Pet]) -> None: ...` (where `Pet` inherits a `@dynamic` protocol). Sema's `_apply_property_setter_wrapping` (`tpyc/sema/method_expansion.py:270-276`) auto-wraps the first setter param in `Own[]`, producing `Own[Optional[Pet]]`. The centralized `validate_type` rejection then fires with "Use `Optional[Pet]` or `Box[Pet]`" -- but the user already wrote `Optional[Pet]`; the auto-wrap is invisible. **Fix shape:** at setter wrap time, skip the Own wrap for `Optional[<polymorphic class>]` params (the unwrapped Optional[Pet] shape is the right setter surface for polymorphic targets). Requires threading the type registry into `_apply_property_setter_wrapping` via `expand_methods_for_record`. Alternative: emit a setter-context-aware diagnostic from validate_type's OwnType branch when the call-site indicates an auto-wrap, though that requires passing context through validate_type. Filed during /code-review of the `own-opt-poly-reject` branch.
- **[LOW small]** Free-function and free-method signatures containing `Own[Optional[Polymorphic]]` skip the centralized sema rejection when the polymorphic target class is defined LATER in the same module. `register_function` (`tpyc/sema/registration.py:2619`) calls `validate_type` once at registration time, and `is_polymorphic_class_type` returns False for unregistered records (the "forward-ref defer" path documented in the OwnType rejection). The deferral works for record fields/methods because `validate_record_field_protocols` re-runs validate_type after inheritance is finalized; no analogous second pass exists for free functions. **Fix shape:** add a per-module post-Phase-1 pass that re-validates free-function param + return types after all records' inheritance is processed (analogous to `validate_record_field_protocols`). Filed during /code-review of the `own-opt-poly-reject` branch.
- **[LOW small]** `isinstance(self, Sub)` inside a generator method body (`def f(self) -> Iterator[T]: ... yield ...`) is rejected at sema; codegen support has two unresolved pieces. (1) The generator frame captures `__self: const T&` unconditionally, even for non-`@readonly` generators -- so the cast input is always const, and codegen needs to emit `const Sub*` for self in generator bodies (`_is_const_borrow_source` would need to treat `self` as const-borrow when `generator_self_ref` is set). (2) The `__next__` body uses goto-based state-machine dispatch (`case N: goto __resume_N`), and the C++17 if-init form codegen uses for polymorphic dispatch (`if (Sub* __ptr = dynamic_cast<...>(...); __ptr) {`) is rejected by C++ when a `goto` target inside the if-block bypasses the init. **Fix shape:** in `polymorphic_cast_arg`, treat `self`-in-generator as a const source (independent of method readonly-ness); gate `_build_isinstance_init_clause` on `not in_generator_body` and fall through to the fresh-cast extraction path (which doesn't have the goto-jump-over issue). Filed during /code-review of the `self-isinstance-dispatch` branch.
- **[LOW small]** `await coro` where `coro` is a local typed as a `@dynamic` protocol (e.g. `coro: Own[Cancellable[T]]`) is rejected at sema with "await operand must be a direct call to an async def, a Task[T] / Future[T], or a value of a type with a __poll__ ... method", and a sema-side workaround that recognizes the protocol shape exposes a downstream codegen bug: the borrowed-await path emits `__sub_0 = &(coro)` (`unique_ptr<P>*`) where it should emit `__sub_0 = coro.get()` (`P*`). Both halves need fixing together: extend the await operand check in `tpyc/sema/expressions.py` (around the `_extract_awaitable_inner` fallback) to accept `Cancellable[T]` / `Awaitable[T]` protocol-typed operands by unwrapping their type-arg slot, and teach the borrowed-await codegen in `tpyc/codegen_cpp/gen_async.py` to call `.get()` on `unique_ptr<P>` sources instead of taking address-of. New code path opened by the `feat-cancellable-async-typing` work (Cancellable is now an implicit-stdlib protocol so users can write `Own[Cancellable[T]]` directly); no test exercises the shape today because the existing async tests all await fresh call expressions, not protocol-typed locals.
- **[LOW small]** A user-defined top-level function whose name collides with an imported stdlib function (e.g. `def run(...)` alongside `import asyncio` + `asyncio.run(...)`) makes codegen emit the wrong namespace qualifier for the qualified call: `asyncio.run(caller())` generates `::tpyapp::__main__::run<...>(...)` (the user module's namespace) instead of the asyncio namespace, so the call references a non-existent symbol and C++ fails (`'tpyapp::__main__' has not been declared`). Sema picks the right FunctionInfo (the generated signature is asyncio.run's `run<T>(Adapter...)`), so this is a codegen namespace-qualification bug -- the qualified-call emit keys the namespace off the bare name and a same-named local function shadows the import. Workaround: don't name a local function the same as an imported stdlib function you also call qualified. Surfaced while authoring the Phase-D3 `await_in_for_else` test (a local `async def run` shadowed `asyncio.run`).
- **[LOW small]** Asymmetric variable-lookup between the two arms of the post-guard fact filter in `_gen_if` (`tpyc/codegen_cpp/statements.py` around line 4032). The `is_recursive_union` arm uses `self.ctx.var_types.get(k)` (locals + params only) while the new polymorphic arm uses `self.ctx.lookup_var_type(k)` (locals + params + globals + self). A recursive-union `self.field` or module-global narrowed via early-return is silently excluded from `post_facts` while a polymorphic one in the same shape is included. The polymorphic arm's behavior is the correct one; the recursive-union arm should align. Pre-existing; surfaced during /tpy-review of `fix-poly-early-return-narrowing`.
- **[LOW small]** Termination-check on the early-return post-guard narrowing path uses `isinstance(then_body[-1], (TpyReturn, TpyRaise))` (`tpyc/codegen_cpp/statements.py` around line 4024), which is strictly shallower than `stmts_terminate()` -- it misses then-bodies whose last statement is a `TpyIf` that terminates on every path (e.g. `if cond: return X` `else: return Y` as the trailing statement). Affects both the recursive-union arm and the new polymorphic arm; the polymorphic fix on `fix-poly-early-return-narrowing` widened the surface where the gap is reachable. **Fix shape:** swap the shallow check for `stmts_terminate(then_body)` so nested-if-on-all-paths termination triggers the post-guard extraction. Filed during /tpy-review of `fix-poly-early-return-narrowing`.
- **[MED small]** `await fn(*args, ...)` for a non-value vararg element type miscompiles silently. `tpyc/codegen_cpp/gen_async.py::_gen_coro_emplace_arg` doesn't route `TpyVarargPack` through `_gen_vararg_pack`; it falls through to `_gen_expr`'s generic fallthrough, which emits literal `/* unknown expr */` C++. No TPy diagnostic -- the C++ compiler errors out with an opaque "no matching call to optional::emplace()". Two further-blocking issues even after the dispatch is wired: (a) the async-def factory param type is emitted as `std::span<const T>` rather than `tpy::varargs<T>` (sync/async vararg-lowering divergence in `tpyc/codegen_cpp/functions.py` vs `gen_async.py`), and (b) the call-site temp `std::array<T*, N>` is a `__poll__` stack local, so the borrow inside the constructed sub-coro frame dangles across the first suspension. Safe lowering would need to hoist the temp into the *awaiter's* coro frame (parallel to M4's rvalue-receiver lift). Reproducer: `async def f(*xs: SomeRefType): await asyncio.sleep(0); for x in xs: ...; async def g(): r1 = ...; await f(r1)`. Surfaced while probing whether a CPython-shape variadic `asyncio.gather(*tasks)` was feasible (it is not for async-def varargs today; v1.5 M9 shipped `asyncio.gather(*tasks)` as a *sync* factory returning an awaitable, plus `gather_list(tasks)` for the list shape -- both homogeneous, sidestepping this bug). All three pieces still need to land before any user-facing *async-def* vararg API (e.g. the CPython-shape heterogeneous variadic-tuple `gather[*Ts]`).
- **[LOW small]** Subclass `__init__` body that writes to an inherited `@nocopy + __del__` field (`self.base_nocopy_field = expr`) emits `this->base_nocopy_field = ...` which fails C++ compile -- the type has neither copy- nor move-assignment, so the body-form write is unbuildable. No sema or codegen guard rejects this; the path was always reachable, but `fix-mil-hoist-reorder` made it slightly more reachable because any inherited-field assign now also breaks the MIL chain for subsequent own fields. Real-world impact low: users typically initialize base fields via `super().__init__(...)` rather than direct assignment in the subclass body. Fix: reject in sema (writing to a non-default-constructible inherited field outside `super().__init__()` arguments) with a guidance message pointing at the super() pattern. Surfaced by /tpy-review of the MIL hoist fix.
- **[LOW small]** Phase 20 slicing-site sema rejection (`_check_polymorphic_slicing` in `tpyc/sema/compatibility.py`) misses borrow shapes beyond `(TpyName, TpyFieldAccess, TpyMethodCall, TpyCall)`. Specifically `TpySubscript` (e.g., `saved = exceptions[0]; self.exc = saved` after intermediate binding, or direct `self.exc = exceptions[0]`) and `TpyIfExpr` (`self.exc = a if cond else b`) both produce a polymorphic borrow that bypasses the gate. The original BUGS.md slicing footgun resurfaces through these source shapes. Fix: extend `is_borrow_shape` at `tpyc/sema/compatibility.py:267-270` to include both. Surfaced by /tpy-review of the Phase 20 branch.
- **[LOW small]** Phase 20 slicing-site rejection skips when source is `Own[T]` (correct in general -- move semantics preserve dynamic type), but the existing `Own[Child] -> Own[Base]` coercion guard in `_check_compat` (around line 867) only fires when both sides are `is_user_record`. For native exception types (`Own[ValueError]` move into `Own[BaseException]`) neither guard fires and the silent slicing is reintroduced for the move path. The `Box[Throwable]` user-facing pattern means real user code is unlikely to hit this in practice, but the gap is an ownership-invariant hole. Fix: extend the type-mismatch guard to native subclass-into-base owned moves, or add a Throwable-specific carve-out at the slicing-rule layer. Surfaced by /tpy-review of the Phase 20 branch.
- **[MED small]** Nesting two `await`-in-`finally` regions is rejected at CFG-build time. The inner `AsyncFinallyExit` would need to forward a pending exception (`std::current_exception` stored in the inner's slot) or a pending return (the inner's return-value slot + flag) to the outer's slots when the outer is itself a CFG-based finally. Today the inner exit unconditionally rethrows / emits `Poll::ready`, skipping the outer finally body. Reproducer: `try: try: await x(); finally: await y(); finally: await z()` -- pinned by `tests/cases/async/error_await_in_control_flow`. Fix: at AsyncFinallyExit emit time, walk the active region stack for an enclosing TryRegion with `captured_exc_field` / `pending_return_flag`; if present, store-and-transition to its `finally_entry_bb` instead of rethrow/Poll::ready. Roughly 0.5 day once the M3.3 infrastructure is hot.
- **[LOW small]** `else:` on `async for` is rejected at parse time (`tpyc/parse/parser.py`; reproducer `tests/cases/async/error_async_for_else`). Sync `for`/`while`-`else` with a suspension is now supported (generator-resumable migration Phase D3: the CFG models break-vs-normal-exit with distinct edges -- normal-exit runs the else, `break` targets a separate after-BB that skips it -- so no "exited-via-break" flag is needed). `async for` stays rejected because its `__anext__`-driven advance (a Yield, not an `AsyncForAdvance` terminator) doesn't yet route the normal-exit edge through an else region. Fix when needed: give `_build_async_for` the same exit-BB/after-BB split as `_build_for` so the `async for` advance's exhausted edge runs the else.
- **[LOW small]** `__finally_ret_<n>` frame slot for M3.3.2 pending-return is declared with bare `T name;` (default-init), no NSDMI. The control flow guarantees the slot is assigned before any `std::move(this->__finally_ret_<n>)` reads it (return saves to slot, then state transitions to finally entry, then AsyncFinallyExit moves), so this is safe today. But unlike the sibling `__finally_pending_<n>` bool (which gets `= false` NSDMI), there's no in-class default initializer to make the invariant explicit. A future refactor that introduces a path reading the slot before the return-site assignment would silently `std::move` from an uninitialized value. Fix: add NSDMI for the value slot too -- value-types can use `{}` (zero-init / default ctor); reference-type slots already wrap in `std::optional`.
- **[MED medium]** `__exit__`'s `exc_val: Optional[BaseException]` parameter can be stored in `self` fields (or escaped to a longer-lived owner) with no sema guard; the underlying `const BaseException*` points into the catch block's exception object, which is destroyed when the catch handler returns. If `__exit__` returns `True` (suppression), the exception is destroyed immediately on catch-block exit and any stored pointer dangles. Before v1.5 M2, `exc_val` was always `nullptr` so the path was inert; M2 makes it a live polymorphism-intact pointer and the dangling-pointer footgun becomes reachable. Reproducer (intentional misuse): `class CM: last: Optional[BaseException] = None; def __exit__(self, et, exc_val, etb) -> bool: self.last = exc_val; return True`. After the suppressing `with` exits, `self.last` is a dangling pointer; any subsequent read is UB. Fix: borrow-checker escape analysis on `exc_val` -- it must not be stored in self fields, returned, or passed to functions that may store it. Pairs with the existing slicing-site sema rejections entry in TODO.md (similar shape: reject lifetime-impossible escapes of polymorphic Optional pointers).
- **[MED medium]** `tpyc/typesys.py::contains_type_param` (simplified in a recent WIP commit) now uses `inner_types()` which explicitly filters out INT-kind `TypeParamRef`s (e.g. `N` in `Array[T, N: int]`); callers in Send/Sync derivation, `registration.py`, `expressions.py`, and `calls.py` silently miss INT-kind TPRs embedded in `NominalType.type_args`. The previous `contains_type_param` walked `NominalType.type_args` directly to detect this; the regression is undocumented. Compounding: `tpyc/test_contains_type_param.py` was deleted in the same WIP commit (it explicitly guarded the INT-kind walk + the `names` filter), removing the only test coverage for this behavior. Related: `tpyc/sema/type_ops.py::is_type_param_ref` (new helper used in 4 `registration.py` sites) covers only `PtrType`, `OwnType`, `ReadonlyType`, `Array`, `List` -- misses `CallableType`, `UnionType`, `OptionalType`, `dict`, `set`, generic `NominalType` wrappers. Generic record method params of type `Optional[T]` / `int | T` / `Callable[[T], int]` would not be recognized as type-param-bearing. Also: `tests/cases/generics/generic_field_with_wrapper_typeparam` test was added in the same WIP series to cover one variant of this, but doesn't cover the `CallableType`/`UnionType` blind spots. Fix: restore `contains_type_param`'s INT-kind handling (or document the deliberate behavior change with a justification); expand `is_type_param_ref` to cover the missing type shapes; add regression tests for the previously-covered paths. Surfaced by /tpy-review of the v1.5 M2 / dyn-isinstance branch.
- **[LOW small]** Reusing the same `as`-variable name across sibling `with` blocks miscompiles when the type is a value type (e.g. `int`).
  Reproducer: `with CM() as x: ...; with CM() as x: ...` where `CM.__enter__` returns an `int`. Generated C++ rebinds via `x = &(__ctx_2.__enter__())` -- pointer assignment to a value-type local -- and the C++ build fails. The pointer-local rebinding path in `_gen_with` (`tpyc/codegen_cpp/statements.py:2370` area) was designed for reference types and should fall through to value-copy assignment (`x = __ctx_2.__enter__();`) when `item.enter_type.is_value_type()`. Surfaced while writing follow-up tests for v1.5 M1; not v1.5-introduced (the pointer-local path predates this work). Workaround: use distinct names.
- **[LOW small]** `__exit__` returning `bool` may suppress `CancelledError` (matches CPython behavior but is a known footgun).
  v1.5 M1's `with` codegen catches `::tpy::BaseException&` -- which includes `CancelledError`. A user-defined `__exit__` that returns `True` on any caught exception silently swallows task cancellation. This matches CPython's `__exit__` contract (cancellation IS a BaseException subclass exactly so user code can choose to suppress it), but is worth flagging because production task-runner code typically wants to NOT suppress `CancelledError`. No sema guard today. (M5's `async with` is cleanup-only -- `__aexit__` returns `None` -- so the footgun doesn't apply to async with yet; it activates when E9 / Phase 20 enables `exc_val: Optional[BaseException]` inspection + suppression for `__aexit__`.) Possible mitigation: sema warn on bare `return True` in `__exit__` / `__aexit__` bodies that don't explicitly handle `CancelledError`. Until then, document in the language tour.
- **[MED small]** Match-class-pattern `as` bind is silently read-only when the bind ends up pre-declared as `std::optional<T>`. Writes to bound-record fields hit the optional's copy, not the live variant slot.
  Reproducer (plain `.py`): a record `class C: payload: A | B` whose method `set_x(v)` writes `self.payload.x` via narrowing -- `match self.payload: case A() as a: a.x = v; case _: raise ...`. The terminating wildcard arm causes sema's match analyzer (`tpyc/sema/match.py:260-271`) to mark the bind as "definitely-assigned" and add it to `if_branch_decls`. Codegen's branch-decl pre-pass (`tpyc/codegen_cpp/statements.py:_emit_branch_decls`) then emits `std::optional<A> a;` ahead of the switch; the case body does `a = std::get<0>(__match_subject); a->x = v;` -- the second `=` writes into the optional's local storage, not back into `__match_subject` (and from there `self.payload`). Without the terminating wildcard, the bind stays inline (`auto& a = std::get<0>(...)`) and writes propagate; that's why simple two-arm patterns (no wildcard) work. **Fix:** either narrow the pre-decl criterion to only fire when the bind is used after the match (not just "definitely-assigned" inside it), or change branch-decl emission so a class-pattern-derived bind uses `T*` storage and assigns `&std::get<N>(__match_subject)` inside the arm. Surfaced while building Pascal variant-record `@property` setters; worked around at the Pascal level by routing setters through "construct a fresh variant, assign payload wholesale" -- but that workaround needs the second item below to also be fixed.
- **[MED small]** Reassignable record local is stored as `std::optional<T>`, which fails C++ overload resolution when assigning the local to a `std::variant<T, U, ...>` field of which `T` is a member.
  Reproducer (plain `.py`): a record `class C: payload: A | B` whose method builds a fresh `A` in a local and assigns it to `self.payload` -- `fresh = A(); fresh.x = 5; self.payload = fresh`. The local `fresh` is emitted as `std::optional<A> fresh` (TPy's reassignable-record-local storage convention), then `this->payload = std::move(fresh)` fails: `variant<A, B>` has no `operator=` taking `std::optional<A>`. Adding an explicit type annotation (`fresh: A = A()`) doesn't change the storage shape. **Fix:** at the assignment site, if the LHS is a `UnionType` whose members include the local's bare type and the RHS is an `optional`-stored local, codegen should unwrap (`*fresh` or `std::move(*fresh)`) on the way in. Alternatively, give locals annotated with a single record type the bare `T` storage shape rather than `std::optional<T>` -- but that's a wider invariant change. Surfaced while building Pascal variant-record `@property` setters that needed to construct a fresh variant alternative and assign it to a union-typed `payload` field.
- **[LOW small]** `is_type_non_copyable` walks `type_args` for phantom type params (type args not stored in any field), producing over-conservative copy errors.
  Reproducer (pre-Phase-4): `class Tagged[T]: tag: Int32` -- T is phantom (no T-typed field). `Tagged[Rc[X]]` (Rc is `@nocopy`) reports as non-copyable even though no Rc is actually stored. Surfaced visibly after Phase 4 extended `is_type_non_copyable` to recognize abstract `@dynamic` protocols: the `dynamic_generic_field` test had to switch from copy to `Own[...]` move because `Tagged[Greeter]` is now flagged. The fix walks `type_args` only when they're reachable through fields. Pre-existing imprecision; surfaced during the Phase 4 cleanup of the Box[P].set/clone/take work.
- **[LOW small]** `unsafe_init` is not abstract-T-safe -- its `@cpp_template("::new(...) {T}({1})")` placement-new fails for abstract T.
  Latent today (no current caller after Phase 2's Box.set rewrite uses `unsafe_replace` instead). Any future stdlib type using `unsafe_init` for in-place reconstruction with abstract T will hit ill-formed C++ at template instantiation. Proper fix: either (a) add an abstract-T overload of `unsafe_init` that rejects/redirects via `if constexpr (is_dyn_protocol_base_v<T>)`, or (b) sema-reject `unsafe_init[T]` calls where T is abstract @dynamic. The primitive's semantics ("placement-new at this slot") don't have a meaningful interpretation for abstract T (the slot's actual size depends on the dynamic type, not T), so option (b) is arguably more honest.
- **[LOW small]** Pre-Phase-3 `Box.take()` body had latent UB on non-trivially-destructible T: `T val = std::move(*_ptr); ::operator delete(_ptr, alignof(T));` skipped `~T()` on the moved-from object before freeing storage.
  Fixed in Phase 3 by routing through the new `tpy::transfer_ownership` helper, whose concrete branch does `T val = std::move(*p); destroy_at(p); ::operator delete(...);`. Logging the historical defect here for the audit trail; the symptom was UB on any T with a non-trivial destructor that ran through Box.take. Surfaced by the Codex review of the Box[P] plan; fix landed alongside the abstract-T case.
- **[LOW small]** `heap_replace` / `transfer_ownership` exception safety: the concrete branches assume the move ctor / move-construct doesn't throw, but don't enforce it; a throwing move ctor would leave the slot in a UB state (double-destroy or leak).
  Reproducer (latent): hypothetical `class T: def __copy__(self) -> Own[Self]: raise SomeError(...)` -- or any T whose move construction has an observable side effect that throws. `heap_replace<T>` (concrete branch) runs `destroy_at(p)` before placement-new; if `::new(p) T(std::move(value))` throws, the Box's `_ptr` still points at a now-destroyed slot, and `Box.__del__` re-runs `heap_release(p)` -> double-destroy UB. `transfer_ownership<T>` (concrete branch) has the symmetric gap: `T val = std::move(*p)` throwing skips `destroy_at(p) + operator delete` -> leak. Safe today because TPy emits noexcept moves for all generated structs (no user-defined move constructors), and standard types T = `T` (record-by-value) get default noexcept moves. Fix: add `static_assert(std::is_nothrow_move_constructible_v<T>)` (matches `heap_take`'s implicit assumption) or annotate the helpers `noexcept(std::is_nothrow_move_constructible_v<T>)` so the precondition shows up in error messages. Pre-existing in `heap_take` too. Surfaced by /tpy-review of the Box[P] Phase 1-5 work.
- **[LOW small]** Async executor multi-thread race: `_current_executor` (TPy module global in `lib/tpy/asyncio/_executor.py`) is a single process-wide `Ptr[Executor]`, not thread-local. The nested-executor backstop in `Executor.__init__` only checks `_current_executor`, so two concurrent `asyncio.run` calls on different threads will both pass the check and then race on `_set_current_executor` / `_clear_current_executor`. v1 asyncio is single-executor-per-process by design (documented invariant) so this is latent today; switch to a TPy thread-local module global when TPy gains that facility OR when multi-threaded async (v3+) is on the roadmap. - **[HIGH medium]** Returning a borrow into an `Own[OptionalType[P_ref]]` / `Own[UnionType non-value]` param's storage is a dangling pointer; no diagnostic.
  Three shapes today emit compiling-but-unsafe C++:
   1. `def f(x: Own[P | None]) -> P | None: return x` -- the function returns `::tpy::optional_to_ptr(x)`; `x` is `std::optional<P>&&` and dies at function exit, so the returned `P*` dangles immediately.
   2. `def f(x: Own[P | None]) -> tuple[P | None, Int32]: return (x, ...)` -- the returned tuple holds `&*x` in its first slot; same dangling lifetime.
   3. `def f(u: Own[A | B]) -> A | B: return u` -- `::tpy::to_ptr_variant(u)` emits pointers into the value-variant param; same dangling lifetime at function exit.
  Same family as the existing "Cannot return local or temporary as reference" diagnostic that fires for plain `Own[T]` returning a borrow -- but the storage/borrow-form duality of pointer-repr Optional and pointer-variant Union means the returned shape (`P*` / `variant<A*, B*>`) looks like a pointer-form return rather than a borrow into a value, and the existing dangling-return check doesn't trip. - **[MED medium]** Borrowed-mode `await` operands can dangle if the awaited reference-type object does not outlive the suspension.
