# Bugs

Known compiler defects: incorrect output, crashes, miscompiles, rejection of valid code, missing diagnostics for unsafe code.

For missing features and language design gaps see `TODO.md`.

Each entry's first line is a **[priority size]** tag plus a one-sentence summary; the full description follows on the next lines. Priority is one of:

- `IMM` -- users hit this in their first non-trivial program (or basic Python idioms);
- `HIGH` -- users hit this regularly in non-trivial programs / stdlib work;
- `MED` -- specific patterns or advanced features;
- `LOW` -- latent / quality / hardening, no current user impact.

Size is one of `small` (hours-1d), `medium` (1-3d), `large` (~week), `xlarge` (bigger).

## Compiler bugs
- **[MED] An inherited `async def` (await / `async with` / `async for`) on a GENERIC base miscompiles.** `class IntBox(Box[Int32]): ...` where `Box[T]` defines `async def fetch(self) -> T` and `IntBox` inherits it: `await b.fetch()` emits `std::optional<__coro_IntBox_fetch>` -> g++ `'__coro_IntBox_fetch' was not declared; did you mean '__coro_Box_fetch'?`. The non-generic inherited case is fixed (`coro_struct_owner` re-bases the coro-struct owner onto the method's defining record), but for a generic base the inherited method's resolved `owning_type_qname` reports the *subclass* (generic instantiation re-owns it), so the re-base no-ops and the receiver-named struct is emitted but never created. Even if the owner were re-based to `Box`, the struct is templated (`__coro_Box_fetch<int32_t>`) and the rebuilt owner carries empty `type_args`. No TPy diagnostic; C++ build error only. Pre-existing -- identical error on master; the non-generic fix did not touch this path. Reachable for any concrete subclass of a generic base with an inherited async method / context manager / async iterator. **Fix shape:** the re-based owner must carry the receiver's MRO binding of the base's type params (from `Derived.mro_ancestors`), and the generic-instantiation method re-owning must preserve the defining base's qname. Surfaced by /tpy-review of the non-generic inherited-async fix. Needs `/tpy-fix-bug`.
- **[LOW small] `with` / `async with` / `async for` walk the MRO for their dunders, but subscript (`__getitem__` / `__setitem__`) lookup does not.** A subclass that inherits `__getitem__` / `__setitem__` from a base (without overriding) silently fails the subscript operator -- the slice-lookup sites in `tpyc/sema/expressions.py` (`record.methods.get("__getitem__")` / `"__setitem__"`, ~lines 3479/3520) are own-only, unlike the MRO-aware `get_method_overloads_with_parents` now used for the with/async-with/async-for manager/iterator dunders. Pre-existing (present on master); same inherited-dunder gap, different operator. **Fix shape:** route the subscript dunder lookups through `get_method_overloads_with_parents` too. Surfaced by /tpy-review (architecture-fit) of the inherited-async fix.
- **[LOW small] A generic record's type-parameter bound is not enforced at a bare annotation that does not construct.** `x: Box[Rc[Int32]]` where `class Box[T: Send]` is accepted with no error even though `Rc[Int32]` violates the `T: Send` bound -- `tpyc/sema/type_ops.py::validate_record_type_args` (reached from variable-annotation validation) checks arity / kind / forward-refs but never consults `record_info.type_param_bounds` via `satisfies_bound`. Construction sites DO enforce it (`_analyze_record_constructor` in `calls.py`, and the generic-factory call path), so a record obtainable only via a constructor/factory (e.g. `Channel` via `channel[T: Send]()`) is covered in practice; the gap is bare annotations with no construction. Affects every bounded generic record, not just Send/Sync markers (protocol/subtype bounds too); no diagnostic. Surfaced designing `Channel[T]` Send enforcement (Phase 4); applies directly to the channel's `Sender`/`Receiver`/`_ChanState` records (which now carry the `T: Send` bound) -- e.g. `rx: Receiver[SharedCache]` as a bare annotation is not rejected, only `channel[SharedCache](...)` at construction is. **Fix shape:** have `validate_record_type_args` validate substituted type args against the record's `type_param_bounds` via `satisfies_bound`, mirroring the construction-site check. Needs `/tpy-fix-bug`.
- **[MED small] Tuple-unpack target locals are not hoisted into the coroutine/generator frame, so they cannot survive an `await`/`yield`.** `async def f(): tx, rx = make_pair(); await tx.send(...); await rx.recv()` fails the C++ build with `'tx' was not declared in this scope` (and `'rx' ...`) -- the unpacked locals are emitted as plain block locals, not frame slots, so they vanish across the suspension boundary. Single-target assignments (`x = ...`) and params ARE hoisted correctly; only the destructuring-assignment targets are missed by the across-suspension local collection. No TPy diagnostic; C++ error only. Workaround: don't hold tuple-unpacked locals across a suspension (e.g. unpack then move them into separate coroutines before the first await). Surfaced building the `Channel[T]` producer/consumer test (Phase 4). **Fix shape:** include tuple-unpack (and other destructuring) assignment targets in the resumable-frame hoist set in `gen_async.py` / `gen_generators.py` (the set that already captures simple-assignment locals). Needs `/tpy-fix-bug`.
- **[LOW small] The `Iterable[Own[T]]` copy-warning suppression is position-agnostic, silently dropping a legitimate warning for multi-arg containers.** The conformance check (`tpyc/sema/compatibility.py`, `actual_provides_own`) suppresses the "copies T elements; use copy_iter()" warning whenever the actual type carries `Own` in ANY type-arg slot. For an actual whose `Own` sits on a non-iterated arg -- e.g. `dict[K, Own[V]]` passed where `Iterable[Own[K]]` is expected (a dict iterates its keys `K`) -- the copy warning for reference-typed `K` is suppressed even though `K` is not owned. Not unsound (the copy still materializes correctly); a missed diagnostic only. Mirrors the pre-existing position-agnosticism of the expected-side strip. **Fix shape:** make the suppression position-aware -- fire only when the actual's `Own`-position signature aligns with the expected's iterated-element slot, not any slot. Surfaced by /tpy-review (safety-model) of the Own/Iterable symmetric-strip fix.

- **[MED small] `await t` where `t` is a for-loop variable over a `list[Task[T]]` fails the C++ build.** `for t in tasks: await t` (tasks: `list[Task[T]]`) emits a borrow that double-pointers the loop element -> g++ `cannot convert 'Task<T>**' to 'Task<T>*' in assignment`. The for-loop element is already a pointer/reference into the list, and the await borrow-emit re-takes its address (same `&(<already-pointer>)` family as the module-global-awaitable and module-global-with-manager entries). No TPy diagnostic. Workaround: `await asyncio.gather(*tasks)` / `await asyncio.gather_list(tasks)` instead of a manual await loop, or index (`await tasks[i]`). Fix: the await borrow-emit must not re-address a loop-var element already lowered to a pointer. Surfaced choosing the join shape for the asyncio Lock/Semaphore tests.
- **[MED small] An owned value-variant union local (`Own[A | B]`) moved onward into an `Own[A | B]` param fails the C++ build: the move emits `std::move` on the borrow `variant<A*, B*>` form, which can't bind to the value-variant `variant<A, B>&&` param.** Reproducer: `def make() -> Own[A | B]: return A(1)` then `v = make(); w = consume(v)` where `consume(v: Own[A | B]) -> Own[A | B]`. g++: `invalid initialization of reference of type 'std::variant<A, B>&&' from ... 'std::variant<A*, B*>'`. The owned union local is materialized in borrow (pointer-variant) form, but transferring ownership into an `Own[union]` sink needs the value-variant storage form -- the storage-form<->borrow-form conversion (the `to_ptr_variant` / value-variant family, sibling of the value-variant-union-return entry below) is not applied on the move. Affects BOTH single-assign (`v = make()`) and whole-tuple unpack (`v, _ = pair()`): the rvalue movability path marks `Own[A | B]` movable in both, then the move hits the form mismatch. The optional analog (`Own[P | None]`, pointer-repr) compiles -- only the value-variant union errors. Toolchain-caught, not silent; no TPy diagnostic. Pre-existing -- independent of the owned-tuple-unpack feature, which only made unpack reach the same movable-rvalue path single-assign already used. Surfaced by /tpy-review (safety-model) of owned-tuple-unpack, confirmed pre-existing via /tpy-fix-bug reproduce (single-assign fails identically). **Fix shape:** materialize the value-variant form when moving an owned pointer-variant-union local into an `Own[union]` sink (mirror the storage-form conversion the field/container-init path uses). Needs `/tpy-fix-bug`.
- **[MED small] Named-source whole-tuple unpack of an owned (`@nocopy` / `Own`-element) tuple copies the source and fails the C++ build.** `t = make_pair(); a, b = t` where `make_pair() -> tuple[Own[A], Own[A]]` (`A` is `@nocopy`) emits `auto __tup = t;` -- a copy of the nocopy tuple -> g++ `use of deleted function A::A(const A&)`. No TPy diagnostic; C++ build error only. The rvalue-source form (`a, b = make_pair()`) works (the temporary is moved into `__tup` and each element moved out -- the owned-tuple-unpack feature). The gap is the named-source path: `_gen_tuple_unpack` (`tpyc/codegen_cpp/statements.py`) binds `auto __tup = <source>` by value even when the source is a last-use movable owned tuple local, instead of `auto __tup = std::move(t)` plus marking `t` consumed. Pre-existing; surfaced implementing whole-tuple owned unpack (the narrow move-out slice). **Fix shape:** when the unpack source is a last-use movable owned tuple local, move it into `__tup` and register the consume; the copy stays correct for borrow/value tuples. Part of the named-source increment of the general move-out-of-aggregate capability (see Safety / borrow checker). Needs `/tpy-fix-bug`.
- **[LOW] `await asyncio.sleep(0)` does not yield to other scheduled tasks before re-waking the awaiter.** A zero-second sleep builds a `SleepFuture` timer that resolves immediately rather than performing a cooperative yield, so `create_task(f()); await asyncio.sleep(0)` reads the awaiter's view of any state `f()` mutates as still-stale (`f()` has not run yet), whereas CPython runs the spawned task up to its first suspension during the `sleep(0)`. Concretely `ran` stays `False` under TPy where CPython sees `True`. No diagnostic; silent scheduling divergence. Workaround: use a non-zero sleep (`sleep(0.01)`), or join the task explicitly (`await gather(...)`). Surfaced choosing the regression shape for the async-global-mutation fix.
