# Bugs

Known compiler defects: incorrect output, crashes, miscompiles, rejection of valid code, missing diagnostics for unsafe code.

For missing features and language design gaps see `TODO.md`.

Each entry's first line is a **[priority size]** tag plus a one-sentence summary; the full description follows on the next lines. Priority is one of:

- `IMM` -- users hit this in their first non-trivial program (or basic Python idioms);
- `HIGH` -- users hit this regularly in non-trivial programs / stdlib work;
- `MED` -- specific patterns or advanced features;
- `LOW` -- latent / quality / hardening, no current user impact.

Size is one of `small` (hours-1d), `medium` (1-3d), `large` (~week), `xlarge` (bigger).

## Compiler bugs
- **[IMM medium]** `__str__` vs `__repr__` not distinguished -- strings inside containers print without quotes.
- `__str__` vs `__repr__` separation: C++ `operator<<` serves as both, but Python distinguishes them. `print(x)` should use `__str__` (no quotes on strings), while container printing (`print([x])`) should use `__repr__` (quotes). Currently `operator<<` can't distinguish the two contexts. For recursive unions, `print(json_val)` where json_val holds a dict with string values prints `{'a': hello}` instead of `{'a': 'hello'}`. Affects all types, not just recursive unions -- the compiler handles this ad-hoc via `gen_print` (top-level) vs `detail::print_element` (containers). Fix: implement proper `__str__`/`__repr__` methods and have `print()` call `__str__`, containers call `__repr__`.
- **[LOW large]** Several codegen patterns trip `-Werror`, blocking warnings-as-errors.
- Enable C++ compiler warnings as errors (see `CppCompilerConfig.warn_flags` in compiler.py): blocked on exhaustive match/finally/with not emitting `__builtin_unreachable()` after end labels (`-Werror=return-type`), INT64_MIN/UINT64_MAX emitted as bare literals (`-Werror` large-integer-constant), and native globals emitting `extern T x = val` (`-Werror` extern-initialized). Also need generated code cleanup for `-Wall`/`-Wextra`/`-Wsign-conversion` (unused vars/labels/params, sign-conversion on array indexing).
- **[MED medium]** Borrow checker doesn't flag `old = d.get(k); del d[k]; use(old)` as a dangling pointer use.
- Use-after-free not caught by borrow checker: `old = d.get(k); del d[k]; use(old)` -- `dict.get()` returns a pointer into the dict's internal storage. `del d[k]` frees that entry, making `old` a dangling pointer. The subsequent `use(old)` is undefined behavior (reads garbage). The borrow checker should warn that `old` borrows from `d` and `del d[k]` invalidates it. Workaround: reorder to use `old` before `del`.
- **[HIGH small]** `repr(x)` and f-string `{}` on union types fail with "No matching overload".
- `repr()` and f-string `{}` don't work on union types: `repr(x)` where `x: A | B` fails with "No matching overload". Requires isinstance narrowing to access the concrete type. Fix: `_repr_fallback_template` should handle `UnionType` via `std::visit` dispatch.
- **[HIGH small]** `key in dict` with a tuple-typed key dispatches to tuple's `__contains__` instead of dict's.
- `key in dict` fails when key is a tuple type: the `in` operator sees the tuple LHS and tries tuple `__contains__` instead of dict `__contains__`. Workaround: use `dict.get()` or restructure keys as flat integers.
- **[HIGH medium]** `[False] * n` crashes at runtime because `list[bool]` lowers to `std::vector<bool>` (bit-packed proxy).
- `[False] * n` crashes at runtime: `list[bool]` maps to `std::vector<bool>`, which is a C++ special case (bit-packed proxy type). `repeat_range`/`from_range` don't work with it because `vector<bool>::reference` is a proxy, not a real `bool&`. Workaround: use `list[Int32]` with 0/1 values. Fix: either avoid `std::vector<bool>` (use `std::vector<uint8_t>` or `std::vector<char>` for `list[bool]`), or specialize the repeat path.
- **[MED medium]** Readonly-deduced method returning `Own[Span[T] | list[T]]` fails because const Span doesn't convert to declared non-const Span.
- Readonly-deduced method returns `Span[const T]` but declared return type has `Span[T]`: when a method is deduced readonly, `list_slice` on the const container returns `std::span<const T>`, but the return type `Own[Span[T] | list[T]]` uses non-const `std::span<T>`. The implicit conversion fails. Fix: propagate readonly into Span members of union return types when the method is deduced const, or emit a const_cast in codegen.
- **[MED small]** Inherited `__repr__` not used by `operator<<`; `print(child)` falls back to `<Child object at ...>`.
- Inherited `__repr__` not used by `operator<<`: `_gen_record_ostream` only checks direct methods (not inherited) to avoid `BaseException.__str__` leaking into exception subclasses. This means `print(child)` gives `<Child object at 0x...>` even when the parent defines `__repr__`, but `repr(child)` correctly finds the inherited method. Consider checking inherited `__repr__` while excluding known problematic base classes.
- **[HIGH small]** `repr()` of strings doesn't escape `\n`/`\t`/quotes; emits the raw bytes instead of Python escape form.
- `repr()` of a string containing special characters does not escape them. Python's `repr("a\nb")` returns the 5-char string `'a\nb'` (literal backslash + n inside quotes); TPy emits `'a` + newline + `b'` (literal newline inside quotes). Same for tabs, quotes, non-printables. Surfaces in container printing (`print([s])`, `print({s})`) and direct `repr(s)`. Fix: container/repr paths for strings should emit the Python escape form, not the raw bytes. Lives in `runtime/cpp/include/tpy/printing.hpp` (`detail::print_element` for str inside containers) and the standalone `repr()` builtin path. Test workaround: avoid `repr()` on strings with control characters.
- **[MED small]** `in` operator overload-mismatch error reports only the first overload's param type instead of all candidates.
- `in` operator error with multi-overload `__contains__`: when no overload matches, the error reports only the first overload's param type (e.g. "expected UInt8") even though other overloads exist (e.g. `bytes`). Should list all candidates like function call overload errors do.
- **[HIGH medium]** Variable re-exports through `# tpy: native_module` facades fail sema with "'X' is not a variable".
- Variable re-exports through native_module facades don't produce usable VARIABLE bindings downstream. `lib/tpy/tpy/__init__.py` is `# tpy: native_module` (declaration-only, no C++); doing `from ._submodule import SOME_CONST` there and then user code doing `from tpy import SOME_CONST` fails sema with "'SOME_CONST' is not a variable" (expressions.py:528 -- the binding kind is IMPORTED_NAME, not VARIABLE). Types/functions/records re-export through native_module facades fine; only variables hit this. Workaround: user imports directly from the submodule -- that's why `tpy.version` is a separate submodule (`from tpy.version import __version__`) rather than re-exported through `tpy`. Fix: namespace lookup should follow IMPORTED_NAME to the underlying binding and expose it as a variable when the source is a module-level const.
- **[LOW small]** `p.x = p.y + 1` emits two `deref_check(p)` calls; the LHS one is dead under C++17 RHS-before-LHS sequencing.
- Redundant LHS `deref_check` in `p.x = EXPR` when the RHS already derefed `p`. C++17 sequences RHS-before-LHS for the whole assignment, so a `deref_check(p)` on the RHS provably runs before any LHS code -- the LHS's own `deref_check(p)` is dead. `p.x = p.y + 1` currently emits `::tpy::deref_check(p).x = (::tpy::add_check<int32_t>(::tpy::deref_check(p).y, 1));` when `p`'s non-null status wasn't already established. Statement-boundary narrowing (fixed in this commit for cross-statement elision) can't help here because sema analyzes the target before the value; runtime evaluation is reversed. A narrow special case in assignment codegen would catch it: if the RHS expression emission added `p` to `non_null_ptr_vars` (via the pending-flush mechanism), the LHS can use that fact when rendered. Live in `codegen_cpp/statements.py` in the assignment emission path. Pre-existing pattern exposed by the new `ptr_deref_statement_boundary` regression test.
- **[MED small]** `is_final` flag isn't propagated when a constant is re-exported through a package `__init__.py`.
- `is_final` on `ModuleVarInfo` does not propagate through package `__init__.py` re-exports. `compiler.py::_extract_exports` populates `exports.final_variables` from `analyzer.ctx.final_globals`, which only contains *locally-declared* Finals; when `pkg/__init__.py` does `from .constants import VERSION` (where `VERSION: Final[str]`), the re-exported `VERSION` is added to `exports.variables` but not `exports.final_variables`, so downstream `_is_static_str` treats `from pkg import VERSION` as non-static. Fix: when a name is re-exported (present in `exports.reexported_variables`), look up the source module's `ModuleVarInfo.is_final` and propagate it. Noticed while threading Final info end-to-end for the macro_api `Final[str]` detection.
- **[MED medium]** Submodule `__tpy_init()` not chained when reached via attribute access on a `native_module` parent; constants read default-initialized.
- Init chain doesn't propagate transitively through native_module facades. When a non-native submodule (e.g. `tpy.version`) has module-level constants with non-trivial `__tpy_init()` and its parent is `# tpy: native_module`, user code that reaches those constants via attribute access on the parent (e.g. `tpy.version.__version__` via `import tpy`) compiles but reads default-initialized values because the submodule's `__tpy_init()` is never chained into the user module's `__tpy_init()`. Workaround: import the submodule directly (`from tpy.version import ...`) which does chain the init. Fix: emit init-chain edges for transitive imports even when the intermediate module is a native_module. Pairs with the sema fix above.
- **[HIGH medium]** `import pkg.sub` followed by `pkg.sub.X` for variable access fails sema with "Undefined variable: 'pkg'".
- `import pkg.sub` followed by attribute access (`pkg.sub.X`) not supported in tpyc; only `from pkg.sub import X` works. With `import tpy.version` + `tpy.version.__version__`, sema rejects with "Undefined variable: 'tpy'" even though the import succeeded. Works in CPython (standard Python import semantics). Workaround: use `from tpy.version import __version__` instead. Fix: bind the top-level package name as a namespace-like object after `import pkg.sub` so attribute access walks the chain. (Function-call form `import pkg.sub` + `pkg.sub.fn(...)` already works; only variable access fails.)
- **[MED small]** `BytesView` lacks `operator==`; dict/set with bytes keys fail to compile.
- `BytesView` as dict key / set element: `__hash__` works but `std::span<const uint8_t>` has no `operator==`, so `ordered_map`/`ordered_set` fail to compile. Needs an `__eq__` overload or `std::equal_to` specialization.
- **[LOW small]** List comprehension returned from a non-`Own` reference-returning function would dangle (no current reproducer).
- Comprehension in a non-`Own` reference-returning function is UB. `def f() -> list[T]: return [x for x in ...]` where the return is lowered as a reference/view (e.g. an implicit `std::vector<T>&` path) would dangle because the comprehension's `__result` lives in a GCC stmt-expr block (formerly an IIFE lambda -- same issue). Pre-existing, not introduced by the IIFE->stmt-expr conversion. No known reproducer in current tests because container returns flow through `Own[T]` (by-value). Fix: detect comprehension returns and either force `Own[T]` or reject.
- **[LOW medium]** `fixed_int.hpp` overflow-panic builds error strings via P2448 constexpr; works but is non-obvious -- should pass static `string_view`.
- `fixed_int.hpp` checked-arith helpers rely on C++23 P2448 for the `std::string` construction in their overflow panic branches -- works but is non-obvious. Cleaner alternative: have `tpy_panic` take a `string_view` literal and pass a pre-formatted static message (avoids the `std::string(fixed_int_name<T>()) + "..."` concat entirely). Requires changing panic-message formatting everywhere.
- **[HIGH small]** `%` on floats uses C `fmod` truncation instead of Python floor; diverges for mixed-sign operands.
- `tpy::fmod` / `tpy::fmod_f32` use C's `std::fmod` (sign-of-dividend, truncation), but Python's `%` on floats uses floor semantics (sign-of-divisor). Agrees for same-sign operands but diverges for mixed signs (Python `-1.5 % 2.5 == 1.0`; `std::fmod(-1.5, 2.5) == -1.5`). Fix: replace with `a - floor(a / b) * b` in both the runtime and constexpr paths. Will change the result of `%` on mixed-sign floats, so bump related snapshots.
- **[MED medium]** Overflow / div-by-zero in `Final` initializers surfaces as a C++ constexpr error instead of a clean tpyc diagnostic.
- Final initializer overflow / div-by-zero (`Final[Int32] = -INT32_MIN`, `Final[float] = A / 0.0`) currently surface as cryptic C++ constexpr errors via P2448 rather than clean tpyc sema diagnostics. Users should never see a C++ error. Fix: fold constant Final initializers in sema and emit a proper diagnostic (with source location + explanation) when the fold panics. The P2448 rejection can remain as a last-resort safety net but should not be the user-visible mechanism.
- **[IMM small]** `for e in f():` where `f()` returns `Own[list[T]]` fails C++ compile (lvalue ref to rvalue).
- Iterating directly over a call that returns `Own[list[T]]` fails C++ compilation: `for e in make_batch(n):` emits `auto& __obj_0 = make_batch(n);` which can't bind an lvalue reference to an rvalue. Happens both at top level and inside function bodies. Workaround: bind the call to a named local first (`batch = make_batch(n); for e in batch:`). Fix: use `auto&&` (or `auto` for value types) for the hidden iteration temporary when the iterable expression is an rvalue. Likely in `codegen_cpp/statements.py` for-loop emission.
- **[MED medium]** Same-named local in a while body and a sibling if/elif branch produces "not declared" C++ errors due to single inner-scope hoist.
- Variable-hoist gap across sibling scopes: when the same local name is declared with `name: T = ...` inside a while-loop body **and** inside a sibling if/elif branch of the same function, the codegen hoists a single declaration at the loop's (inner) scope and then emits bare `name = ...` (no type) for the sibling branches, producing "not declared in this scope" C++ errors. Reproduced in `base64._b64_encode` while writing the stdlib module -- names `b0`/`b1` used inside `while ...:` and inside the subsequent `if rem == 1:`/`elif rem == 2:` branches. Workaround: rename the variables in the sibling branches. Fix: hoist same-name locals across branch-sibling scopes to the function scope (or emit fresh declarations in each branch). Lives in the codegen scope/hoist logic.
- **[MED small]** Free function with a `bytearray` param + in-body `.append()` codegens `const&` and fails C++ compile; methods work.
- Free function with `bytearray` parameter + in-body mutation (`param.append(...)`) gets the parameter lowered as `const std::vector<uint8_t>&` in generated C++, then fails with "passing const ... discards qualifiers" from `push_back`. Reproduced in `hashlib._pack_be32(dst: bytearray, v: UInt32)` while writing the SHA-256 module. Methods mutating `self.buffer` (bytearray field) work fine, so the issue is specific to free-function params. Workaround: inline the packing at the caller instead of a helper. Fix: sema mutation-detection should register `bytearray.append` (and other mutating methods) as param-mutating so auto-const inference doesn't strip mutability.
- **[MED small]** Empty bytes literal `b""` rejected as default parameter value despite being a constant expression.
- Default parameter value `b""` (empty bytes literal) rejected at sema: "Default parameter value must be a constant expression (literal, None, or fixed-int constructor like Int32(5))". Empty bytes literal IS a constant. Reproduced in `hashlib.sha256(data: bytes = b"")`. Workaround: use `bytes | None = None` and check for None. Fix: recognize `b""` (and possibly bounded-size `b"..."`) as a constant default value in `sema` default-value validation.
- **[IMM medium]** PEP 484 string return-type annotations (`-> "ClassName"`) and `from __future__ import annotations` fail parse.
- Forward-ref string annotations `-> "ClassName"` (PEP 484 style) in return types fail with "Cannot parse type annotation: Constant(value='ClassName')". `from __future__ import annotations` triggers the same failure because all annotations become string constants. Reproduced in `hashlib.SHA256.copy(self) -> "SHA256"`. Workaround: order class definitions before use sites and drop `__future__ annotations`. Fix: parser should accept string constants in annotation contexts and defer resolution to sema.
- **[HIGH medium]** `from pkg import submod` doesn't bind `submod` as a usable namespace; only `from pkg.submod import X` works.
- `from pkg import submod` doesn't bind `submod` as a usable name -- only `from pkg.submod import X` works. Reproduced when `lib/tpy/re.py` tried `from _bindings import pcre2` then `pcre2.compile(...)` -- sema rejects with "'pcre2' not found in module '_bindings'" unless the parent package's `__init__.py` explicitly re-exports the submodule. Workaround: import each name individually (`from _bindings.pcre2 import compile, code_free, OPT_CASELESS, ...`), aliasing collisions away. The re facade pays this with a 20-line import block of aliased symbols. Same root cause family as `import pkg.sub` + attribute and the qualified-type / qualified-except entries below -- submodule names don't surface as namespace bindings in user code.
- **[MED medium]** `field: pkg.Type` rejected in annotations as "Unsupported qualified type"; forces alias-on-import.
- Qualified type names (`pkg.Type`) rejected in type annotations: sema errors "Unsupported qualified type: <name>". Even after `from pkg.submod import X as _Alias` succeeds, declaring `field: pkg.submod.X` requires the alias too. Reproduced in `lib/tpy/re.py` declaring `_md: Ptr[pcre2.MatchData]`. Workaround: alias-on-import (`from pkg.submod import X as _Alias`), use `_Alias` in annotations. Same root cause as the `from pkg import submod` gap.
- **[HIGH small]** Module-level `Final` constants rejected as default parameter values; forces inlining the literal.
- `Final[X] = SOME_NAMED_CONST` rejected as default-parameter value: sema accepts only literals, None, or fixed-int constructors (e.g. `UInt32(0)`). Forces `def f(flags: UInt32 = UInt32(0)) -> ...:` instead of the readable `def f(flags: UInt32 = NOFLAG) -> ...:`. Surfaced across every signature in `lib/tpy/re.py`. Fix: accept references to module-level `Final` constants in default-arg position (they're as constant as a literal -- no runtime evaluation).
- **[HIGH medium]** `f(0)` for an unsigned param errors "expected UInt64, got Int32" -- literals that provably fit should coerce.
- Non-negative integer literals don't coerce to unsigned target types at call sites. `f(x: UInt64)` called with `f(0)` errors "Type mismatch in argument 'x': expected UInt64, got Int32" -- forces `f(UInt64(0))`. This is consistent with the documented widening rules (LANGUAGE_FEATURES.md: `Int32 -> UInt64` cross-sign widening is deliberately not automatic because negative signed values don't round-trip through unsigned types), but literals are a special case: their values are known at compile time, so the compiler can prove `0`, `1`, `256` etc. fit any unsigned target without losing information. Surfaced heavily in `lib/tpy/re.py` where PCRE2's C API uses `size_t`/`uint32_t` throughout (every `_pcre_match(..., UInt64(0), UInt32(0), ...)` call site). Fix: sema should treat integer literals as "untyped" (Rust-style) or "polymorphic" at call sites -- when the target is a fixed-width type and the literal's value fits, use the target type directly instead of DefaultInt. Overflow-detection stays compile-time (reject `UInt8` arg passed `300`).
- **[HIGH small]** `except re.error:` rejected by parser; forces `from re import error` at module top.
- `except qualified.name:` rejects qualified exception class names: parser errors "'except' requires a simple name". Catches like `except re.error as e:` must be rewritten `from re import error; ... except error as e:`. Mechanical: parser's except-clause should accept attribute access (same shape as a type annotation).
- **[MED small]** `from re import error as re_error; except re_error:` codegens `catch (const re_error&)` -- alias used as C++ type, fails compile.
- Aliased import in except clause emits the alias name as a C++ type. `from re import error as re_error; ... except re_error as exc:` codegens `catch (const re_error& exc)` -- using the alias name as if it were the C++ type, which fails to compile ("re_error was not declared"). The unaliased form `from re import error; except error as exc:` correctly emits `catch (const ::tpystd::re::error& exc)`. Fix: codegen for catch-clause types should resolve the import alias to the underlying qualified type name (same way the call-site path resolves `compile(...)` -> `::tpystd::re::compile(...)` when imported aliased).
- **[MED medium]** Staticmethod bodies emit inline in the .hpp, forcing every type they reference to be defined above the enclosing record.
- `@staticmethod` bodies on records are always emitted inline in the generated `.hpp`, forcing users to order `.py` declarations so every type the body *references* (throws, constructs by value, instantiates generics with) is a complete type before the owning record. Regular functions and instance methods split header/source -- the body lives in `.cpp` where forward declarations are enough. For a staticmethod, a forward decl of a thrown exception type is not enough: C++ needs the complete type to throw, so `raise MyError(...)` from a staticmethod forces `class MyError` to be defined above the enclosing record. Surfaced in `lib/tpy/re.py`: the `error` exception class and its `_pcre2_error_msg` helper both had to move above `_OwnedCode` (which has a `_compile` staticmethod throwing `error`) -- there is a comment there explaining the constraint. Same hazard for any staticmethod that returns-by-value or constructs a user type declared later in the file. Workaround: manual reordering. Fix: emit non-template staticmethod bodies to the `.cpp` like other non-template methods -- templates must stay inline, but that's the same existing rule as the rest of codegen. The inline-only emission for staticmethods appears to be an artifact of how records-level codegen lays out method bodies, not a deliberate design choice.
- **[HIGH medium]** User Exception subclass doesn't auto-inherit native `__init__(message)`; `raise error("msg")` rejected.
- User Exception subclass doesn't auto-inherit native `__init__(message)`: `class error(Exception): pass` then `raise error("msg")` errors "'raise error()' does not accept arguments". CPython auto-inherits `Exception.__init__` via MRO; TPy requires each subclass to declare its own. Best workaround today (used by `lib/tpy/re.py::error`): declare `def __init__(self, message: String = "") -> None: super().__init__(message)` -- `String` (std::string) is needed instead of `str` because `tpy::Exception(std::string)` has no string_view overload (see next entry). Result: `re.error` is catchable but the param-type signature differs from CPython's idiomatic `str`. Fix options: (a) one-line C++ struct + `@native` binding for each user exception (matches existing _exceptions.py pattern, requires runtime/cpp/ touch); (b) sema synthesizes `__init__` for user Exception subclasses with empty bodies, delegating to the parent's native constructor.
- **[MED small]** BaseException hierarchy has only `std::string` ctor -- forces user exceptions to type message as `String` not `str`.
- `tpy::Exception` (and the rest of the BaseException hierarchy in `runtime/cpp/include/tpy/core.hpp`) only has a `std::string` constructor; passing a `std::string_view` fails to compile because there's no implicit conversion. This forces user-defined Exception subclasses with explicit `__init__` to type their message param as `String` (std::string) rather than the more idiomatic `str` (std::string_view). Surfaced in `lib/tpy/re.py::error.__init__`. Two fixes, either works: (a) add a `BaseException(std::string_view msg) : message(msg) {}` overload in core.hpp -- one line, matches std::string's own string_view-accepting constructor; (b) codegen materializes string_view -> std::string at super().__init__ call sites where the parent constructor expects std::string. (a) is strictly simpler and less surprising for users who write the C++ themselves.
- **[HIGH medium]** Generic `U` substituted with `str` produces `string_view` for both param and return -- owned-string result dangles.
- Generic `U` over `str` drops lifetime when composed with `Fn[...]` returning `U`. Minimal repro (no stdlib):
  ```python
  def apply[U](f: Fn[[U], U], init: U) -> Own[U]:
      return copy(f(init))
  print(apply(lambda s: s + "!", "hello"))   # prints garbled bytes
  ```
  Codegen infers `U = std::string_view` (the param form of `str`), so the lambda is generated as `[](std::string_view) -> std::string_view { return str_concat(...); }` -- `str_concat` returns an owned `std::string`, the implicit conversion yields a dangling view. The non-generic form (`def apply_str(f: Fn[[str], str], init: str) -> str: ...`) works because `str` return type is correctly `std::string`. Surfaced while wiring `lib/tpy/functools.py::reduce`; functools ships with an int/float smoke case and a docstring warning to avoid str reduce until this lands. Same root-cause family as the heapq note about generic-T not specializing `T = std::string` to `std::string_view` for params -- both are the codegen-time split between "storage type" and "parameter type" for `str` not being threaded through generic substitutions. Fix: when substituting a generic param with `str`, use `std::string` for storage slots (return types, local slots, return-value bindings) and `std::string_view` only for `param_val_or_ref_t` at call boundaries. Lives in codegen type-mapping for generic substitutions.
- **[MED medium]** Generic overloaded function with an `Fn[...]` param can't resolve named function refs or lambdas in the callable slot.
- Overload resolution + `Fn[...]` param: when a generic function is `@overload`ed and one parameter is typed `Fn[...]`, neither named-function refs nor lambdas resolve in the callable-argument slot. Repro (with both overloads local, no stdlib):
  ```python
  @overload
  def f[T, U](g: Fn[[U, T], U], a: list[T], init: U) -> U: ...
  @overload
  def f[T](g: Fn[[T, T], T], a: list[T]) -> T: ...
  def add(x: Int32, y: Int32) -> Int32: return x + y
  f(add, xs)                     # error: 'add' is not a variable
  f(lambda a, b: a + b, xs)      # error: lambda params cannot be inferred
  ```
  The 3-arg form works -- `f(add, xs, Int32(0))` and `f(lambda a, b: a + b, xs, Int32(0))` both compile. Single-overload functions with an `Fn` param work fine with both named refs and lambdas. So the bug is specifically in overload candidate enumeration not trying each candidate's `Fn` signature as a type context for the callable argument (and not re-checking named-function refs against each candidate's `Fn` param). Surfaced when writing `lib/tpy/functools.py`: drop the CPython-style 2-arg `reduce(func, a)` until this lands, ship 3-arg only. Fix: during overload resolution, when a candidate expects `Fn[...]` at position `i`, pre-type-the-arg against that `Fn` signature (for lambdas) or look up the name as a function ref convertible to that `Fn` (for named refs) before computing the candidate's match score. Lives in `sema/overloads.py` / `sema/calls.py`.
- **[MED small]** Overload resolution scores positional args only -- kwargs don't break ties (e.g. `prod([], start=1.0)`).
- Overload resolution doesn't use keyword arguments to disambiguate. With two overloads `prod(Iterable[int])` and `prod(Iterable[float])`, the call `prod([], start=1.0)` should pick the float overload via the `start` kwarg's type, but the resolver scores candidates on positional arg types only -- `[]` conforms to both `Iterable[int]` and `Iterable[float]`, and the kwarg never breaks the tie. Surfaced trying to add an `Iterable[int]` `math.prod` overload alongside the existing float one (attempted and reverted; see `lib/tpy/math.py` header). The infrastructure exists (`_expand_arg_types_with_kwargs` in `sema/overloads.py:562` already widens the arg-type tuple with kwargs), so the fix is plumbing scoring rather than new logic. Workaround: ship N overloads instead of N+1, or split the function name (`prod_int` / `prod_float`).
- **[MED medium]** `(a, b)` of `@nocopy`/`Own[T]` elements codegens copy-construction or tuple-of-references; both wrapping shapes break.
- Tuple construction of `@nocopy`/`Own[T]` elements is broken in both wrapping shapes, with two distinct failure modes that share one fix. Returning `(a, b)` where `a: Handle` is `@nocopy`:
  1. **Return type `tuple[Own[Handle], Own[Handle]]`** codegens `std::tuple<Handle, Handle>{a, b}` -- lvalue copy, fails with "use of deleted function Handle(const Handle&)".
  2. **Return type `Own[tuple[Handle, Handle]]`** codegens `std::tuple<Handle&, Handle&>{a, b}` -- a tuple of *references* to the locals, which then can't convert to the value-holding return type `std::tuple<Handle, Handle>` ("could not convert ... to tuple<Handle, Handle>").
  Blocks CPython-compatible `accept() -> (socket, (host, port))` and `socketpair() -> (sock, sock)` signatures in `lib/tpy/socket.py` regardless of where the `Own` wrapper goes -- Phase 1 shipped `accept() -> Own[Socket]` (caller uses `.getpeername()`) and dropped socketpair. Expected codegen in both shapes: `std::tuple<Handle, Handle>{std::move(a), std::move(b)}`. Lives in codegen tuple-construction path. Minimal repro in `/tmp/agents/own_tuple.py`.

- **[HIGH medium]** `*xs` on a user-record method rejects individual-arg packing and `*`-unpack; works on free/module functions.
- `*args` on user-record methods is unsupported at the sema layer. `class C: def m(self, *xs: float)` followed by `c.m(1.0, 2.0, 3.0)` errors with "Type mismatch in argument 'xs': expected Span[readonly[float]], got float" -- sema treats the method's `*xs` as `Span[readonly[float]]` directly and doesn't pack individual args. `c.m(*nums)` errors with "Unknown expression type: TpyStarUnpack" -- method-call sema doesn't handle `*`-unpack either. Free functions and module functions support `*args` fully (module-qualified path fixed recently); methods are the odd one out. Fix likely lives in `sema/methods.py` / `sema/calls.py` method-call dispatch: mirror the vararg-packing logic that exists for `_gen_call` / function-call resolution. Codegen side (`_gen_method_call`'s user-record arg-loop at `codegen_cpp/expressions.py:2641-2679`) would also need a `TpyVarargPack` dispatch branch once sema starts producing them -- currently that branch would be dead code.
- **[MED large]** `args[1:]` for `*args: SomeClass` (reference-type element) fails C++ compile with cryptic template-instantiation errors.
- Non-value-type `*args` pack slicing (`args[1:]`, `args[:n]`, etc. where element type is a user record / other reference type) fails C++ compilation with cryptic template-instantiation errors deep in `container_ops.hpp` -- not a clean TPy diagnostic. Root cause: `tpy::varargs<T>` primary template is dual-mode -- direct (`T* direct_` pointing to contiguous T storage, populated by `*list` unpacking) or indirect (`T* const* indirect_` pointing to a T* pointer array, populated by `f(a, b, c)` individual-arg packing). `list_slice` needs contiguous T storage to return `std::span<T>`; indirect mode has contiguous T* storage, which is not the same thing. Value-type varargs (float/int/etc.) already works via the public `data()` accessor on the value-type specialization. **Impact: real UX hit** -- any user with `*args: SomeClass` writing the natural `for x in args[1:]:` Python idiom hits a wall of C++ errors. Workaround (`for i in range(1, len(args)): x = args[i]`) is noise Python users don't voluntarily write. **Fix scope (~1 day, medium risk):** (1) runtime: add `list_slice` overload for `varargs<T, false>` returning another `varargs<T, false>` with adjusted pointers (preserves mode); (2) sema: the type of `args[1:]` on non-value varargs must be `varargs[T]` itself, not `Span[T]` -- requires threading through subscript type resolution; (3) codegen: for-loop over a varargs-slice uses the varargs iterator (already dual-mode aware), so should Just Work once types align. Risk lives in (2) -- could have cascading effects on slice-of-Span / slice-of-Array if the result-type logic is shared. **Interim** (if prioritized for UX): add a sema-level reject with a clean diagnostic pointing at this entry instead of letting C++ template errors through.
- **[MED medium]** `from X import Y` inside a function body rejected as "Unsupported statement: ImportFrom"; all imports must be at module top.
- `from X import Y` inside a function body rejected as "Unsupported statement: ImportFrom". All imports must be hoisted to module top. Hits cleanup patterns where a helper would import a single symbol near its only use site for locality. Workaround: hoist everything to the file top, even rarely-used helpers.
- **[MED medium]** Generic `Wrap[T]` storing a `Callable` for cmp_to_key-style wrappers can't feed `self.obj` through readonly-deduced `__lt__`.
- Readonly propagation through generic T blocks storing callable cmp/key in
  comparison dunders. Writing `functools.cmp_to_key`-style wrappers requires
  a generic record `Wrap[T]` with a `cmp: Callable[[T, T], Int32]` field and
  a `__lt__(self, other) -> bool` that calls `self.cmp(self.obj, other.obj)`.
  `__lt__` is deduced readonly, so `self.obj` reads as `readonly[T]`, and
  every natural path to feed it to the Callable fails:
  1. Passing `self.obj` directly: "expected 'T', got 'readonly[T]'".
  2. Typing the field as `Callable[[readonly[T], readonly[T]], Int32]`:
     compiles, but then `a - b` inside a user cmp lambda errors with
     "Invalid operand types for '-': readonly[Int32] and readonly[Int32]"
     -- basic arithmetic is not defined on `readonly[FixedInt]`.
  3. `a: T = copy(self.obj)`: "Cannot pass readonly[T] as mutable T in
     variable 'a'" -- `copy()` does not strip readonly through a generic T.
  4. Dropping `@readonly` on `__lt__`: no effect -- comparison dunders are
     readonly-deduced unconditionally and there is no escape hatch.
  Three possible fixes, each with independent value:
  (a) Teach `copy()` to strip readonly through generics (local binding
      `T = copy(readonly[T])` is safe -- copy creates owned storage).
  (b) Allow arithmetic on `readonly[FixedInt]` (reading a const int is fine;
      the const is just a local-binding marker and the operators are pure).
  (c) Allow opt-out of readonly deduction on specific methods
      (`@readonly(False)` or similar) for dunders that legitimately need
      mutable self access to callable fields.
  Surfaced while trying to add `functools.cmp_to_key`; deferred that
  stdlib item in STDLIB_ROADMAP.md until one of the three lands. (a) is
  probably the lowest-impact fix and would unblock the cleanest cmp_to_key
  implementation. Lives in `sema/` (readonly tracking through generic
  substitution / copy elision).

- **[IMM medium]** `isinstance(d, dict)`, `isinstance(d, dict[str, JsonValue])`, and `isinstance(d, AliasOfDict)` all rejected; only bare concrete classes work.
- `isinstance` should accept type aliases and generic types as the second argument. Today only bare concrete classes work: `isinstance(d, dict)` is rejected ("Generic type 'list' cannot be used as a value"), `isinstance(d, dict[str, JsonValue])` is rejected, and `isinstance(d, AliasOfDict)` is rejected per `docs/LANGUAGE_FEATURES.md:2877`. At runtime/codegen the check is just "which variant alternative does the value hold?" -- the same thing `case dict() as d:` already emits. Three layers, separable: (1) `isinstance(d, AliasOfConcreteGeneric)` -- e.g. `JsonObject = dict[str, JsonValue]`. Sema resolves the alias; runtime checks variant membership against `dict[*]`. Element type is not checked (static typing already guarantees it). Smallest scope, highest user value: makes `if isinstance(d, JsonObject): d["k"]` idiomatic for json users. (2) `isinstance(d, dict[str, JsonValue])` -- accept the parameterized form directly. One symbol away from (1). (3) `isinstance(v, AliasOfUnion)` -- e.g. `JsonValue` itself. Resolve to the alias's members; runtime tests "is value any of these alternatives". Wider change but documented as missing in LANGUAGE_FEATURES. (1) is the half-day branch in the same shape as the recursive-union fixes.
- **[HIGH medium]** `match`, assignment, and call-arg coercion all reject `Own[RecursiveUnion]` rvalues -- forces extracting a helper to consume `json.loads()` results.
- Inline consumption of `Own[RecursiveUnion]` returned from a function. Today, `d = json.loads(s); match d:` is rejected ("match subject must be a union ..., got Own[...]"), `d: JsonValue = json.loads(s)` is rejected (Own->T isn't auto-stripped on assignment), and `f(json.loads(s))` is rejected ("Cannot pass Own[...] directly to parameter ..."). The only working pattern is "extract a helper `def f(v: JsonValue): match v: ...` and call `f(d)` with the receiving local". Three small compiler improvements would make this idiomatic: (1) match analyzer accepts `Own[T]` subjects (auto-unwrap, since Own is already the ownership-transfer marker); (2) assignment from `Own[T]` rvalue to `T` lvalue auto-moves; (3) function call arg coercion accepts `Own[T]` rvalue for a `T` parameter (the receiver borrows). All three are restricted to recursive-union T -- the current rejection exists because non-value-type non-recursive unions need pointer-variant treatment and Own confuses it. Documented as a workaround in `lib/tpy/json.py` module header. The sequel branches that fixed recursive unions one bug at a time hint at the right place to look (`tpyc/sema/calls.py` for arg coercion, `tpyc/sema/match.py` for match subjects).

## Safety / borrow checker
- **[HIGH medium]** Borrow tracker silently clears active borrows on reassignment without warning -- especially dangerous for `str` views.
- Reassignment of borrowed variable doesn't warn: `remove_storage_borrows` silently clears active borrows on reassignment (`s = "other"`) without warning. Only mutation (`.append()`, `del`) triggers warnings. Affects all types but especially `str` in generators -- the only way to invalidate a `string_view` is reassignment/destruction, which is exactly the case the tracker misses.
- **[MED medium]** Borrow tracker only checks param names; global mutations are silent (`ref = g[0]; g.append(x)` produces no warning).
- Globals not tracked in borrow system: `mark_param_mutated` only checks `current_param_names` (`context.py:688`), so global variable mutations are invisible to the borrow tracker. `ref = g[0]; g.append(x)` produces no warning.
- **[MED medium]** Nested function analysis runs in isolated borrow state; nonlocal mutations inside closures don't propagate.
- Nonlocal mutations invisible to outer scope: nested function analysis runs in isolated state (`save_function_state`/`reset_function_tracking`). Mutations to nonlocal variables inside closures don't propagate back to the outer function's borrow tracker.
- **[MED medium]** Borrow check runs in Phase 1 using direct mutation facts; transitive structural mutation through helper methods is missed.
- User-type indirect structural mutation not detected: `_is_invalidating_method` uses `direct_structural_mutated_params` (Phase 1), so `add_twice()` calling `self.add()` which does `self._items.append()` is not caught. Phase 2 propagates `structural_mutated_params` transitively, but the borrow check runs during Phase 1. Fix: add deferred borrow checks after Phase 2, similar to `resolve_pending_borrow_checks`.
- **[LOW medium]** `v = s[0]` where `s: Span[str]` registers `s` as the str-borrow source, but mutations to the backing container don't invalidate `v` (alias chain).
- `Span[str]` subscript view: `SpanType.subscript_borrows()` is intentionally not overridden because `v = s[0]` registers `s` as the str-borrow source, but mutations to the backing container (`arr[0] = "x"` where `s = Span[str](arr)`) call `mark_str_borrowers_mutated("arr")` -- missing `s`. Fix requires `mark_str_borrowers_mutated` to chase the borrow tracker's alias chain so backing-container mutations also invalidate views borrowed through spans.
- **[LOW large]** Only built-in view types (Span, Ptr) are tracked as borrows; user-type view tracking needs the field-vs-class annotation design.
- View type borrow tracking for user types: currently only built-in view types (Span, Ptr) are tracked as borrows. Likely needed when designing tpy stdlib types. See escape analysis design doc (Future Extensions) for field-level vs class-level annotation tradeoffs.
- **[LOW medium]** Hoisted `string_view` (or `const auto&`) loop variable still references container memory after the loop; mutation post-loop dangles it.
- Hoisted non-value loop variable as view: `for s in items: ... print(s)` where `s` is `std::string_view` -- the hoisted `s` is a view into the container, not a copy. If the container is mutated between loop exit and use of `s`, the view dangles. Same concern exists with `const auto&` loop vars. Consider emitting a value copy for hoisted non-value loop variables.
